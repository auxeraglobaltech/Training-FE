Module 1 · Hook ⏱ 2–3 min

Why Git matters on a shared DV project

ASIC DV projects are large, long, and team-based. A single repo might contain UVM testbenches, SystemVerilog IPs, Makefiles, simulation scripts, and regression suites touched by 5–20 engineers simultaneously.

Without version control: overwritten testbench files, lost coverage closure progress, and no audit trail when a regression drops the night before tapeout.

Real cost of no version control: engineer A overwrites engineer B's UVM sequence changes — regression drops from 94% to 61%. Two hours to debug, two more to restore. Git prevents this in seconds.

Git gives your team a shared, immutable history of every change — who touched tb_top.sv, which commit broke the AXI scoreboard, and how to roll it back instantly.

Key takeaway: Git is your team's single source of truth for the entire DV environment — testbenches, scripts, coverage models, and all.
Module 2 · Core Skills ⏱ ~8 min

First-time setup and the daily loop

One-time setup on your Linux machine
# Identity — appears in every commit you make
git config --global user.name  "Your Name"
git config --global user.email "you@company.com"

# Editor used when git needs you to write a message
git config --global core.editor "vim"

# Avoid retyping credentials on every push
git config --global credential.helper store

# Make rebase the default pull strategy (cleaner history)
git config --global pull.rebase true
Clone the project repo
# SSH clone (preferred on company servers)
git clone git@github.com:your-org/asic-dv-project.git
cd asic-dv-project
git status
On branch main
nothing to commit, working tree clean
The daily loop — 5 steps, every day
1
Pull — always start here. Never work on stale code. 
git pull origin main
2
Edit — open your testbench, UVM sequence, Makefile, coverage model in your editor.
3
Stage — choose which changed files go into your commit. 
git add tb/sequences/axi_wr_seq.sv   # specific file
git add -A                           # all changes
git status                           # confirm what is staged
4
Commit — snapshot with a meaningful message. 
git commit -m "feat(axi): add back-to-back write stress sequence"
5
Push — upload to GitHub so teammates can see your work. 
git push origin your-branch-name
Handy inspection commands
git log --onelineCompact recent commit history
git diffUnstaged changes in working tree
git diff --stagedWhat is staged vs last commit
git show <hash>Full diff of a specific commit
Key takeaway: Every day starts with git pull and ends with git push. The 5-step loop is your core rhythm.
Module 3 · Core Skills ⏱ ~8 min

Creating branches and opening pull requests

On a shared DV project, you never commit directly to main. Every change — new sequence, scoreboard fix, coverage model — lives on its own branch so CI can validate it before it touches the golden baseline.

Branch naming convention
# Pattern: type/your-initials-short-description
feat/rs-axi-stress-seq           # new test or feature
fix/rs-scoreboard-overflow       # testbench bug fix
cov/rs-apb-func-coverage         # coverage model work
refactor/rs-uvm-agent-cleanup    # cleanup, no behaviour change
chore/rs-update-gitignore        # build/config changes
Create, verify, and switch branches
# Create a new branch and switch to it immediately
git checkout -b feat/rs-axi-stress-seq
Switched to a new branch 'feat/rs-axi-stress-seq'

# Confirm you are on the right branch before editing
git branch
  main
* feat/rs-axi-stress-seq

# Switch between existing branches
git checkout main
git checkout feat/rs-axi-stress-seq

# List all branches including remote ones
git branch -a
Keep your branch up to date with main
# Fetch latest from remote, then rebase your commits on top
git fetch origin
git rebase origin/main

# If teammates pushed while you were working, this replays
# your commits cleanly on top of their changes
DV tip: Use git rebase (not merge) before raising a PR — it produces a clean linear history that makes git bisect much faster when hunting a broken regression.
Push branch and open a pull request
# Push your branch to GitHub
git push origin feat/rs-axi-stress-seq

# GitHub prints a direct URL to open the PR — click it
remote: Create a pull request for 'feat/rs-axi-stress-seq':
remote:   https://github.com/your-org/asic-dv-project/pull/new/feat/rs-axi-stress-seq

# If you add commits after pushing, update the remote branch
git push origin feat/rs-axi-stress-seq
Delete a branch after it is merged
# Delete local branch
git branch -d feat/rs-axi-stress-seq

# Delete remote branch
git push origin --delete feat/rs-axi-stress-seq
Hands-on exercise
Do this now on your Linux machine
Pull latest: git pull origin main
Create branch: git checkout -b feat/your-initials-test-branch
Edit a .sv file (add a comment), then save
Stage + commit: git add -A && git commit -m "chore: test branch from micro-course"
Push: git push origin feat/your-initials-test-branch
Click the GitHub URL that appears in the terminal output
Success: GitHub shows your branch with a green "Open pull request" button. git log --oneline shows your commit at the top.
Key takeaway: Branch → commit → push → PR. Never commit directly to main. That rule protects every engineer on the project.
Module 4 · Conflict Resolution ⏱ ~10 min

Solving merge conflicts — the DV way

Merge conflicts happen when two engineers edit the same lines of the same file on different branches. They look scary the first time. They are completely routine once you know the pattern.

When do conflicts happen?
git mergeMerging a teammate's branch that touched the same files
git rebaseReplaying your commits on an updated main
git pullPulling while you have local uncommitted changes (if not stashed)
git cherry-pickApplying a commit that conflicts with your current branch
What a conflict looks like in the file

Git inserts conflict markers directly into the file. Open it in your editor and you will see:

<<<<<<< HEAD ← your current branch changes start here // AXI write latency check — version from your branch if (latency > AXI_MAX_LATENCY) `uvm_error(...) ======= ← divider between the two versions // AXI write latency check — version from incoming branch if (latency > AXI_MAX_LATENCY) `uvm_fatal(...) >>>>>>> feat/rs-axi-latency-fix ← incoming branch ends here
Rule: You must remove ALL four marker lines (<<<<<<<, =======, >>>>>>>) and keep only the final, correct code.
Step-by-step conflict resolution
1
See which files conflict 
git status
both modified:   tb/scoreboard/axi_sb.sv
both modified:   tb/sequences/axi_wr_seq.sv
2
Open each conflicted file in your editor — search for <<<<<<< to jump to every conflict marker.
3
Decide: keep yours, keep theirs, or merge both
// After editing — conflict markers removed, correct code kept: // AXI write latency check — use fatal so simulation stops immediately if (latency > AXI_MAX_LATENCY) `uvm_fatal(...)
4
Verify no markers remain 
# Quick check — should return nothing if all conflicts resolved
grep -rn "<<<<<<" tb/
5
Stage the resolved files and continue 
git add tb/scoreboard/axi_sb.sv
git add tb/sequences/axi_wr_seq.sv

# If you were doing a merge:
git commit -m "fix: resolve conflict between axi-sb and latency-fix branches"

# If you were doing a rebase:
git rebase --continue
Abort if things go wrong
# Abort a merge in progress — returns to pre-merge state
git merge --abort

# Abort a rebase in progress — returns to pre-rebase state
git rebase --abort
Use a visual merge tool (optional but faster)
# Configure vimdiff or VS Code as your merge tool
git config --global merge.tool vimdiff
git config --global merge.tool vscode

# Launch it on all conflicted files at once
git mergetool
Preventing conflicts before they happen
Pull oftenRun git pull at the start of every session — reduces drift
Small PRsMerge small changes quickly; large long-lived branches conflict more
CommunicateTell teammates before editing shared files like tb_top.sv
Rebase oftenRebase on main before a PR so conflicts surface early
Key takeaway: A conflict is just two edits to the same line. Open the file, remove the markers, keep the right code, stage it, and continue. Done in 2 minutes once you know the pattern.
Module 5 · Recovery ⏱ ~8 min

Undoing things and recovering from mistakes

Git almost never loses data permanently. The key is choosing the right undo command for the situation — some are safe, some rewrite history.

Safe to use anytime: git revert, git reset --soft, git restore.   Dangerous on shared branches: git reset --hard, git push --force — these rewrite history and can break teammates' repos.
Scenario 1 — discard unstaged changes in a file
# Throw away edits to a file (not yet staged)
git restore tb/sequences/axi_wr_seq.sv

# Discard ALL unstaged changes in the whole working tree
git restore .
Scenario 2 — unstage a file you accidentally staged
# Remove from staging area, keep the file edits
git restore --staged tb/sequences/axi_wr_seq.sv
Scenario 3 — fix the last commit message or add a missed file
# Fix the commit message (before pushing)
git commit --amend -m "feat(axi): correct commit message"

# Add a forgotten file to the last commit (before pushing)
git add tb/sequences/missed_file.sv
git commit --amend --no-edit
Only amend commits that have NOT been pushed. Amending a pushed commit requires a force-push and breaks your teammates.
Scenario 4 — undo the last commit, keep the file changes
# Move HEAD back one commit, leave files as staged
git reset --soft HEAD~1

# Move HEAD back one commit, leave files as unstaged edits
git reset HEAD~1
Scenario 5 — safely undo a commit that is already merged to main
# Creates a NEW commit that reverses the changes — safe on shared branches
git revert <commit-hash>
git push origin main
Scenario 6 — stash work-in-progress before switching branches
# Save current uncommitted changes to a temporary stack
git stash push -m "wip: axi stress seq half done"

# List everything in the stash
git stash list
stash@{0}: On feat/rs-axi-stress-seq: wip: axi stress seq half done

# Restore the latest stash and remove it from the stack
git stash pop

# Restore a specific stash entry
git stash apply stash@{0}
Scenario 7 — find a lost commit with reflog
# Git records every HEAD movement — use this to find "lost" commits
git reflog
a3f1c2d HEAD@{0}: reset: moving to HEAD~1
9b2e8aa HEAD@{1}: commit: feat(axi): add stress sequence   ← your "lost" commit

# Restore it by checking out that hash
git checkout 9b2e8aa
# Or create a new branch from it
git checkout -b recovery/rs-restore-stress-seq 9b2e8aa
Golden rule: If you are unsure which undo command to use, always reach for git revert — it adds a new commit and never rewrites history.
Key takeaway: Git almost never loses your work permanently. git reflog is your safety net. Choose revert for shared branches; reset only for local, unpushed commits.
Module 6 · Team Ops ⏱ ~8 min

Day-to-day team operations toolkit

git blame — find who changed a line and when

Regression broke? Before filing a bug, check who last touched the relevant file.

# Show author and commit hash for each line of a file
git blame tb/scoreboard/axi_sb.sv

# Show a specific line range only
git blame -L 45,60 tb/scoreboard/axi_sb.sv
9b2e8aa (R. Sharma  2024-03-12) if (rdata !== exp_data) `uvm_error(...)

# Then inspect that commit in full
git show 9b2e8aa
git bisect — binary-search for a broken commit

Regression was passing on Monday, failing on Friday. There are 40 commits in between. git bisect finds the culprit in ~6 steps instead of 40.

git bisect start
git bisect bad                        # current state is broken
git bisect good v2.4-release          # last known good tag or hash

# Git checks out a midpoint commit — run your regression, then mark it:
git bisect bad    # or
git bisect good

# Repeat ~6 times. Git announces the first bad commit:
a3f1c2d is the first bad commit
Author: J. Patel — feat(apb): added timeout override in scoreboard

git bisect reset                      # return to your original branch
git cherry-pick — apply a single commit to another branch

A teammate fixed a critical bug on their feature branch and you need it on yours right now — without merging everything else they have.

# Find the commit hash you want
git log --oneline feat/rs-apb-fix
c7d9e12 fix(apb): correct timeout calculation in monitor

# Apply that commit to your current branch
git cherry-pick c7d9e12

# If it conflicts, resolve normally then:
git cherry-pick --continue
git tags — mark release or tapeout milestones
# Create an annotated tag for a tapeout milestone
git tag -a v1.0-tapeout-freeze -m "Regression at 98.3% — tapeout freeze"

# Push tags to GitHub (not pushed automatically with commits)
git push origin --tags

# List all tags
git tag

# Check out the state of the repo at a tag
git checkout v1.0-tapeout-freeze
git log — search commit history
# Search commit messages for a keyword
git log --grep="scoreboard" --oneline

# Show commits by a specific author
git log --author="R. Sharma" --oneline

# Show commits that changed a specific file
git log --oneline -- tb/scoreboard/axi_sb.sv

# Show a visual branch graph in the terminal
git log --oneline --graph --all --decorate
Recommended .gitignore for DV repos
# Simulation outputs — never commit these
*.vcd
*.fsdb
simv
simv.daidir/
csrc/
DVEfiles/
ucli.key
*.log
regression_results/
coverage_reports/
Commit message format the whole team should use
# type(scope): short description ≤72 chars
feat(axi):     add back-to-back write stress sequence
fix(sb):       correct latency calculation in AXI scoreboard
cov(apb):      add functional coverage for error responses
refactor(uvm): split monolithic agent into sub-components
chore(ci):     add smoke regression to PR checks
docs:          update README with simulation setup steps
Key takeaway: blame to find who changed what, bisect to find what broke the regression, cherry-pick to move individual fixes, tags to mark milestones. These four commands will save you hours every week.
