MODULE 1

Why AXI? From Shared Buses to Five Channels

Learning objectives

  • Explain the bottleneck in single-channel buses that AXI removes.
  • State the core idea of AXI: five independent, decoupled channels.
  • List the headline features AXI provides (bursts, outstanding, out-of-order).
  • Place AXI3, AXI4, and AXI5 in context.
Analogy — the bank counter vs the modern bank. An old bus is a bank with one teller window: one customer fully served before the next steps up — fill the form, wait, get cash, leave. AXI is a modern bank: you drop your request at one desk, others are being processed in parallel, and you collect your result at a separate counter whenever it's ready. Requests and results are decoupled, and many are in flight at once.

The problem with one channel

Earlier buses like AHB use essentially one shared address/data path. Address and data are coupled, and a slow subordinate stalls everyone. If a read takes 100 cycles to come back from DRAM, the bus sits idle for 100 cycles — even though other useful work could be done. This is the bottleneck AXI was designed to break.

The AXI idea: five independent channels

AXI (Advanced eXtensible Interface) splits the bus into five independent channels, each with its own handshake, all able to operate at the same time:

ChannelNameDirectionCarries
AWWrite AddressManager → SubordinateAddress & control for a write
WWrite DataManager → SubordinateThe data being written + byte strobes
BWrite ResponseSubordinate → Manager"Write done" + status (OKAY/error)
ARRead AddressManager → SubordinateAddress & control for a read
RRead DataSubordinate → ManagerThe data read back + status

What this buys you

  • Decoupled address and data — a manager can send several addresses before any data comes back.
  • Multiple outstanding transactions — many requests in flight at once; slow responders don't block fast ones.
  • Out-of-order completion — responses can return in a different order than requests were issued (via IDs — Module 5).
  • Bursts — one address can transfer many data beats, amortizing addressing overhead (Module 4).
  • Independent read and write — reads and writes proceed fully in parallel on separate channels.

AXI generations

VersionHighlights
AXI3The original. Bursts up to 16 beats. Allowed write data interleaving. Has WID.
AXI4Bursts up to 256 beats (INCR). Removed write interleaving and WID. Added QoS, regions. The workhorse.
AXI4-LiteA tiny subset: single transfers only, no bursts, no IDs. For simple register interfaces.
AXI5Atomic transactions, cache-stashing, MTE (memory tagging), poison, wake-up signaling, NSAID, coherency alignment with CHI. The current generation — our main focus.
Why a verification engineer cares about all this: every one of those features is a source of legal behaviours you must cover and illegal behaviours you must catch. "Five independent channels" alone means the number of interleavings explodes — and that's before bursts, IDs, and atomics. The rest of this course turns each feature into concrete checks and coverage.

Activity — why five channels and not three?

AXI separates write data (W) from write address (AW), and read data (R) from read address (AR). Why not merge address and data into a single "write" channel and a single "read" channel (giving two channels plus the response)?

Think about when a manager knows the address versus when it has the data ready, and about letting the subordinate accept addresses faster than it can absorb data (or vice versa). What flexibility do you lose if they must move together?

Keeping address and data on separate channels lets them flow at independent rates. A manager can push several write addresses ahead while data trickles behind, or stream data while the subordinate is still accepting the address. The subordinate can apply back-pressure to data without blocking new addresses. Merging them forces lock-step movement and reintroduces exactly the coupling bottleneck AXI exists to remove. The separate B (write response) channel similarly lets completion be reported whenever the write truly lands, decoupled from data acceptance.

What is the single most important architectural idea of AXI?

Everything AXI offers — outstanding transactions, out-of-order completion, parallel read/write — flows from the five independent channels (AW, W, B, AR, R), each with its own handshake. Clock speed and encryption are not the point.

Good & Bad Practices

✓ Good practice

Build your AXI mental model channel-by-channel before thinking about full transactions.

Why: every AXI rule is ultimately a per-channel handshake rule or a cross-channel ordering rule. Master the five channels and the rest composes.

✗ Common mistake

Treating AXI like a single bus where "a write" is one atomic event.

Why it hurts: you'll write checks that assume AW, W, and B happen together, and miss the real bugs that live in their independent timing.

✓ Good practice

Know exactly which AXI version your DUT implements before writing a testbench.

Why: AXI3 allows write interleaving and has WID; AXI4 does not. A check valid for one version is a false failure on the other.

✗ Common mistake

Reusing an AXI3 VIP config on an AXI4 DUT without re-checking burst-length limits.

Why it hurts: AXI3 caps INCR bursts at 16 beats; AXI4 allows 256. Wrong limits either over-constrain stimulus (missed coverage) or generate illegal bursts (false fails).

MODULE 2

The Five Channels in Detail

Learning objectives

  • Name and interpret every major signal on all five channels.
  • Understand the role of byte strobes (WSTRB) and the LAST signal.
  • Trace a complete write and a complete read at the signal level.
  • Recognise which signals a monitor must sample on each channel.
Analogy — a shipping form. The address channels (AW/AR) are the shipping label: where it goes, how big, how it should travel. The data channels (W/R) are the contents of the boxes. WSTRB is the packing slip saying which compartments of the box are actually filled. The response (B) is the delivery confirmation signature.

Signal naming convention

AXI signals are prefixed by channel. Address signals share an Ax prefix when a rule applies to both AW and AR (e.g. AxADDR means "AWADDR and ARADDR"). Every channel has a xVALID/xREADY handshake pair (next module).

Write Address channel (AW)

SignalMeaning
AWVALID / AWREADYHandshake for the write-address channel.
AWIDTransaction ID — tags the write so responses can be matched and ordered.
AWADDRStart address of the write burst.
AWLENBurst length = number of beats − 1 (so 0 means 1 beat; 255 means 256 beats).
AWSIZEBytes per beat, encoded: 0→1 byte, 1→2, 2→4, 3→8 … up to the bus width.
AWBURSTBurst type: FIXED, INCR, or WRAP.
AWCACHEMemory attributes: cacheable, bufferable, allocate hints.
AWPROTProtection: privileged/unprivileged, secure/non-secure, instruction/data.
AWQOSQuality-of-Service priority (AXI4+).
AWREGIONRegion identifier — lets one subordinate present multiple logical regions (AXI4+).
AWLOCKExclusive-access indicator (for atomics via exclusive monitor).
AWUSERUser-defined sideband, meaning is design-specific.

Write Data channel (W)

SignalMeaning
WVALID / WREADYHandshake for write data.
WDATAThe write data for this beat (bus-width wide).
WSTRBByte strobes — one bit per data byte; 1 = this byte is valid and should be written.
WLASTAsserted on the final beat of the burst.
WUSERUser sideband.
WSTRB is where many bugs hide. Byte strobes let a manager write only some bytes of a word (a sub-word write). A subordinate that ignores WSTRB and writes all bytes corrupts the bytes that should have been left alone. Your tests must drive sparse, patterned, and all-zero strobes — and your scoreboard must model them exactly.

Write Response channel (B)

SignalMeaning
BVALID / BREADYHandshake for the write response.
BIDID of the write being responded to — must match the AWID.
BRESPStatus: OKAY, EXOKAY, SLVERR, DECERR (Module 6).
BUSERUser sideband.

There is exactly one B response per write burst — not one per beat. The subordinate sends it after it has accepted (and, depending on AWCACHE, committed) all the write data.

Read Address (AR) and Read Data (R)

AR carries the same fields as AW (ARID, ARADDR, ARLEN, ARSIZE, ARBURST, ARCACHE, ARPROT, ARQOS, ARREGION, ARLOCK, ARUSER). The R channel returns the data:

SignalMeaning
RVALID / RREADYHandshake for read data.
RIDID of the read — matches ARID.
RDATARead data for this beat.
RRESPPer-beat status (reads report status on every beat, unlike writes).
RLASTAsserted on the final beat of the read burst.
RUSERUser sideband.
Key asymmetry: a write burst gets one response on B; a read burst reports RRESP on every beat of R. Mixing this up is a classic monitor bug — counting B beats per burst, or expecting a single status for a read.

Tracing a complete single-beat write

// Manager writes 0xCAFE to address 0x1000, 1 beat, 4-byte bus
AWID=0  AWADDR=0x1000  AWLEN=0  AWSIZE=2 (4B)  AWBURST=INCR   // AW beat
WDATA=0x0000CAFE  WSTRB=0b0011  WLAST=1                       // W beat (low 2 bytes valid)
BID=0  BRESP=OKAY                                             // B response

What happens on the wires: the manager presents AW and W (possibly in the same cycle or apart), the subordinate accepts each with its READY, then drives one B beat with matching BID and a status. Note WSTRB=0b0011 means only the low two bytes are written — the subordinate must leave the upper two untouched.

Activity — read the burst parameters

A monitor captures an AR beat: ARADDR=0x2000, ARLEN=3, ARSIZE=2, ARBURST=INCR on a 32-bit bus. How many data beats will the R channel return, how many bytes per beat, and which addresses do the beats correspond to?

Beats = ARLEN + 1. Bytes/beat = 2^ARSIZE. INCR means each beat's address increases by the number of bytes per beat. Watch the off-by-one in ARLEN.

Beats: ARLEN=3 → 3+1 = 4 beats.

Bytes/beat: ARSIZE=2 → 2² = 4 bytes per beat.

Addresses (INCR): 0x2000, 0x2004, 0x2008, 0x200C.

The R channel returns 4 beats; RLAST is asserted on the 4th. Each beat carries its own RRESP. Your scoreboard must expect exactly 4 beats and flag it as an error if RLAST comes early or late.

How many B (write response) beats does a 16-beat write burst produce?

A write burst gets exactly one B response, regardless of beat count. Reads are the asymmetric case — they report RRESP on every R beat. Expecting one B per beat is a frequent monitor/scoreboard bug.

Good & Bad Practices

✓ Good practice

Model WSTRB precisely in your scoreboard — apply only strobed bytes to your reference memory.

Why: sub-word writes are common and a subordinate that mishandles strobes silently corrupts neighbouring bytes. A strobe-blind scoreboard will never catch it.

✗ Common mistake

Sampling WLAST/RLAST but not cross-checking it against the expected beat count.

Why it hurts: an early or late LAST is a real protocol bug; if you trust LAST blindly you'll mis-frame transactions and corrupt every check downstream.

✓ Good practice

Capture all sideband (PROT, CACHE, QOS, REGION, USER) in your transaction object even if the DUT ignores them today.

Why: coverage of attribute combinations and future reuse depend on it; re-instrumenting a monitor late in a project is painful.

✗ Common mistake

Assuming AWADDR equals the address of every beat in the burst.

Why it hurts: only FIXED bursts keep one address. INCR and WRAP advance per beat; a scoreboard that doesn't compute per-beat addresses checks the wrong memory locations.

MODULE 3

The VALID/READY Handshake

Learning objectives

  • State the VALID/READY handshake rule precisely and why it exists.
  • Understand the golden rule: VALID must not wait for READY.
  • Read timing diagrams for accepted, stalled, and back-pressured transfers.
  • Write the core SVA assertions that protect the handshake.
Analogy — a handshake between two people. One person extends their hand (VALID: "I'm offering this"). The other extends theirs (READY: "I'll take it"). The handshake completes only in the instant both hands are out. Crucially, the offerer must not refuse to extend their hand until they see the other's — that's a deadlock where both wait forever.

The one rule that governs everything

Every AXI channel uses the same two-signal handshake. The source asserts VALID when it has information to send. The destination asserts READY when it can accept. A transfer occurs on a rising clock edge if and only if both VALID and READY are high.

Transfer happens when: VALID == 1 && READY == 1 at a rising clock edge. On that edge, exactly one beat of information moves. If either is low, nothing moves and the source must hold its data stable.

The golden rules of the handshake

  1. Once VALID is asserted, it must stay asserted until the transfer completes (until READY is also high on a clock edge). The source may not withdraw an offer.
  2. The payload (address, data, etc.) must remain stable while VALID is held. You can't change the data mid-offer.
  3. VALID must not depend (combinationally) on READY. A source may assert VALID before READY; it must not wait to see READY before asserting VALID. (READY is allowed to depend on VALID.) Violating this risks deadlock: both sides waiting for the other.

Three timing cases

Back-pressure

When a destination can't keep up, it holds READY low — this is back-pressure. The source must wait, holding VALID and its payload steady. Back-pressure is normal and legal; it's how a slow subordinate throttles a fast manager. Good verification deliberately injects random READY-low gaps on every channel to stress these waits.

Protecting the handshake with SVA

// Rule 1: once VALID is high, it stays high until READY is seen.
property valid_stable_until_ready;
  @(posedge clk) disable iff (!rstn)
    (AWVALID && !AWREADY) |=> AWVALID;   // still valid next cycle
endproperty
a_valid_held: assert property(valid_stable_until_ready)
  else $error("AWVALID dropped before AWREADY");

// Rule 2: payload must be stable while VALID held and not yet accepted.
property addr_stable;
  @(posedge clk) disable iff (!rstn)
    (AWVALID && !AWREADY) |=> $stable(AWADDR);
endproperty
a_addr_stable: assert property(addr_stable)
  else $error("AWADDR changed while waiting for AWREADY");

What these check: the first fires if a source illegally withdraws a VALID offer; the second fires if it changes the address mid-offer. Both are protocol violations that a VIP's bundled assertions catch automatically — but understanding them is what lets you read a VIP failure message and know what it means.

The deadlock trap. If a manager's RTL is coded so AWVALID is only asserted once it sees AWREADY, and the subordinate only asserts AWREADY once it sees AWVALID, neither ever moves — a dead bus. This is why "VALID must not combinationally depend on READY" is a hard rule, and why a hang on the very first transaction often points straight at it.

Activity — is this waveform legal?

On the AW channel you observe: cycle 1 AWVALID=1, AWREADY=0 (AWADDR=0x40). Cycle 2 AWVALID=1, AWREADY=0, but AWADDR has changed to 0x80. Cycle 3 AWVALID=1, AWREADY=1 (AWADDR=0x80). Is this legal? If not, which rule is broken?

The transfer only completes in cycle 3 (both high). Look at what the payload did between the moment VALID was first asserted and the moment the transfer completed.

Illegal. VALID was asserted in cycle 1 with AWADDR=0x40, but the transfer didn't complete until cycle 3. The payload changed (0x40 → 0x80) while VALID was held and unaccepted — violating the payload-stability rule (golden rule 2). The addr_stable assertion above would fire in cycle 2. The legal behaviour is to hold AWADDR=0x40 stable until READY is seen.

Which dependency is forbidden, to avoid deadlock?

VALID must never wait (combinationally) for READY — if both sides wait for the other, the bus deadlocks. READY is allowed to depend on VALID; that direction is fine. This asymmetry is the heart of the handshake.

Good & Bad Practices

✓ Good practice

Randomise READY-low back-pressure on every channel, including B and R, in your VIP.

Why: many bugs only appear when a channel stalls mid-burst. Always-ready testbenches give a false sense of safety and never exercise the wait paths.

✗ Common mistake

Driving back-pressure only on the data channels, leaving address and response channels always-ready.

Why it hurts: address-channel and B/R-channel stalls exercise different FIFO and ordering logic; leaving them always-ready hides a whole class of buffer-overflow and ordering bugs.

✓ Good practice

Bind handshake-stability assertions (VALID held, payload stable) to every channel via a reusable assertion module.

Why: these are cycle-accurate protocol guards. A scoreboard catches functional mismatches far too late; assertions pinpoint the exact failing cycle and signal.

✗ Common mistake

Leaving handshake assertions enabled during reset.

Why it hurts: spurious reset-phase failures flood the log and desensitise the team. Always guard with disable iff (!rstn).

MODULE 4

Burst Mechanics — AxLEN, AxSIZE, AxBURST

Learning objectives

  • Compute the addresses of every beat in FIXED, INCR, and WRAP bursts.
  • Understand AxSIZE, the bus width, and narrow transfers.
  • Apply the AXI burst rules (no 4KB crossing, WRAP alignment).
  • Build a reference model that reconstructs burst addresses for the scoreboard.
Analogy — a delivery run. A burst is one truck delivering to several houses on one trip instead of returning to the depot between each. AxLEN is how many stops, AxSIZE is how big each parcel is, and AxBURST is the route pattern: FIXED keeps hitting the same address (a pump filling one tank), INCR walks down the street, WRAP loops around the block back to the start.

The three burst parameters

ParameterMeaningEncoding
AxLENNumber of beats minus 1AXI4: 0–255 (INCR), 0–15 (FIXED/WRAP). AXI3: 0–15 all types.
AxSIZEBytes transferred per beat2^AxSIZE bytes: 0→1, 1→2, 2→4, 3→8, …, must be ≤ bus width
AxBURSTHow the address evolves per beat0b00=FIXED, 0b01=INCR, 0b10=WRAP, 0b11=reserved

FIXED — same address every beat

Every beat uses the same address. Used for things like reading repeatedly from a FIFO data register or a peripheral port where the "address" is a fixed hardware location.

// FIXED: AWADDR=0x1000, AWLEN=3, AWSIZE=2 (4B)
beat 0 -> 0x1000
beat 1 -> 0x1000
beat 2 -> 0x1000
beat 3 -> 0x1000   // WLAST=1

INCR — incrementing address

Each beat's address advances by the number of bytes per beat (2^AxSIZE). This is the common case for reading/writing a block of memory.

// INCR: ARADDR=0x1000, ARLEN=3, ARSIZE=2 (4B)
beat 0 -> 0x1000
beat 1 -> 0x1004
beat 2 -> 0x1008
beat 3 -> 0x100C   // RLAST=1

WRAP — incrementing then wrapping

Like INCR, but the address wraps back to a lower aligned boundary after reaching the top of a "wrap window." This exists to support critical-word-first cache-line fills: a CPU that misses on the middle of a cache line can fetch that word first, then wrap around to collect the rest.

WRAP has strict rules: AxLEN must be 2, 4, 8, or 16 beats (so the burst is a power-of-two length), and the start address must be aligned to the transfer size. The wrap boundary = (number of beats) × (bytes per beat).

// WRAP: ARADDR=0x1008, ARLEN=3 (4 beats), ARSIZE=2 (4B)
// wrap window = 4 beats * 4 bytes = 16 bytes, aligned to 0x1000..0x100F
beat 0 -> 0x1008
beat 1 -> 0x100C
beat 2 -> 0x1000   // wrapped back to window start
beat 3 -> 0x1004   // RLAST=1

Narrow transfers and unaligned starts

If AxSIZE is smaller than the bus width, the transfer is narrow — only some byte lanes are active each beat, and which lanes shift according to address. If the start address isn't aligned to AxSIZE, the first beat is unaligned and WSTRB/byte-lane handling gets subtle. These are rich bug territory.

The 4KB rule

A burst must not cross a 4KB address boundary. Why 4KB? It's the smallest common page size, and it guarantees a single burst targets a single page — so it can't span two different subordinates or two pages with different memory attributes. A manager that needs to cross a 4KB boundary must split into two bursts. A VIP checker that flags 4KB crossings is mandatory; generating one is a protocol violation.

Reference-model address reconstruction

// Compute beat addresses for the scoreboard (simplified, aligned case)
function void beat_addrs(bit[31:0] start, int len, int size, burst_e btype);
  int bytes = 1 << size;                 // 2^AxSIZE
  int nbeats = len + 1;
  bit[31:0] wrap_mask = (nbeats*bytes) - 1;
  for (int i=0; i<nbeats; i++) begin
    case (btype)
      FIXED: addr[i] = start;
      INCR : addr[i] = start + i*bytes;
      WRAP : addr[i] = (start & ~wrap_mask) | ((start + i*bytes) & wrap_mask);
    endcase
  end
endfunction

What this does: it reproduces, in the testbench, exactly which address each beat targets — so the scoreboard can compare DUT data against the right memory location. Getting the WRAP masking wrong is one of the most common scoreboard bugs in AXI verification.

Activity — does this burst cross 4KB?

A manager issues: AWADDR=0x0FF0, AWLEN=7 (8 beats), AWSIZE=3 (8 bytes), AWBURST=INCR. Does it violate the 4KB rule? Show your work.

Compute the last byte touched: start + (nbeats × bytes_per_beat) − 1. Then check whether start and last-byte fall in the same 4KB-aligned block (i.e. whether bits [31:12] match).

Bytes/beat = 2³ = 8. Beats = 8. Total bytes = 64 = 0x40.

Start = 0x0FF0. Last byte = 0x0FF0 + 0x40 − 1 = 0x102F.

Start's 4KB block: 0x0FF0 → bits[31:12] = 0x0 (block 0x0000–0x0FFF). Last byte 0x102F → block 0x1000–0x1FFF. They differ → the burst crosses the 4KB boundary at 0x1000. This is illegal. The manager must split it into two bursts at the 0x1000 boundary. A good VIP fires a 4KB-crossing assertion here immediately.

For a WRAP burst, AxLEN+1 (the number of beats) must be:

WRAP bursts must be 2, 4, 8, or 16 beats and start-aligned to the transfer size, because the wrap boundary is computed as beats × bytes-per-beat and must be a clean power-of-two window (this is what makes critical-word-first cache fills work).

Good & Bad Practices

✓ Good practice

Constrain stimulus so bursts are protocol-legal (no 4KB crossing, WRAP power-of-two and aligned), then separately test that the DUT rejects/handles illegal ones if it must.

Why: unconstrained random generates illegal bursts that produce false failures, drowning the real bugs.

✗ Common mistake

Computing WRAP addresses as if they were INCR.

Why it hurts: the scoreboard checks the wrong memory locations after the wrap point, reporting mismatches that look like DUT bugs but are testbench bugs.

✓ Good practice

Add functional coverage on (AxSIZE × AxBURST × narrow vs full-width × aligned vs unaligned).

Why: bugs cluster at the intersection of narrow transfers and unaligned starts; per-field coverage alone won't tell you that combination was hit.

✗ Common mistake

Only ever testing full-width, aligned INCR bursts.

Why it hurts: real traffic includes narrow, unaligned, FIXED, and WRAP. Byte-lane and strobe-steering logic is exercised only by the cases you skipped.

MODULE 5

IDs, Ordering & Out-of-Order Transactions

Learning objectives

  • Explain what AxID is and how it enables out-of-order completion.
  • State the AXI ordering rules: same-ID vs different-ID.
  • Understand outstanding transactions and transaction interleaving.
  • Design a scoreboard that handles out-of-order, multi-ID traffic.
Analogy — a coffee shop order number. You order, get a number, and step aside. Drinks come out as they're ready — not necessarily in order. A simple latte beats a complicated one ordered earlier. The number (the ID) is how you know which drink is yours. But two orders with the same number must come out in order, or you couldn't tell them apart.

What AxID does

Every transaction carries an ID (AWID/ARID). The response carries the matching ID (BID/RID). The ID is a tag that lets the manager match responses to requests even when they come back out of order — and it's the basis of AXI's ordering model.

The ordering rules

Same ID → ordered. Transactions with the same AxID to the same direction must complete in the order they were issued. The manager relies on this.

Different ID → no ordering guarantee. Transactions with different IDs may complete in any order relative to each other. This is what lets a fast subordinate response overtake a slow one.

Concretely: if a manager issues read A (ID=5), read B (ID=5), read C (ID=9), then:

  • A's data must arrive before B's data (same ID 5 → ordered).
  • C (ID 9) may arrive before, between, or after A and B — no constraint.

Outstanding transactions

A manager may issue many transactions before earlier ones complete — these are outstanding. The number it can have in flight is its outstanding capability (often per-ID and total limits). More outstanding transactions hide latency better but need deeper buffers. Verification must push to (and past) the declared limits to find buffer-overflow and ID-tracking bugs.

Interleaving

In AXI3, write data from different IDs could be interleaved on the W channel (controlled by WID). AXI4 removed write data interleaving and the WID signal — write data for a burst must now arrive contiguously. Read data from different IDs may still interleave beat-by-beat on the R channel (the RID on each beat tells you which transaction it belongs to). This is a frequent source of version confusion.

Designing the scoreboard

// Per-ID queues are the key data structure for an OOO scoreboard.
// Each ID has its own expected-order FIFO; across IDs, order is free.
mailbox #(axi_txn) expected_q [int];   // indexed by ID

function void on_request(axi_txn t);
  if (!expected_q.exists(t.id))
    expected_q[t.id] = new();
  expected_q[t.id].put(t);              // enqueue in issue order, per ID
endfunction

function void on_response(axi_txn r);
  axi_txn exp;
  // For this ID, the response MUST match the head of that ID's queue.
  expected_q[r.id].get(exp);            // same-ID ordering enforced here
  if (r.data !== exp.data)
    `uvm_error("SB", $sformatf("ID %0d data mismatch", r.id))
endfunction

The core insight: one queue per ID. Within a queue, order is strict (head must match next response). Across queues, any interleaving of arrivals is legal. A single global FIFO scoreboard is the classic wrong design — it will report false mismatches the moment different-ID responses legally reorder.

Activity — spot the illegal reordering

A manager issues reads in this order: R1(ID=2), R2(ID=2), R3(ID=7), R4(ID=2). Responses arrive in this order: R3, R1, R4, R2. Is any rule violated?

Ignore ID=7 (only one, no ordering constraint with others). Now look only at the ID=2 transactions in issue order vs arrival order: R1, R2, R4 issued; in what order did they arrive?

ID=2 transactions were issued in order R1, R2, R4. They arrived in order R1, R4, R2. That means R4 returned before R2 — but R2 was issued before R4 and they share ID=2. Violation: same-ID transactions must complete in issue order. R3 (ID=7) overtaking is fine. The bug: R4 before R2.

A per-ID-queue scoreboard catches this automatically — when R4 arrives, the head of ID=2's queue is R2, so the data won't match and the check fires at exactly the right moment.

Two AXI read transactions have different ARIDs. What does the protocol guarantee about their completion order?

Different IDs carry no ordering guarantee — that freedom is exactly what enables out-of-order completion and latency hiding. Only same-ID transactions must stay in order.

Good & Bad Practices

✓ Good practice

Use per-ID expected queues in the scoreboard; enforce order only within an ID.

Why: it matches the protocol's actual ordering model. A single global FIFO produces false mismatches on legal reordering.

✗ Common mistake

Assuming responses always come back in request order.

Why it hurts: the testbench breaks the instant the DUT legitimately reorders different-ID traffic — and you'll waste days "debugging" a non-bug.

✓ Good practice

Cover ID reuse, max-outstanding-per-ID, and read interleaving explicitly.

Why: ID-tracking and reorder buffers are where the subtle bugs live; these states won't be hit by accident.

✗ Common mistake

Carrying AXI3 write-interleaving assumptions into an AXI4 environment.

Why it hurts: AXI4 forbids write-data interleaving and dropped WID; an AXI3-era checker either misses real bugs or flags legal AXI4 traffic.

  • Know how errors must be handled — and why a burst still completes.
  • Build error-injection and response checks into verification.
Analogy — delivery outcomes. OKAY is "delivered." EXOKAY is "delivered, and your special reserved-slot request succeeded." SLVERR is "the recipient existed but rejected the package." DECERR is "no such address — undeliverable." In every case you still get a notification — the truck doesn't just vanish.

The four response codes (xRESP)

CodeEncodingMeaning
OKAY0b00Normal successful access.
EXOKAY0b01Exclusive access succeeded (the exclusive read/write pair completed atomically). Only meaningful for exclusive accesses.
SLVERR0b10The subordinate was reached but reported an error (e.g. write to a read-only register, unsupported size).
DECERR0b11Decode error — no subordinate at this address. Generated by the interconnect's decoder.

Where responses appear

  • Writes: one BRESP on the B channel for the whole burst.
  • Reads: RRESP on every R beat. Different beats of the same burst can even carry different responses (e.g. some beats OKAY, a later beat SLVERR).
SLVERR vs DECERR — who generates them? DECERR comes from the interconnect (the address decoded to nothing). SLVERR comes from the subordinate itself (it was reached but couldn't complete the request). Getting this attribution right matters when you debug: a DECERR points at the memory map or routing; a SLVERR points at the target's internal logic.

Errors don't abort the burst

A crucial and often-missed rule: an error response does not cancel the rest of the burst. If beat 2 of a 4-beat read returns SLVERR, the subordinate must still drive beats 3 and 4 (typically also with an error or with junk data) and assert RLAST on beat 4. The transaction completes its full beat count. A subordinate that stops early — dropping RLAST — hangs the manager waiting for beats that never come.

Error injection in verification

// Subordinate VIP: randomly inject error responses to exercise manager recovery
constraint err_dist_c {
  resp dist {
    OKAY   := 90,    // mostly clean
    SLVERR := 7,
    DECERR := 2,
    EXOKAY := 1     // only when exclusive
  };
}
// Checker: every request must get exactly one matching response, ever.
// No response = hang (caught by timeout). Extra response = protocol error.

Why inject errors: most RTL is well-tested on the happy path and buggy on error recovery. Does the manager correctly propagate a SLVERR up to software? Does it free the transaction's buffer slot? Does a DECERR on one ID corrupt tracking of others? Error injection is where these escape-prone paths get exercised.

Timeouts are your friend. The most dangerous error behaviour is no response — a dropped transaction that hangs the manager forever. Always run a per-transaction timeout in the scoreboard and treat expiry as a failure. A silent hang with no timeout just wastes CI hours with no diagnostic.

Activity — classify the responses

For each scenario, name the expected response code: (1) A write to a valid RAM address succeeds. (2) A read targets address 0xDEAD_0000, which is in a memory-map hole. (3) A write targets a valid peripheral, but the register is read-only. (4) An exclusive store completes with its reservation still intact.

Ask two questions per case: was a subordinate even reached (if not → DECERR)? If reached, did it succeed (OKAY/EXOKAY) or reject (SLVERR)? EXOKAY is only for successful exclusive accesses.
  • (1) OKAY — normal success.
  • (2) DECERR — no subordinate at that address; generated by the interconnect decoder.
  • (3) SLVERR — the subordinate was reached but rejected the write (read-only register).
  • (4) EXOKAY — the exclusive access succeeded with the reservation honoured.

Beat 2 of a 4-beat read burst returns DECERR. What must the subordinate do?

An error never aborts a burst. All declared beats must be driven and RLAST asserted only on the true final beat. Dropping beats or asserting RLAST early hangs or confuses the manager — itself a serious protocol bug.

Good & Bad Practices

✓ Good practice

Inject SLVERR/DECERR with a weighted distribution and verify the manager recovers and reports correctly.

Why: error-recovery paths are the least-tested RTL and the most common silicon escapes.

✗ Common mistake

Only testing OKAY responses.

Why it hurts: the entire error-handling datapath ships unverified — and that's exactly where field failures originate.

✓ Good practice

Run a per-transaction timeout and treat a missing response as a failure.

Why: a dropped transaction hangs silently; without a timeout it just burns simulation time with no signal of what broke.

✗ Common mistake

Treating a mid-burst error as a reason to stop checking the rest of the burst.

Why it hurts: the protocol requires the burst to complete; your checker must still verify beat count and RLAST placement even on error.

MODULE 7

AXI5 Features

Learning objectives

  • Understand the AXI5 atomic transactions and how they replace the exclusive-only model.
  • Explain QoS, regions, and user signals and their verification angles.
  • Describe the modern sideband features: cache-stashing, MTE, poison, wake-up, NSAID.
  • Know what each feature means for stimulus, checking, and coverage.
Analogy — upgrading a highway. AXI4 was a great highway. AXI5 adds toll-free express lanes (QoS), pre-stocking shops near where you're headed (cache stashing), tamper-evident seals on cargo (poison & MTE), and a way to wake a closed depot just before you arrive (wake-up signaling). The road is the same; the features make it smarter and safer.

Atomic transactions (AtomicOps)

Earlier AXI offered only exclusive access: a read-then-write pair, where the write succeeds (EXOKAY) only if nothing else touched the location in between. It works but needs a round trip and an exclusive monitor. AXI5 adds true atomic transactions that perform a read-modify-write at the endpoint in one transaction:

Atomic opWhat it does
AtomicStoreApply an operation (add, AND, OR, XOR, max, min…) to the target location with the supplied data. No data returned.
AtomicLoadSame as AtomicStore but returns the original value before the operation.
AtomicSwapUnconditionally swap the target with the supplied value, returning the old value.
AtomicCompareCompare-and-swap: write only if the current value matches an expected value; returns the original.

These map directly onto the atomic instructions CPUs need for locks and lock-free data structures. Signaling uses AWATOP on the write-address channel, with the operation encoded and the result (for the load-style ops) returned on the read data channel.

An atomic looks like a write that also returns data — the endpoint does the read-modify-write in one indivisible step:

Verification angle for atomics: atomicity is the whole point, so your checks must prove the read-modify-write is indivisible — no other transaction may interleave at that location during the op. Build a reference model of each AtomicOp, and stress concurrent access to the same address from multiple managers. Endianness and the byte-lane behaviour of the operation are rich corner cases.

QoS — Quality of Service

AxQOS is a 4-bit priority hint. Higher values request higher priority through the interconnect. It is a hint, not a guarantee — the protocol does not mandate a specific arbitration outcome. For verification this means you can't assert "higher QoS always wins"; instead you cover that the field is transported intact and you measure arbitration behaviour against the interconnect's documented policy.

Regions

AxREGION lets a single subordinate present several logical regions (e.g. control vs data apertures) without re-decoding the address. The interconnect sets it based on the address map. Check that the region value matches what the memory map says for each address.

User signals

AWUSER/WUSER/BUSER/ARUSER/RUSER are user-defined sideband with no protocol-defined meaning. They are commonly used for parity, custom IDs, or routing hints. Because they're project-specific, your VIP must be configured with the local definition; a generic checker can only verify they're transported, not interpreted.

Cache stashing

Cache stashing lets an initiator push data into another agent's cache before that agent needs it — for example, a network controller stashing an incoming packet straight into the CPU's L2 so the first access hits instead of missing. It needs coherency support (ties into ACE/CHI). Verification must confirm the stash lands in the right cache and that coherency state stays correct.

MTE — Memory Tagging Extension

MTE attaches small tags to memory regions and pointers; a mismatch signals a memory-safety violation (use-after-free, buffer overflow). AXI5 carries the tag traffic. For verification, model the tag store and check tag-check transactions return the right match/mismatch outcome.

Poison

A poison bit marks data as known-corrupt (e.g. from an uncorrectable ECC error) without immediately faulting. The poison propagates with the data; consuming poisoned data triggers an error at the point of use. Verify that poison is carried end-to-end and that it neither appears spuriously on clean data nor gets lost on corrupt data.

Wake-up signaling (low power)

AWAKEUP lets an interface signal activity is coming so a powered-down or clock-gated component can wake before transactions arrive — saving power without adding latency on the critical path. Verify wake/sleep handshakes don't drop or delay transactions and don't deadlock at the power-state boundaries.

NSAID / TrustZone

AxPROT[1] already distinguishes secure vs non-secure. AXI5 adds finer-grained NSAID (Non-Secure Access IDentity) for Realm/secure-world partitioning. Verification must prove isolation: a non-secure access must never reach a secure-only region, and the access-identity must be carried faithfully — a security property, so it's checked as an assertion, not just covered.

Activity — choose the mechanism

A CPU needs to atomically increment a shared counter at 0x9000 that several cores hammer concurrently. Should it use AXI exclusive access or an AXI5 AtomicStore(add)? Give one verification scenario that would stress whichever you choose.

Exclusive access needs a read, a local modify, then a conditional write — and it can fail and retry under contention. An AtomicStore performs the add at the endpoint in one transaction. Which scales better under heavy contention, and what concurrency must your test create?

AtomicStore(add) is the better fit: the increment happens atomically at the endpoint in a single transaction, with no read-modify-write round trip and no retry storm under heavy contention.

Stress scenario: have N managers each issue many AtomicStore(add, +1) to 0x9000 concurrently, with randomized back-pressure and interleaving. The reference model predicts the final value = initial + total number of adds. Any lost update (final value too low) proves the atomicity guarantee is broken — the single most important property to verify for atomics.

What is the key advantage of an AXI5 AtomicStore over the older exclusive-access mechanism?

Exclusive access is a read, then a conditional write that can fail and retry under contention. An AtomicStore performs the operation at the target in a single indivisible transaction — simpler and far more scalable when many agents contend for the same location.

Good & Bad Practices

✓ Good practice

For each AXI5 feature the DUT claims to support, build a reference model and a concurrency stress test — especially for atomics and coherent stashing.

Why: these features are about behaviour under contention; a single-threaded directed test proves almost nothing about atomicity or coherency.

✗ Common mistake

Treating QoS as a hard guarantee and asserting "higher QoS always wins."

Why it hurts: QoS is a hint; the protocol mandates no specific outcome. That assertion will fire on perfectly legal arbitration and waste debug time.

✓ Good practice

Verify security properties (NSAID, secure/non-secure) with assertions, not just coverage.

Why: isolation is a must-never-happen property; coverage tells you a case was hit, an assertion proves the illegal case never occurs.

✗ Common mistake

Letting poison or MTE tags be silently dropped by the testbench model.

Why it hurts: if your model discards them, you can't tell whether the DUT propagates them correctly — the safety feature ships unverified.

MODULE 8

ACE & Cache Coherency

Learning objectives

  • Explain why cache coherency is needed and what problem it solves.
  • Describe how ACE extends AXI with snoop channels.
  • Understand cache-line states (MOESI-style) at an introductory level.
  • See how ACE bridges toward CHI (the next course).
Analogy — shared document, local copies. Several people each photocopy a shared document and edit their copy. If person A changes a line, everyone else's copy is now stale. Coherency is the rule-set that keeps all the copies consistent: when A edits, others are told to discard or update their copy. The caches are the photocopies; snoops are the "your copy is stale" messages.

The coherency problem

Each CPU core has its own cache — a fast private copy of recently used memory. When two cores cache the same address and one writes it, the other's cached copy becomes stale. Without coordination, the second core reads an old value and the program breaks. Cache coherency hardware guarantees that all cores see a single, consistent view of memory despite their private caches.

ACE = AXI Coherency Extensions

ACE extends AXI with the signaling needed for coherency. It keeps the five AXI channels and adds extra fields on the address channels (to declare coherent intent) plus three snoop channels that let the interconnect interrogate a cache:

Snoop channelDirectionPurpose
AC (snoop address)Interconnect → cached manager"Do you have address X? Here's what I need you to do with it."
CR (snoop response)Cached manager → interconnect"Here's my cache's state for X" (do I have it, is it dirty…).
CD (snoop data)Cached manager → interconnectIf I have dirty data, here it is — to supply to the requester or memory.

Cache-line states (MOESI)

Coherency protocols track the state of each cache line. The common model is MOESI:

StateMeaning
ModifiedThis cache has the only copy and it's dirty (differs from memory). Must write back.
OwnedDirty and shared — this cache is responsible for it, but others may hold read copies.
ExclusiveOnly copy, clean (matches memory). Can be written without telling anyone (then becomes M).
SharedPossibly cached elsewhere too; clean read-only copy.
InvalidNot present / stale. A read must fetch it.

Snoops cause state transitions: a snoop for a write may force another cache from Shared to Invalid; a snoop for a read may move Modified to Owned or Shared while supplying the dirty data. Verifying these transitions — for every state, every snoop type, every race — is the heart of coherency verification.

Bridge to CHI: ACE bolts coherency onto AXI's signal-based, channel-per-wire structure. That works for a handful of coherent managers, but as core counts grow, the wiring and snoop broadcast cost explode. CHI (Course 3) re-imagines the whole thing as a packet/flit-based protocol with a home node that tracks ownership — far more scalable. ACE is the conceptual stepping-stone: same coherency ideas, different (more scalable) delivery.

Activity — predict the snoop

Core A holds line X in Modified (dirty). Core B issues a read of X that requires a coherent, up-to-date copy. Walk through what must happen so B gets correct data, and name the likely final states of X in A and B.

Memory is stale (A's copy is dirty), so B must not read memory directly. The interconnect has to involve A. After A supplies the data, can both A and B legally hold a clean shared copy? What happens to "who owns the dirty data"?
  1. B's coherent read reaches the interconnect.
  2. The interconnect sends an AC snoop to A for X.
  3. A responds on CR (I have it, it's dirty) and supplies the data on CD.
  4. The interconnect forwards that current data to B (and may update memory).

Final states (one legal outcome): if the dirty data is written back to memory, both end in Shared (clean). If not written back, A moves to Owned (still responsible for the dirty data) and B becomes Shared. The exact outcome depends on the snoop type the interconnect issued — which is precisely the kind of detail a coherency scoreboard must model.

What do ACE's snoop channels (AC/CR/CD) let the interconnect do?

Snoop channels let the interconnect ask a cache about a line (AC), hear its state (CR), and collect dirty data (CD) — the machinery that keeps every core's view of memory coherent. It's about consistency, not speed or encryption.

Good & Bad Practices

✓ Good practice

Model cache-line state in the scoreboard and check the state after every snoop, not just the data returned.

Why: a read can return correct data while leaving the line in the wrong state — a latent bug that breaks the next access. Data-only checks miss it.

✗ Common mistake

Reading memory directly in the scoreboard to predict expected data in a coherent system.

Why it hurts: memory may be stale when another cache holds the dirty copy; the scoreboard must model cache ownership, not raw memory.

✓ Good practice

Stress concurrent access to the same line from multiple coherent managers with randomized snoop timing.

Why: coherency bugs are races; they only appear when snoops, reads, and writes to one line overlap in time.

✗ Common mistake

Verifying coherency only with one manager active at a time.

Why it hurts: with no contention there's nothing to be coherent about — the entire snoop/ownership mechanism goes untested.

MODULE 9

Verifying AXI — Putting It All Together

Learning objectives

  • Assemble a complete AXI verification environment: stimulus, checkers, coverage.
  • Architect an out-of-order scoreboard and a protocol-assertion layer.
  • Build a functional coverage model that reflects a real test plan.
  • Apply the "try to break it" mindset to AXI-specific corners and debug.
Analogy — a customs checkpoint. Your verification environment is a customs operation. The driver sends traffic (stimulus), monitors inspect every vehicle without interfering (passive checking), assertions are the rules printed on the wall that instantly flag a violation, the scoreboard is the manifest that proves what went in came out, and coverage is the logbook proving you actually inspected every category of cargo — not just waved trucks through.

The complete environment

The three pillars

1. Stimulus. Constrained-random sequences generate protocol-legal traffic: mixed read/write, all burst types, narrow and unaligned transfers, many IDs, deep outstanding, random back-pressure on every channel. Directed tests pin down specific corners (4KB-boundary-adjacent bursts, max-length bursts, atomic contention). The constraints encode the legal space (Module 4's rules); the randomness explores it.

2. Checking. Two complementary layers:

  • Protocol assertions (SVA) bound to the interface — handshake stability, payload stability, no 4KB crossing, WRAP alignment, RLAST placement, exactly-one-B-per-write, response legality. These fire at the exact failing cycle.
  • Scoreboard — end-to-end data integrity with per-ID queues for out-of-order, a reference memory model honouring WSTRB, and per-transaction timeouts.

3. Coverage. Functional coverage tied to the test plan proves you actually exercised the space — not just that nothing failed.

// A slice of an AXI functional coverage model
covergroup axi_cg @(posedge clk);
  burst_type : coverpoint tr.burst { bins fixed={FIXED}; bins incr={INCR}; bins wrap={WRAP}; }
  len_cp     : coverpoint tr.len   { bins one={0}; bins small={[1:15]}; bins large={[16:255]}; }
  size_cp    : coverpoint tr.size  { bins all[] = {[0:7]}; }
  resp_cp    : coverpoint tr.resp  { bins ok={OKAY}; bins exok={EXOKAY}; bins slv={SLVERR}; bins dec={DECERR}; }
  // crosses: bugs live at the intersections
  size_x_burst : cross size_cp, burst_type;       // narrow WRAP? narrow FIXED?
  len_x_resp   : cross len_cp, resp_cp;            // error on a long burst?
endgroup

Why the crosses matter: covering each field alone tells you that FIXED happened and that SLVERR happened — but not that a SLVERR ever occurred on a FIXED burst. Bugs cluster at exactly those intersections, which is why a real coverage model is mostly crosses.

Commercial VIP

In practice you rarely hand-write all of this. Commercial AXI VIP (Synopsys VC VIP, Cadence UVM VIP, Siemens questa VIP) ships a configurable manager/subordinate, hundreds of bundled protocol assertions, and a coverage model. Your protocol knowledge — everything in Modules 1–8 — is what lets you configure it correctly (right AXI version, widths, ID space, outstanding limits), interpret its failures, and know what its coverage numbers actually mean. The VIP is a power tool; understanding the protocol is knowing how to hold it.

The "try to break it" corners for AXI

  • Maximum outstanding transactions, then one more — does ID tracking overflow?
  • Back-pressure every channel simultaneously, mid-burst — does anything deadlock?
  • Different-ID responses returning fully reversed — does the scoreboard stay correct?
  • Reset asserted in the middle of an active burst — do in-flight transactions drain or get cleanly dropped?
  • Bursts ending exactly one byte before a 4KB boundary; WRAP at every legal length.
  • Concurrent atomics to the same address from many managers — any lost updates?

A debug walkthrough

Scenario: a regression fails with a scoreboard data mismatch on ID=3, but only when the test seed produces heavy different-ID traffic. The handshake assertions are all silent.

Diagnosis path: silent protocol assertions mean the bus behaviour is legal — so suspect the testbench or an ordering assumption first. Heavy different-ID traffic + mismatch on one ID points at out-of-order handling. Top hypotheses: (1) the scoreboard is using a single global FIFO instead of per-ID queues and mis-pairing a legally-reordered response; (2) an off-by-one in per-beat address reconstruction for a WRAP burst on that ID; (3) WSTRB not modelled, so a sub-word write looks like a mismatch. Reproduce with the logged seed, dump the per-ID queue state at the mismatch cycle, and check whether the "mismatch" is actually a legal reordering the scoreboard mishandled.

Activity — design a coverage cross

You're verifying an AXI interconnect and worry about error handling on unusual bursts. Propose one functional coverage cross (two or three coverpoints) that would prove you've exercised the riskiest error-on-burst combinations, and justify it.

Errors are reported differently for reads (per beat) vs writes (one B). The risky combos involve which beat of a multi-beat burst carries the error, and which burst type. Think about crossing burst type × response code × maybe beat position.

A strong cross: burst_type × resp_code × error_beat_position, where error_beat_position bins the location of the first error beat (first / middle / last / none).

Justification: the dangerous corners are an error on the last beat (does RLAST still assert correctly?), an error in the middle of a WRAP burst (does the burst still complete all beats?), and a DECERR vs SLVERR on different burst types. Crossing these three coverpoints proves you didn't just see "a SLVERR somewhere" but actually hit, say, "SLVERR on the middle beat of a WRAP read" — exactly the combination where beat-count and RLAST bugs hide. Covering the fields independently would report 100% while never having tested that specific, bug-prone intersection.

Your protocol (SVA) assertions are all silent, but the scoreboard reports a data mismatch. What's the most reasonable first hypothesis?

Silent protocol assertions mean the observed bus traffic obeys the protocol — so a data mismatch most likely comes from the checking side: a scoreboard that assumes in-order completion, mismodels WSTRB, or miscomputes WRAP beat addresses. Always suspect legal-but-unhandled behaviour before assuming a deep DUT bug.

Good & Bad Practices

✓ Good practice

Layer checking: bound SVA for protocol legality and a scoreboard for data integrity.

Why: assertions catch protocol bugs cycle-accurately; the scoreboard catches functional/data bugs. Neither alone is sufficient.

✗ Common mistake

Declaring "done" on code coverage alone.

Why it hurts: code coverage shows what executed, not what was verified. Functional coverage tied to the test plan is what tells you the intended scenarios were actually hit.

✓ Good practice

Log the random seed on every run and treat any timeout as a failure.

Why: an unreproducible failing seed is a verification escape; a silent hang with no timeout burns CI with no diagnostic.

✗ Common mistake

Configuring commercial VIP for the wrong AXI version or ID width and trusting its green coverage.

Why it hurts: a misconfigured VIP cheerfully reports passing while either generating illegal traffic or never exercising the features your DUT actually implements.
