Project Explanation Questions
Asked in 100% of interviews. Your single biggest lever. Prepare a 3-minute and a 7-minute version of every project on your resume.
⌕
Core Questions — Every Interview
Q1.1Introduce yourself and walk me through your projects.HIGH▾
Answer
Lead with: name, total years, domain, projects in reverse chronological order. Keep under 2 minutes. Structure: 'I have X years in ASIC DV. My most recent project was [most impressive — e.g. RTD-DMA AGU verification] where I was responsible for [block]. Before that, [project 2 — NoC, AES]. My strongest area is [UVM, AXI protocol, DMA microarchitecture verification].'
💡 Insight
Interviewers decide in the first 90 seconds whether to invest the interview. A crisp introduction that names real IPs (RTD-DMA, NoC fabric, AES crypto engine, NoC arbiter) and real companies immediately establishes credibility. Generic introductions ('I have worked on various IPs') are forgettable. Name the technology. Name the architecture. Name the block. Be confident.
Q1.2Explain your latest / most complex project in complete detail.HIGH▾
Answer
Cover these 6 points in order:

1. What is the block — function, inputs, outputs, where it sits in the SoC, why it matters.
2. TB architecture — UVM components, how they connect, VIPs used, virtual interface structure, config_db setup.
3. Key test cases — 3 to 5 specific scenarios with rationale. Not 'read and write' — meaningful scenarios like 'stall injection mid-2D traversal' or 'simultaneous 3-master arbitration collision'.
4. Corner cases — boundary conditions, simultaneous event scenarios, error injection, wrap-around, race conditions.
5. Bugs found — symptom, debug process, root cause (RTL signal level), resolution, confirmation.
6. Your personal contribution — what YOU built vs what the team built.
💡 Insight
Interviewers probe until you run dry. Prepare signal-level detail for your most complex project. If you can explain your DMA descriptor pipeline at signal level — citing desc_valid handshake, Shadow Register latching, err_unaligned ASIL-D flag — that tells the interviewer more than 20 UVM phase questions. Average candidates run out at 'I verified AXI'. Strong candidates go to pin-level timing.
⚠ Watch Out
Every claim on your resume is a commitment. If it says NoC — prepare to explain round-robin arbitration logic at signal level. If it says DMA — prepare to explain the descriptor execution pipeline. Interviewers read resumes and target exactly what's written.
Q1.3What test cases did you write? Give 3–5 specific examples with rationale.HIGH▾
Answer
Always answer with: TC name → what stimulus was applied → what was expected → why this scenario matters.

DMA example: TC1 — Stall injection: assert stall_in mid-2D traversal. Expected: pipe_en goes low, rem_inner_cnt freezes, no address slip. Catches deterministic DMA corruption bugs.
TC2 — PONGSW boundary: stall asserted exactly at context swap cycle. Expected: Shadow Register loaded cleanly, no partial descriptor.
TC3 — Misaligned address: force raw_addr_int % desc_width != 0. Expected: err_unaligned fires, slice halts, no AXI transaction issued.

NoC example: TC1 — All 3 masters simultaneous to same slave: verify round-robin grant order and no data corruption.
TC2 — High-priority master arrives mid-grant of low-priority master: verify arbitration switches within 1 cycle.
💡 Insight
'I wrote read, write, and reset test cases' scores 2/10. 'TC1: Back-to-back AXI write bursts from 3 masters to same slave — verified round-robin grant and data integrity under contention' scores 9/10. Specificity = credibility. Interviewers know immediately when you actually wrote the test cases vs inherited them.
Q1.4What bugs did you find? How did you identify them and resolve them?HIGH▾
Answer
Use the 4-part bug story structure for every bug:

Symptom: What failed — assertion fire, scoreboard mismatch, coverage plateau, timeout, wrong output.
Debug process: What you looked at — waveform at timestamp, UVM verbosity increased, specific signal traced, added $display.
Root cause: The actual RTL issue at signal level — off-by-one, wrong priority encoding, uninitialized reset, combinatorial vs registered gating.
Resolution: RTL fix, confirmation by re-running regression, coverage re-checked.

Example: 'During stall_in assertion, rem_inner_cnt decremented by 1 before freezing — off-by-one. Found via $display on counter vs pipe_en edge at stall boundary. Root cause: pipe_en gating was registered (1-cycle delay). RTL fix: changed to combinatorial wire assignment. Confirmed: 500+ random stall scenarios pass with no counter slip.'
💡 Insight
If you haven't found real RTL bugs, be honest but strategic: 'The most significant finding was during coverage analysis — I discovered a missing scenario for write-after-write to same register in one clock cycle. Adding a directed test exposed a read-modify-write race that wasn't in the original test plan.' That's a real contribution even without a traditional RTL bug.
Q1.5What corner cases did you cover? Give specific examples from your project.HIGH▾
Answer
Prepare minimum 3 corner cases per project. A corner case is a boundary condition, simultaneous event, or error condition — not basic read/write.

DMA/AGU: Stall asserted at exact PONGSW boundary (context swap cycle). Matrix of 1×1 (single beat traversal). Descriptor with maximum inner_cnt and zero outer_cnt. PING and PONG base addresses identical (error injection). err_unaligned on the very last beat of a burst.

NoC/Interconnect: All masters simultaneously at same clock requesting same slave. Priority inversion mid-grant. Address exactly at decode boundary between two slaves. Reset assertion during active burst transfer.

AES: All-zero 128-bit plaintext. All-zero key. Known NIST CAVS test vectors (deterministic gold reference). Key expansion with all-same bytes.

FIFO/Buffer: Write to full and read simultaneously same clock edge. Wrap-around at exactly last address. Reset when FIFO is half full.
💡 Insight
Corner cases separate 3-year from 5-year engineers consistently. A 5-year engineer's corner case thinking: 'What happens if two events coincide on the same clock edge?' and 'What happens at exact boundaries?' and 'What happens if reset comes during an active transaction?' These are the scenarios that contain real silicon bugs. Prepare 5+ per project.
Q1.6What is sign-off criteria for IP verification?HIGH▾
Answer
Professional sign-off checklist:

1. Functional coverage closure: All coverpoints at 100% target, all waivers documented with justification in the verification plan.
2. Code coverage thresholds: Statement, branch, toggle, FSM — typically 90%+ with dead-code waivers confirmed by RTL designer.
3. Regression stability: Zero failing tests (or all failures root-caused and waived). Minimum 3 consecutive clean regressions before sign-off.
4. Verification plan checklist: Every item checked off — verified, not-applicable, or waived with documented rationale.
5. Peer review sign-off: DV lead + client/customer review and approval.
6. GLS pass (if applicable): Post-synthesis netlist simulation clean at RTL-equivalent functional coverage.
💡 Insight
This question identifies engineers who've been through a real sign-off vs those who just ran tests. Key thing to say: 'Functional coverage is the primary metric — 100% code coverage alone is not sufficient. The test plan is the contract between DV and design. Every waiver must be justified and visible to the client.' This shows professional, process-oriented thinking that senior roles require.
Q1.7Code coverage 70%, functional coverage 100% — what do you do?HIGH▾
Answer
Systematic analysis approach:

Step 1: Run detailed coverage report — identify exactly which lines/branches are uncovered with path information.
Step 2: Categorise each gap: dead code (RTL path can never be exercised by design intent) vs reachable but untested code.
Step 3: For reachable gaps — write directed tests targeting those specific conditions (error paths, fault handlers, boundary conditions).
Step 4: For dead code — confirm with RTL designer that path is intentionally unreachable. Document waiver: what, why, who confirmed, when.
Step 5: Never waive without confirmation — synthesis tools can optimise away incorrectly-waived paths and hide real silicon bugs.
💡 Insight
This is a trap for candidates who think 100% functional = done. Code coverage gaps often reveal: dead code (legitimate) OR functional coverage model gaps you didn't realise. Always check both before waiving. Key follow-up interviewers ask: 'Would you sign off with 70% code coverage?' — be prepared to justify your decision and know that the answer depends heavily on WHY those lines are uncovered.
Q1.8Functional coverage 70%, code coverage 100% — what do you do?HIGH▾
Answer
This is more serious than the reverse — specification gaps remain unclosed.

Step 1: Get per-bin coverage report — identify exactly which coverpoints and bins have zero hits.
Step 2: For each uncovered bin: is the scenario physically possible in this design? If yes — write constrained or directed tests.
Step 3: Adjust constraints to steer randomisation toward uncovered bins. Tune weights or use coverage-driven generation.
Step 4: If bin is logically unreachable (illegal combination) — create illegal_bin to exclude from goal with justification.
Step 5: Review covergroup design itself — are there scenarios in the spec that your coverage model doesn't yet capture?
💡 Insight
Coverage closure is an iterative engineering process. Build a daily coverage dashboard and track the trend. If coverage progresses 2–3% per day with new tests — you will close. If it's stuck for 3+ days despite many new tests — those remaining bins need manual analysis. Most common stuck-coverage cause: bins requiring very specific simultaneous signal conditions (interrupt arriving at exact pipeline stage boundary) — need extremely targeted directed tests, not more random tests.
Q1.9How do you debug a data mismatch in the scoreboard?HIGH▾
Answer
Step-by-step systematic process:

1. Get timestamp from UVM_ERROR — note exact simulation time.
2. Enable verbosity: +UVM_VERBOSITY=UVM_DEBUG — see all transactions and TB activity.
3. Check monitor first — is it sampling at the correct clock edge with correct protocol? Not all mismatches are DUT bugs — monitor may have a timing error.
4. Check reference model independently — run the golden model with the same inputs outside of the scoreboard. Does it produce the expected output?
5. Check scoreboard comparison logic — is comparison correct? Handling out-of-order (ID-based matching) correctly?
6. Open waveform at timestamp — compare actual DUT output, what monitor captured, and what scoreboard expected.
7. Isolate with directed test — create a minimal deterministic test that reproduces the exact mismatch without randomness.
💡 Insight
The #1 mistake: immediately escalating to RTL team assuming DUT bug. In practice, 40–60% of scoreboard mismatches are TB bugs — wrong reference model, incorrect comparison logic, out-of-order handling issues, monitor timing errors. Always verify the testbench before escalating. Wasting an RTL designer's time on a TB bug destroys credibility and delays real bug investigation.
⚠ Watch Out
Out-of-order mismatches: if you use a queue (FIFO) for scoreboard but the DUT returns out-of-order, you'll get spurious mismatches. Use an associative array keyed by transaction ID for out-of-order comparison.
