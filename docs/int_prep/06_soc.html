SoC Verification Questions
Differentiates IP-level from SoC-level engineers. Key at WD, Qualcomm, Tenstorrent, and ARM.

SoC Architecture and Flow
Q6.1Difference between IP verification and SoC verification.HIGH▾
Answer
IP verification: single block in isolation. UVM constrained-random. Full TB control of all inputs. Goal: prove IP meets its specification. Dedicated VIPs for each interface. Simulation times: minutes to hours per test.

SoC verification: multiple IPs integrated together. Stimulus primarily via C programs executed by embedded processor. Focus on emergent behaviour — bugs from IP interactions, incorrect integration. Connectivity checks (is IRQ pin connected to correct controller input?). Boot sequence, real-world scenarios. Simulation times: hours to days per test. SoC-level bugs: wrong address mapping, wrong interrupt routing, wrong reset sequencing, incorrect clock domain connection — not IP function bugs.
💡 Insight
The mental model shift: IP verification asks 'does this block work correctly?' SoC verification asks 'do all these blocks work correctly together in a system?' The bugs are fundamentally different. SoC integration bugs include: AXI master connected to wrong slave port (wrong address decode), interrupt line from IP connected to wrong PLIC input, reset signal polarity inverted, clock divider misconfigured. These bugs ONLY appear at SoC level — IP testbench can't catch them.
Q6.2How does C code execute in SoC verification? Full flow.HIGH▾
Answer
Full flow:
1. Write C test: access memory-mapped registers (volatile pointers), trigger operations, check results via status registers.
2. Compile: riscv64-unknown-elf-gcc generates ELF binary.
3. Convert: riscv64-unknown-elf-objcopy produces inst.hex (instructions) and data.hex (constants/data).
4. Back-load: $readmemh() or UVM backdoor loads hex files into IRAM and DRAM at simulation start.
5. Deassert reset: processor starts at reset vector, fetches first instruction from IRAM, executes C code.
6. Monitor: UVM monitors passively observe DUT outputs (AXI transactions, interrupt signals, register writes).
7. Check: C test writes pass/fail code to a scratch register → UVM scoreboard reads register value at test end.
💡 Insight
The C-to-SV communication is the most asked follow-up. Most common pattern: C test writes result (PASS=1, FAIL=0) to a known scratch register address at test end. UVM monitors the bus — when it sees a write to that address, it reads the value and declares pass/fail. This cleanly decouples C test timing from SV TB timing. DPI (Direct Programming Interface) is the more sophisticated approach — allows C functions to call SV functions and vice versa for tighter integration.
Q6.3What happens after SoC reset deassertion? Boot sequence.HIGH▾
Answer
Detailed boot sequence:
1. Reset deassertion → all flip-flops reset to known state.
2. CPU PC jumps to reset vector (hardwired, typically 0x00000000 or 0x80000000 for RISC-V).
3. Reset vector contains jump to Boot ROM.
4. Boot ROM executes: initialises stack pointer, configures clocks/PLLs, waits for PLL lock, initialises memory controller (DDR), enables caches.
5. Boot ROM copies bootloader from flash (slow) to SRAM (fast execution).
6. Bootloader executes: loads OS kernel or bare-metal application from storage.
7. Application main() runs: initialises peripherals, starts tasks.

Verification focus: Reset vector address correct (connectivity check). First instruction fetched correctly. PLL lock within N cycles before peripheral access. No register access before clock stable.
💡 Insight
Boot sequence verification is important at WD and Qualcomm. Common integration bugs: (1) Reset vector address mismatch — processor jumps to unmapped address at boot. (2) PLL not locked before peripheral clock used — first few register writes go to wrong value. (3) Memory controller not initialised before DDR access — bus hangs. Write directed tests specifically for boot sequence timing.
Q6.4Interrupt vs exception. How does core handle multiple simultaneous?MED▾
Answer
Interrupt: asynchronous, from external event — timer overflow, GPIO edge, UART RX data, DMA completion. Independent of current instruction — arrives at instruction boundaries. Can be enabled/disabled via interrupt enable bits (MIE in RISC-V).

Exception: synchronous, caused by instruction execution — illegal instruction, instruction fetch fault, load/store misaligned, ECALL (system call), division by zero. Must be handled immediately — cannot be deferred.

Multiple interrupts: PLIC (Platform-Level Interrupt Controller) in RISC-V assigns configurable priorities (typically 1–7). When multiple pending: highest priority served first. Same priority: lowest ID wins (implementation-defined). Nesting: higher-priority interrupt can preempt lower-priority ISR if software re-enables interrupts in the ISR handler.
💡 Insight
Interrupt vs exception distinction is fundamental for processor verification. The verification angle: write a test that triggers both an interrupt and an exception simultaneously (e.g., write to an unmapped address while a timer interrupt is pending). Verify: correct cause register (mcause), correct PC save (mepc), correct handler selected, correct priority resolution. This is an integration test that catches ISR routing bugs.
Q6.5What is cache coherency? How is it handled in multi-core SoC?MED▾
Answer
Problem: when multiple cores each have their own private L1 cache and share main memory, coherency ensures all cores see the same value for the same memory address. Core A reads address 0x100 (cached). Core B writes to 0x100. Core A's cache has stale value.

MESI protocol: each cache line has a state — Modified (M: only this cache has it, dirty), Exclusive (E: only this cache, clean), Shared (S: multiple caches have clean copy), Invalid (I: not valid).
On write: core broadcasts invalidate (or update) to all other caches. Others move to Invalid. Next read from another core fetches fresh value from memory or snoops it.

AXI ACE (Coherency Extension): adds snoop channels (AC, CD, CR) to AXI. Hardware manages coherency automatically.
💡 Insight
Cache coherency is asked at WD, AMD, and Tenstorrent. The verification angle: create a multi-core coherency test — Core A writes to shared variable, Core B reads it. Verify Core B sees Core A's value (not stale cache). Time the write-to-read interval. Test invalidation under contention. This is a critical SoC-level test — if coherency is broken, multi-threaded software will produce wrong results in silicon.
