UVM Questions
Asked in 95% of interviews. You must write driver, monitor, sequence, and scoreboard from memory on paper.

Architecture and Phases — HIGH frequency
Q2.1Explain UVM TB architecture end-to-end.HIGH▾
Answer
Hierarchy: uvm_test → uvm_env → uvm_agent(s) → scoreboard + coverage collector.

Active agent: driver + sequencer + monitor. Passive agent: monitor only.

Data flow: Test starts sequence on sequencer → Sequencer passes seq_item to driver → Driver drives DUT via virtual interface → DUT responds → Monitor samples DUT output → ap.write(txn) broadcasts to scoreboard and coverage → Scoreboard compare_phase checks result.
💡 Insight
Best answers explain WHY each component exists. Driver: translates abstract transaction to pin-level signals. Monitor: passive sensor — never drives. Scoreboard: automated checker — comparator. Analysis port over TLM because it's one-to-many and non-blocking. The monitor never waits for a slow scoreboard.
Q2.2What are all UVM phases? What is top-down vs bottom-up?HIGH▾
Answer
Build phases (function calls):
build_phase — create child components (TOP-DOWN: parent creates children).
connect_phase — connect TLM ports (BOTTOM-UP: children connect first, then parents).
end_of_elaboration_phase — final pre-simulation checks.
start_of_simulation_phase — print configuration, display hierarchy.

Run phase (task — parallel across components):
run_phase with 12 sub-phases: pre_reset → reset → post_reset → pre_configure → configure → post_configure → pre_main → main → post_main → pre_shutdown → shutdown → post_shutdown.

Cleanup phases (function — bottom-up):
extract_phase → check_phase → report_phase → final_phase.
💡 Insight
Sub-phases of run_phase are asked at Qualcomm and AMD. Key design principle: sub-phases enforce temporal separation without explicit handshaking. Reset logic runs in reset sub-phase. Configuration in configure. Main stimulus in main. Prevents 'configure before reset complete' race conditions — common in ad-hoc testbenches.
Q2.3Write driver skeleton with complete sequencer handshake.HIGH▾
class my_driver extends uvm_driver #(my_txn);
  `uvm_component_utils(my_driver)
  virtual my_if vif;

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db #(virtual my_if)::get(
          this, "", "vif", vif))
      `uvm_fatal("DRV","vif not set in config_db")
  endfunction

  task run_phase(uvm_phase phase);
    my_txn req;
    vif.valid <= 1'b0;         // Idle state
    @(posedge vif.clk);

    forever begin
      seq_item_port.get_next_item(req);  // Block until item ready

      @(posedge vif.clk);
      vif.addr  <= req.addr;             // Non-blocking assignments
      vif.data  <= req.data;
      vif.valid <= 1'b1;

      @(posedge vif.clk iff vif.ready); // Wait for DUT ack
      vif.valid <= 1'b0;

      seq_item_port.item_done();         // Unblock sequencer
    end
  endtask
endclass
⚠ Watch Out
Three common mistakes: (1) Calling item_done() before DUT acknowledges — floods driver with items. (2) Using = (blocking) to drive signals — causes race conditions with monitor. Always use <=. (3) Using #delays instead of @(posedge clk) — makes TB timing fragile.
Q2.4Write monitor skeleton with analysis port.HIGH▾
class my_monitor extends uvm_monitor;
  `uvm_component_utils(my_monitor)
  virtual my_if vif;
  uvm_analysis_port #(my_txn) ap;  // Broadcast port

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    ap = new("ap", this);
    if (!uvm_config_db #(virtual my_if)::get(
          this, "", "vif", vif))
      `uvm_fatal("MON","vif not set")
  endfunction

  task run_phase(uvm_phase phase);
    my_txn txn;
    forever begin
      @(posedge vif.clk);
      if (vif.valid && vif.ready) begin
        txn = my_txn::type_id::create("txn");
        txn.addr  = vif.addr;
        txn.rdata = vif.rdata;
        ap.write(txn);  // Non-blocking broadcast
      end
    end
  endtask
endclass
💡 Insight
Monitor is STRICTLY passive — never drives signals. ap.write() is non-blocking regardless of how many scoreboards/coverage collectors are connected. This is why monitors use analysis ports over TLM ports — monitors should never stall waiting for downstream consumers.
Q2.5Write a UVM sequence skeleton.HIGH▾
class my_sequence extends uvm_sequence #(my_txn);
  `uvm_object_utils(my_sequence)

  function new(string name="my_sequence");
    super.new(name);
  endfunction

  task body();
    my_txn req;

    // Method 1: Explicit (more control)
    req = my_txn::type_id::create("req");
    start_item(req);
    assert(req.randomize() with {
      req.addr inside {[0:255]};
    });
    finish_item(req);  // Blocks until driver calls item_done()

    // Method 2: Macro shortcut
    `uvm_do_with(req, { req.addr == 8'hFF; })
  endtask
endclass

// Start in test:
// my_seq seq = my_seq::type_id::create("seq");
// seq.start(env.agent.sequencer);
💡 Insight
start_item() / finish_item() gives full control — you can add delays, print info, or perform checks between them. `uvm_do is convenient but hides details. In interviews, explaining start_item/finish_item shows deeper knowledge of the sequence-driver communication protocol.
Factory, config_db, TLM — HIGH frequency
Q2.6What is UVM factory? Why use create() instead of new()?HIGH▾
Answer
Factory is a global registry of all UVM classes enabling runtime type substitution. When you call create(), UVM checks the factory for any override — if found, creates the overriding type. new() bypasses the factory entirely — override has zero effect.

Registration: `uvm_component_utils(my_comp), `uvm_object_utils(my_obj). Override: factory.set_type_override_by_type(base::get_type(), derived::get_type()). Instance override: factory.set_inst_override_by_type(..., "env.agent.driver").
💡 Insight
Factory is why UVM scales to large teams. Team A builds the base testbench. Team B creates specialised error injection variants by extending Team A's components. Team B registers override in their test — zero changes to Team A's env or agent. Real use case: create error_driver extending base_driver that randomly corrupts data. Override in error test only. Normal tests use base driver automatically.
Q2.7Write config_db set and get syntax.HIGH▾
// SET — in test build_phase or top-level TB module
uvm_config_db #(virtual my_if)::set(
  this,           // Context (who is setting)
  "env.agent*",   // Hierarchical path (wildcards OK)
  "vif",          // Key name
  vif             // Value to store
);

// Set integer configuration
uvm_config_db #(int)::set(this, "env.agent",
  "num_txns", 100);

// GET — in driver/monitor build_phase
virtual my_if vif;
if (!uvm_config_db #(virtual my_if)::get(
  this,   // Context
  "",     // Relative path (empty = this component)
  "vif",  // Key
  vif     // Output variable
))
  `uvm_fatal("CFG", "vif not found — check set() path")
💡 Insight
Always check get() return value with `uvm_fatal. The most common bug: wrong hierarchical path in set() causes get() to return 0 silently — then vif is null and run_phase crashes. Debug: +UVM_CONFIG_DB_TRACE on command line prints all set/get operations with full paths. Immediate visibility of mismatches.
Q2.8What is analysis port vs TLM port? When does monitor use each?HIGH▾
Answer
Analysis port (uvm_analysis_port): broadcast, one-to-many, non-blocking. write() call completes immediately regardless of how many subscribers are connected. Used for monitor → scoreboard and coverage. Monitor never stalls.

TLM port (uvm_blocking_put_port etc.): point-to-point, potentially blocking. put() can block if consumer is not ready. Used for sequencer → driver communication (seq_item_port is a TLM port).

Monitor always uses analysis port — it should never be blocked by a slow scoreboard. Scoreboard implements analysis_imp with a write() function that is called automatically for each monitor transaction.
💡 Insight
If you use a TLM port from monitor to scoreboard, you create a dependency — a slow scoreboard stalls the monitor which stalls the driver which stalls the DUT. With analysis port: monitor is completely decoupled from downstream components. This architectural choice prevents a class of timing bugs that can occur in TB design.
Q2.9What are multiple analysis imps? How do you handle 4 monitors to one scoreboard?MED▾
Answer
Each uvm_analysis_imp in a class creates a write() function. For multiple connections, use `uvm_analysis_imp_decl macro to create distinctly-named write functions:

// In scoreboard:
`uvm_analysis_imp_decl(_axi) // Creates write_axi()
`uvm_analysis_imp_decl(_apb) // Creates write_apb()

class my_sb extends uvm_scoreboard;
uvm_analysis_imp_axi #(axi_txn, my_sb) axi_imp;
uvm_analysis_imp_apb #(apb_txn, my_sb) apb_imp;
function void write_axi(axi_txn t); ... endfunction
function void write_apb(apb_txn t); ... endfunction
endclass
💡 Insight
This is asked at AMD and Qualcomm when multiple protocol agents feed one scoreboard (common in SoC-level TBs). The macro generates a uniquely-named imp class — each monitor connects to its own named imp. Without this, you'd need multiple scoreboard classes or manual demultiplexing.
Q2.10What is virtual sequencer and virtual sequence? Real example.MED▾
Answer
Virtual sequencer: uvm_sequencer_base component holding handles to multiple real sub-sequencers. Has no driver — it's a coordinator only. Declared with `uvm_declare_p_sequencer(my_vseqr).

Virtual sequence: runs on virtual sequencer, coordinates multiple sub-sequences via p_sequencer handles.

SoC example — verifying CSR then triggering interrupt:
// Virtual sequence body:
axi_write_seq wr_seq;
irq_monitor_seq irq_seq;
fork
wr_seq.start(p_sequencer.axi_seqr);
irq_seq.start(p_sequencer.irq_seqr);
join
// Write via AXI and monitor IRQ simultaneously
💡 Insight
Virtual sequences are what make SoC-level test writing manageable. Without them: 5 separate sequences, complex event-based synchronisation between them. With virtual sequence: one body() method orchestrates all agents with natural fork-join coordination. If you've done SoC verification, this should be a detailed answer with a real example from your project.
Advanced UVM — MED frequency
Q2.11What are UVM callbacks? Give a practical example.MED▾
Answer
Callbacks inject additional behaviour at hook points without modifying the base component source. Define callback class (extends uvm_callback). Component calls callback functions at hooks. Register specific callbacks in specific tests.

Error injection example: Base driver has virtual function post_drive() — empty by default. Error injection callback overrides post_drive() to randomly flip data bits. Register only in error injection test. Zero changes to base driver or env.
💡 Insight
Callbacks are the professional alternative to copy-paste. Without callbacks: fork base driver, add error injection, maintain two versions forever. With callbacks: one driver, multiple callback variants, all tested independently. AMD specifically asks for a real testbench example — not a generic explanation.
Q2.12What is raise_objection and drop_objection? What happens without them?MED▾
Answer
raise_objection(this) at the start of test run_phase prevents the simulation from ending prematurely. drop_objection(this) signals completion — simulation ends when all objections are dropped to zero.

Without raise: simulation ends immediately at time 0 (all phases complete with no outstanding objections — nothing to wait for).

Pattern:
task run_phase(uvm_phase phase);
phase.raise_objection(this);
// ... run sequences ...
phase.drop_objection(this);
endtask

Drain time: phase.phase_done.set_drain_time(this, 100ns) — allows pending transactions to complete after last drop.
⚠ Watch Out
Common mistake: dropping objection inside a sequence (sequences don't have access to the phase object directly). Drop objection in the test after sequence.start() returns. Another mistake: raising objection in driver/monitor — these run forever and never drop, hanging simulation.
Q2.13Active vs passive agent — when does active become passive?MED▾
Answer
Active agent (is_active = UVM_ACTIVE): has driver + sequencer + monitor. Drives DUT inputs. Used when the testbench controls that interface.

Passive agent (is_active = UVM_PASSIVE): monitor only. Observes without driving. Used when:
1. DUT is the master on that interface — DUT initiates transactions, TB only monitors.
2. SoC integration level where another block drives the interface — TB observes DUT-to-DUT traffic.
3. For coverage and checking only — no stimulus generation needed.

Switch: agent.is_active = UVM_PASSIVE in build_phase (or via config_db). Driver and sequencer not instantiated.
💡 Insight
Passive agents are critical in SoC verification. You have active agents on CPU/stimulus interfaces (TB drives), and passive agents on DUT-to-DUT interfaces (observe for coverage and protocol checking). Interview trap: 'Can a passive agent have a sequencer?' — No. If someone says yes, they're confusing passive with virtual.
Q2.14Difference between copy() and clone()? What is $cast?MED▾
Answer
copy(src): copies fields FROM src INTO current object — in-place modification. No new object created.

clone(): creates a NEW object, copies all fields into it, returns handle to new object. Equivalent to: new + copy.

$cast: safe runtime downcast. Checks type compatibility before assignment. Returns 1 (success) or 0 (failure).

// Without $cast — compiler rejects downcast:
// child_h = base_h; // ERROR

// With $cast — safe:
child_txn c;
if (!$cast(c, base_handle))
`uvm_fatal("CAST", "Incompatible types");
💡 Insight
Both copy() and clone() require do_copy() override for custom fields (dynamic arrays, nested objects). Default implementation only copies fields known to the base class. If your txn has a rand byte payload[] dynamic array — implement do_copy() to deep-copy the array. Otherwise clone() gives you a new txn with a SHARED array reference — still shallow.
Q2.15UVM severity levels, verbosity levels, and how to control them.MED▾
Answer
Severity levels:
UVM_INFO: informational message.
UVM_WARNING: potential issue — doesn't increment error count.
UVM_ERROR: increments error count — simulation continues by default.
UVM_FATAL: kills simulation immediately — no recovery.

Verbosity levels (message filtering):
UVM_NONE (0) → UVM_LOW (100) → UVM_MEDIUM (200, default) → UVM_HIGH (300) → UVM_FULL (400) → UVM_DEBUG (500).

Control on command line:
+UVM_VERBOSITY=UVM_HIGH — show HIGH and below.
+UVM_VERBOSITY=UVM_DEBUG — show everything.

In code: set_report_verbosity_level(UVM_HIGH); or per-component.
📌 Pro Tip
Use UVM_HIGH for transaction-level debug (every sequence item). Use UVM_DEBUG for signal-level debug (every clock edge). Keep normal simulation at UVM_MEDIUM — HIGH verbosity in regression creates huge log files and slows simulation.
