Q3.1Write constraint: exactly 4 bits set to 1 in a 32-bit variable.HIGH▾
rand bit [31:0] val;
constraint c_4bits { $countones(val) == 4; }

// Variation: at least 4 bits
constraint c_atleast4 { $countones(val) >= 4; }

// Without $countones (if asked):
class txn;
  rand bit [31:0] val;
  rand int ones_count;
  constraint c_count {
    ones_count == 0;
    foreach(val[i]) ones_count += val[i];
    ones_count == 4;
  }
endclass
💡 Insight
$countones() is the correct and cleanest answer. Asked at Intel, AMD, and Insemi. Variations to know: 'odd number of 1s' → $countones(val) % 2 == 1. 'At least N bits high' → $countones(val) >= N. 'Exactly N bits low' → $countones(~val) == N.
Q3.2Write constraint: dynamic array ascending order, odd values only, size 10–20.HIGH▾
class arr_txn;
  rand int arr[];

  constraint c_size { arr.size() inside {[10:20]}; }

  constraint c_odd  {
    foreach(arr[i]) arr[i] % 2 != 0;
  }

  constraint c_asc  {
    foreach(arr[i])
      if(i > 0) arr[i] > arr[i-1];  // strictly ascending
      // use >= for non-decreasing
  }
endclass
💡 Insight
Three separate named constraints — each can be disabled independently with c_odd.constraint_mode(0). Asked at Mirafra (Shivam Awasthi, 2023) with this exact combination. Note: arr[i] > arr[i-1] is strictly ascending. arr[i] >= arr[i-1] is non-decreasing (allows duplicates). Pick based on requirement.
Q3.3Write constraint: 5-bit variable with odd number of 1s.HIGH▾
rand bit [4:0] val;

// Method 1: $countones
constraint c_odd_ones { $countones(val) % 2 == 1; }

// Method 2: Without system task (if asked at AMD/Mirafra)
class odd_ones_txn;
  rand bit [4:0] val;
  function int count_ones(bit [4:0] v);
    int cnt = 0;
    foreach(v[i]) if(v[i]) cnt++;
    return cnt;
  endfunction
  constraint c_odd {
    count_ones(val) % 2 == 1;
  }
endclass
💡 Insight
Mirafra (Shivam Awasthi) specifically asked to write this WITHOUT $countones — using a function inside the constraint. This tests deeper understanding: constraints can call functions that return values, as long as the function is deterministic and doesn't contain procedural side effects.
Q3.4Write constraint: AXI 4KB page boundary — burst must not cross page.HIGH▾
rand bit [31:0] awaddr;
rand bit [7:0]  awlen;   // AWLEN: number of beats = awlen+1
rand bit [2:0]  awsize;  // AWSIZE: bytes/beat = 2^awsize

constraint c_4k {
  // All beats must stay within same 4KB page
  // Total transfer size: (awlen+1) * (1 << awsize)
  // Last byte address: awaddr + total_size - 1
  // Must be in same page: addr[31:12] unchanged

  (awaddr & 32'hFFF) + ((awlen + 1) * (1 << awsize))
    <= 32'h1000;
  // i.e. offset_within_page + transfer_size <= 4096
}
💡 Insight
This is the most technically precise constraint in AXI verification. The 4KB rule: all beats of INCR and WRAP bursts must stay within the same 4KB page (address bits [31:12] must not change). AXI interconnects implement address decode per 4KB page — a burst crossing the boundary routes different beats to different slaves. Asked at AMD, Insemi, Tenstorrent.
Q3.5Write constraint: power of 2, unique array, and Fibonacci.HIGH▾
// Power of 2 (two methods):
rand int val;
constraint c_pow2   { val != 0; (val & (val-1)) == 0; }
// Alternative: rand int exp; constraint c { val == 1< 1) fib[i] == fib[i-1] + fib[i-2];
}
💡 Insight
Power of 2 bit-trick: powers of 2 have exactly one bit set. Subtracting 1 flips all lower bits to 1. AND gives 0. Works for all powers of 2. val!=0 required because 0 also satisfies the trick. Google asked 'any other way?' — show the shift approach. Fibonacci has only one solution — it's a deterministic constraint.
Q3.6What is solve-before? How do you disable constraints? What are soft constraints?MED▾
// Disable constraint at runtime:
obj.c_4k.constraint_mode(0);  // OFF
obj.c_4k.constraint_mode(1);  // ON

// Check if enabled:
if (obj.c_4k.constraint_mode()) ...

// Soft constraint — overridable:
constraint c_default { soft addr inside {[0:100]}; }
// Override in uvm_do_with — inline wins:
`uvm_do_with(req, { req.addr == 200; })
// req.addr will be 200, soft constraint ignored

// Solve-before — affects distribution:
rand int burst_type;  // FIXED=0, INCR=1, WRAP=2
rand bit [31:0] addr;
constraint c_order {
  solve burst_type before addr;
  if(burst_type == 2) addr % 4 == 0;  // WRAP needs aligned
}
💡 Insight
solve-before affects probability distribution. Without it, the solver may produce statistically biased results when one variable constrains another. Real use case: solve AWBURST before AWADDR — WRAP bursts need aligned addresses, INCR doesn't. Without solve-before, the solver may overwhelmingly produce INCR (easier to satisfy) rather than balanced FIXED/INCR/WRAP distribution.
Assertions — Write Live
Q3.7Write assertion: req → ack within 1–3 cycles. All important operators.HIGH▾
// Core assertion:
property p_ack;
  @(posedge clk) disable iff (!rst_n)
  req |-> ##[1:3] ack;    // |-> overlapping implication
endproperty
ASSERT_ACK: assert property(p_ack)
  else `uvm_error("ASSERT",
    $sformatf("ACK missing at t=%0t",$time));

// Cover: confirm assertion is actually exercised
COVER_REQ: cover property(@(posedge clk) req);

// Operators reference:
// ##N      : exactly N cycles later
// ##[1:3]  : 1 to 3 cycles (inclusive)
// |->      : overlapping implication (same cycle)
// |=>      : non-overlapping (next cycle)
// $rose(x) : 0->1 only (not X->1)
// $fell(x) : 1->0 only
// $stable(x): no change from previous cycle
// $past(x) : value of x one cycle ago
// $past(x,N): value N cycles ago
// $changed(x): different from previous cycle
💡 Insight
Two things most candidates miss: (1) disable iff (!rst_n) — without this, assertion fires spuriously every reset cycle. (2) cover property — confirms the assertion was actually triggered. An assertion that is never triggered gives false confidence. Always pair assert with cover. |-> vs |=>: req |-> ##1 ack means ack at clock N+1. req |=> ##1 ack means ack at clock N+2.
Q3.8Write assertion: counter stable when disabled, increments when enabled.HIGH▾
property p_stable;
  @(posedge clk) disable iff (!rst_n)
  !en |-> $stable(cnt);
endproperty

property p_incr;
  @(posedge clk) disable iff (!rst_n)
  en |-> cnt == $past(cnt) + 1;
endproperty

ASSERT_STABLE: assert property(p_stable);
ASSERT_INCR:   assert property(p_incr);

// Variation: counter wraps at 255
property p_wrap;
  @(posedge clk) disable iff (!rst_n)
  en |-> cnt == ($past(cnt) == 8'hFF ? 8'h00
                                     : $past(cnt)+1);
endproperty
💡 Insight
Two separate properties is always cleaner than one combined. Each can be named, disabled independently, and produces a clear message when it fires. This exact question was asked at Intel, AMD, and Insemi. The wrap variation tests whether you understand overflow behaviour — know it.
Q3.9Write assertion for T flip-flop, and AXI high-priority arbitration.HIGH▾
// T flip-flop: when T=1, Q toggles; when T=0, Q stable
property p_tff_toggle;
  @(posedge clk) t |-> q == !$past(q);
endproperty
property p_tff_stable;
  @(posedge clk) !t |-> $stable(q);
endproperty

// AXI arbitration: hi_req gets grant when both request
property p_arb_priority;
  @(posedge clk) disable iff (!rst_n)
  (hi_req && lo_req) |-> ##[0:2] (hi_grant && !lo_grant);
endproperty

// VALID must stay high once asserted until READY:
property p_valid_stable;
  @(posedge clk) disable iff (!rst_n)
  (awvalid && !awready) |=> awvalid;
endproperty
ASSERT_VALID: assert property(p_valid_stable);
💡 Insight
The AWVALID stability assertion is critical for AXI verification — the spec requires VALID to stay high once asserted until READY responds. Missing this assertion means AXI protocol violations go undetected. This is one of the most common sources of AXI integration bugs. Asked at WD and Tenstorrent.
Q3.10Difference between consecutive [*N], goto [->N], and non-consecutive [=N] repetition.MED▾
Answer
Consecutive [*N]: signal must be true for exactly N consecutive cycles. a[*3] means a=1 at t=0, t=1, t=2.

Goto [->N]: signal must be true exactly N times, gaps allowed between occurrences. ack[->3] — ack goes high, can go low, high again, can go low, high once more. Sequence anchored to last occurrence.

Non-consecutive [=N]: like goto but sequence continues after Nth match rather than ending. Last match doesn't need to immediately precede the next element.

Range syntax: a[*2:5] — a must be true between 2 and 5 consecutive cycles.
💡 Insight
Goto [->] is the most commonly confused operator. Real use case: in AXI write bursts, WVALID may deassert between beats (pipeline stall). WVALID[->AWLEN+1] means AWLEN+1 beats of WVALID=1, potentially non-consecutive. This is more accurate than WVALID[*AWLEN+1] which requires consecutive cycles. Intel asked about this distinction specifically.

Q3.11Write complete covergroup: bins, ignore_bins, illegal_bins, cross coverage.HIGH▾
covergroup axi_cg @(posedge clk);
  option.per_instance = 1;   // Separate stats per instance

  cp_addr: coverpoint addr {
    bins low   = {[8'h00 : 8'h3F]};
    bins mid   = {[8'h40 : 8'hBF]};
    bins high  = {[8'hC0 : 8'hFD]};
    ignore_bins reserved = {8'hFE};  // Exclude from goal
    illegal_bins bad     = {8'hFF};  // Error if ever seen
  }

  cp_burst: coverpoint burst_type {
    bins fixed  = {2'b00};
    bins incr   = {2'b01};
    bins wrap   = {2'b10};
  }

  cp_len: coverpoint awlen {
    bins single  = {8'd0};          // 1 beat
    bins short   = {[8'd1 : 8'd7]};
    bins long    = {[8'd8 : 8'd255]};
  }

  // Cross: all combinations
  cx_burst_len: cross cp_burst, cp_len {
    // FIXED burst with len>0 is technically valid but unusual
    ignore_bins fixed_long =
      binsof(cp_burst.fixed) && binsof(cp_len.long);
  }
endgroup : axi_cg
💡 Insight
ignore_bins excludes values from coverage goal — they don't count for OR against your percentage. illegal_bins errors if the value is EVER seen in simulation. Use illegal_bins for values that must never occur (protocol violations, reserved encodings). Cross coverage bin count = product of individual coverpoint bin counts — manage size carefully.
Q3.12Write FSM state AND transition coverage.HIGH▾
typedef enum {IDLE, FETCH, DECODE, EXEC, WB, ERROR} fsm_t;
fsm_t state;

covergroup fsm_cg @(posedge clk);
  // State coverage
  cp_state: coverpoint state {
    bins idle   = {IDLE};
    bins fetch  = {FETCH};
    bins decode = {DECODE};
    bins exec   = {EXEC};
    bins wb     = {WB};
    bins error  = {ERROR};
  }
  // Transition coverage — specific important transitions
  cp_trans: coverpoint state {
    bins i2f  = (IDLE   => FETCH);
    bins f2d  = (FETCH  => DECODE);
    bins d2e  = (DECODE => EXEC);
    bins e2w  = (EXEC   => WB);
    bins w2i  = (WB     => IDLE);
    // Error entry from any state
    bins any2err = (IDLE,FETCH,DECODE,EXEC,WB => ERROR);
    // Recovery path — critical!
    bins err2i   = (ERROR => IDLE);
    // Unusual but valid: DECODE -> EXEC stall repeat
    bins stall   = (DECODE => DECODE);
  }
endgroup
💡 Insight
Always include error recovery transitions (ERROR→IDLE). Untested recovery is where real silicon bugs hide — the chip can get stuck in error state permanently. Also include 'stall' self-transitions (DECODE→DECODE) for pipeline stall scenarios. State coverage alone misses these paths. Asked at AMD, Samsung, Mirafra.
Q3.13Code coverage vs functional coverage: types and which is primary metric.HIGH▾
Answer
Code coverage (automatic):
Statement: which RTL lines executed.
Branch: which if/else, case branches taken.
Toggle: which signals transitioned 0→1 and 1→0.
Expression: sub-expressions within conditions.
FSM: states visited and transitions taken.

Functional coverage (manual — user-defined):
Covergroups, coverpoints, cross coverage — user specifies what matters based on the specification. Requires deep design knowledge to write correctly.

Primary metric: Functional coverage. Code coverage is a diagnostic tool. 100% code coverage does NOT mean verification is complete — it only means all RTL lines were executed, not that they executed correctly or with the right input combinations.
💡 Insight
Classic failure mode: 100% code coverage on a register block from one test that happens to touch every line. But functional coverage at 40% because you never tested: W1C clear-on-write semantics, RO field write resistance, reset value correctness, misaligned access error response. This exact distinction is how experienced interviewers separate process-driven DV engineers from test-writers.
Fork-Join, OOP, Scheduling
Q3.14Fork-join types and classic for-loop trap — predict output.HIGH▾
// TRAP QUESTION — predict output:
for(int i=0; i<3; i++) begin
  fork
    $display("Value: %0d", i);
  join_none
end
// OUTPUT: 3  3  3  (NOT 0 1 2)
// WHY: i shared. join_none spawns but threads don't run
// until parent yields. Loop ends (i=3). All threads see 3.

// FIX: automatic captures value at spawn time:
for(int i=0; i<3; i++) begin
  fork
    automatic int j=i;
    $display("Value: %0d", j);  // OUTPUT: 0  1  2
  join_none
end

// join:     wait for ALL threads
// join_any: wait for FIRST thread, others continue
// join_none: fire and forget, parent continues immediately

// fork-join_any output prediction:
fork
  #15 $display("A");  // fires t=15
  #5  $display("B");  // fires t=5  → join_any exits here
  #10 $display("C");  // continues after join_any
join_any
#2 $display("D");     // fires at t=5+2=7
// Order: B(5), D(7), C(10), A(15)
💡 Insight
The for-loop fork-join_none trap is THE most asked SV trick question at AMD, Intel, and multiple others. ~100% of candidates who haven't seen it before get it wrong. Once understood, it's unforgettable. The lesson: join_none threads share enclosing scope — loop variable is shared. automatic creates an independent local copy at spawn time. Know this cold.
Q3.15Write polymorphism example relevant to a DV testbench.HIGH▾
// Base driver — virtual hook
class base_drv extends uvm_driver #(my_txn);
  `uvm_component_utils(base_drv)
  virtual task drive(my_txn t);
    @(posedge vif.clk);
    vif.data <= t.data;  // Normal drive
  endtask
  task run_phase(uvm_phase phase);
    my_txn req;
    forever begin
      seq_item_port.get_next_item(req);
      drive(req);  // Calls virtual — dispatches to derived
      seq_item_port.item_done();
    end
  endtask
endclass

// Error injection — override the hook only:
class err_drv extends base_drv;
  `uvm_component_utils(err_drv)
  int err_rate = 10;  // 10%
  virtual task drive(my_txn t);
    if($urandom_range(0,99) < err_rate)
      vif.data <= t.data ^ 32'hDEAD;  // Corrupt
    else
      super.drive(t);  // Normal path
  endtask
endclass

// In test — one line change, zero env/agent changes:
// factory.set_type_override_by_type(
//   base_drv::get_type(), err_drv::get_type());
💡 Insight
AMD and Meta specifically ask for a testbench-relevant polymorphism example — not animals making sounds. This is the canonical answer: error injection via driver override using factory. Zero changes to env or agent. The derived class is ONLY registered in the error test. This shows you understand WHY virtual functions and factory exist together in UVM.
Q3.16Difference: blocking vs non-blocking. Predict output of blocking/non-blocking mix.HIGH▾
// Blocking (=): execute immediately, sequentially
// Non-blocking (<=): schedule at end of time step (NBA region)

// PREDICT OUTPUT:
always @(posedge clk) begin
  a = 1;      // blocking: a is 1 immediately
  b <= a;     // non-blocking: schedules b=current_a=1
  a = 0;      // blocking: a is now 0
  c <= a;     // non-blocking: schedules c=current_a=0
end
// After time step: b=1, c=0, a=0
// b captures a BEFORE second blocking assignment
// c captures a AFTER second blocking assignment

// SV event scheduler regions:
// Active:     Blocking assignments, procedural code
// NBA:        Non-blocking updates (after Active)
// Observed:   Assertions evaluated
// Reactive:   Procedural TB code re-evaluated
// Postponed:  $strobe, $monitor (final values)

// $display vs $strobe:
a <= 1;
$display(a);  // Sees OLD value (Active region)
$strobe(a);   // Sees FINAL value (Postponed region)
💡 Insight
The blocking/non-blocking mix output prediction is asked at WD, Intel, and AMD. Key principle: non-blocking reads the RHS at the time of the statement, but writes to the LHS at the END of the time step. So b<=a reads a=1 (the current value), even though a will be 0 by end of Active region. Scoreboard rule: use $strobe for monitoring final signal values, not $display.
Q3.17Write SV code: out of 3 threads, after first 2 complete, kill all.MED▾
task run_two_and_kill();
  int done_cnt = 0;
  event two_done;

  fork
    begin : thread1
      do_work_1();
      done_cnt++;
      if(done_cnt == 2) -> two_done;
    end
    begin : thread2
      do_work_2();
      done_cnt++;
      if(done_cnt == 2) -> two_done;
    end
    begin : thread3
      do_work_3();
      done_cnt++;
      if(done_cnt == 2) -> two_done;
    end
    @two_done;  // Wait for event
  join_any    // Exit when @two_done fires

  disable fork;  // Kill remaining threads
endtask
💡 Insight
disable fork kills ALL child threads spawned in the current scope. This exact pattern is used for timeout implementation in UVM: fork { actual_work } and { #timeout_ns; } join_any; disable fork; — whichever finishes first exits join_any, then disable fork kills the other. Intel asked this in a 2023 interview.
Q3.18Dynamic array vs associative array vs queue: when to use each in a scoreboard?MED▾
Answer
Dynamic array (int arr[]): contiguous, integer index, resizable with new[N]. O(1) access. Use for: packet payloads, sequential data, test patterns where order and size are known at runtime.

Associative array (int arr[key]): sparse, any type key, O(log N) lookup. Use for: scoreboards keyed by transaction ID (out-of-order matching), address maps, configuration tables.

Queue (int arr[$]): ordered, push_back/pop_front, auto-grows. O(1) push/pop. Use for: FIFO-style transaction histories, in-order checking.

Scoreboard design rule: AXI out-of-order → associative array keyed by ARID. In-order APB → queue. Large register map lookup → associative array keyed by address.
💡 Insight
AMD asked 'which is better' — never answer 'it depends' without justification. Answer: 'For AXI out-of-order scoreboard, associative array keyed by ID is better — O(log N) match vs O(N) queue scan for each transaction. For in-order APB, queue is simpler and sufficient. For register map: associative array keyed by address offset.' The data structure choice determines scoreboard correctness and performance.
