RAL and Register Verification
Q7.1What is UVM RAL? Walk through the class hierarchy.MED▾
Answer
RAL = Register Abstraction Layer. Models the entire register map as a class hierarchy:

uvm_reg_block (top container) → uvm_reg_map (address map: maps register to address) → uvm_reg (individual register) → uvm_reg_field (bit fields within register: name, width, access type, reset value).

Integration: reg_block.default_map.set_sequencer(sequencer, adapter). Adapter subclasses uvm_reg_adapter, implements reg2bus() (converts reg op to bus txn) and bus2reg() (converts bus response back to reg).

Flow: test calls reg.write(status, value) → RAL → adapter.reg2bus() → bus transaction → sequencer → driver → DUT → monitor → adapter.bus2reg() → RAL updates mirror → check status.
💡 Insight
RAL is the professional approach to register verification. Without RAL: custom sequences for every register — doesn't scale past 10 registers. With RAL: write once, reuse across all 500+ registers. Mirror checking (reg.mirror()) automatically compares expected register state to actual DUT — finds resets to wrong values, R/W permission violations, and field encoding errors without writing individual assertions for each register.
Q7.2Front-door vs back-door access — when to use each?MED▾
Answer
Front-door: access via actual bus transaction (AXI, APB, AHB). Bus-accurate — takes simulation time. Exercises the bus interface and DUT bus protocol simultaneously. Required to test bus-related functionality (address decode, error responses, wait states, burst handling).

Back-door: direct HDL path via UVM backdoor methods or $hdl_read/write. Zero simulation time — instantaneous. Bypasses bus entirely. Use for: fast initialisation of large register files (1000 registers × front-door = 1000 bus transactions = slow); checking RTL state without triggering bus side-effects; DFT tests where bus may be unavailable; setting up testbench state before test.

reg.write() = front-door. reg.poke() = back-door. reg.peek() = back-door read. reg.read() = front-door read.
💡 Insight
Combined pattern: back-door initialise registers to known state (fast), front-door verify that AXI bus access reads/writes them correctly (tests the bus + register simultaneously). This is more efficient than front-door initialisation while still achieving full protocol coverage. HCL interview specifically asked: 'When would you choose back-door over front-door?' — this combined pattern is the answer.
Q7.3What register types exist in CSR verification?MED▾
Answer
RW (Read-Write): write any value, read back same value. Most common.
RO (Read-Only): write has no effect — value unchanged. Driven by hardware. Verify: write attempt doesn't change value, read returns hardware-driven status.
WO (Write-Only): read returns 0 or undefined. Write activates function. Verify via side effects on control signals.
W1C (Write-1-to-Clear): hardware sets bit. Writing 1 clears it. Writing 0 has no effect. Used for interrupt status bits. Verify: set (hardware trigger), read (=1), write 1 (clears), read again (=0). Writing 0 to already-set bit — no change.
RC (Read-Clear): reading the register clears it. Read twice — second read returns 0 for cleared bits.
W1S (Write-1-to-Set): writing 1 sets bit. Writing 0 has no effect. Inverse of W1C.
💡 Insight
W1C is the most commonly verified and most commonly bugged register type. The failure modes: (1) write 0 incorrectly clears the bit (should have no effect). (2) clearing one W1C bit inadvertently clears adjacent W1C bits (byte-write mask error). (3) Hardware-set event arrives simultaneously with software-clear — race condition in the register fabric. These bugs only appear with careful directed testing.
Q7.4How did you verify CSR control signal generation and status readback?MED▾
Answer
Control signal verification:
1. Write specific value to control register via AXI front-door.
2. Next clock: sample downstream control outputs from DUT at the interface boundary.
3. Scoreboard compares: written bit field → expected control signal encoding → actual DUT output.
4. Test: each control field independently. Test all valid encoding values. Verify control holds stable until register is modified again.
5. Reset: verify all control signals return to safe reset values on reset assertion.

Status readback:
1. Drive status inputs from functional blocks (force via backdoor or connect to stimulus agent).
2. Read STATUS register via AXI front-door.
3. Verify PRDATA matches driven status values.
4. Verify correct bit mapping — functional block A status maps to correct bit positions in register.
5. Verify status captures transient events (write-1-clear pattern for sticky status bits).
💡 Insight
Common CSR bugs found in verification: (1) Control signal updates with 1-cycle latency vs expected same-cycle update. (2) Status readback returns stale value because status signal from functional block's clock domain not properly synchronised to register bus clock. (3) Reset value wrong — control signal at reset is not the safe default (e.g., DMA enable=1 at reset when it should be 0). These bugs require specific directed test scenarios.
Q7.5What is eFuse? What are the key verification scenarios?LOW▾
Answer
eFuse (electronically-programmable fuse): one-time programmable (OTP) memory. Bits can only be programmed ONCE — once blown, cannot be reset. Used for: device serial numbers, security keys, hardware configuration, feature enabling/disabling, manufacturing calibration data.

Verification scenarios:
1. Read before program — all bits should return 0 (unprogrammed state).
2. Program a specific bit — write operation blows the fuse.
3. Read after program — programmed bits should return 1.
4. Attempt to re-program a blown fuse — value must remain 1 (no change). This is the OTP property.
5. Read after reset — programmed bits persist across reset (non-volatile).
6. Partial programming — program some bits, verify others unchanged.
7. ECC on eFuse — if ECC is used, verify error detection on corrupted eFuse reads.
📌 Pro Tip
eFuse verification is important at Intel (eFuse used for CPU SKU configuration and security keys). The OTP property is the most critical: once a bit is 1, it must NEVER become 0 regardless of write attempts. The verification assertion: @(posedge clk) (prev_efuse_val[i] == 1) |-> (efuse_val[i] == 1).
