Sequential Logic and Timing
Q5.1Latch vs FF: what's the difference? Both memory elements? Why prefer FF?HIGH▾
Answer
Both are memory elements — both store 1 bit of state.

Latch: level-sensitive. Transparent when enable=HIGH — output follows input instantly. Holds value when enable=LOW. Problem: input glitches during enable=HIGH window propagate directly to output. Creates unbounded combinational paths (latch + logic = path STA can't easily characterise).

Flip-Flop: edge-triggered. Samples input ONLY at active clock edge (rising or falling). Output changes only at that edge — completely ignores input between edges. Clean, predictable setup and hold windows.

FF preferred: synchronous design with FFs has predictable, STA-analysable timing. All paths have clear start (FF clock pin) and end (FF data pin) points. Latches create 'transparent windows' where timing is unconstrained — STA is complex or impossible during the window.
💡 Insight
Synthesis tools infer latches from incomplete if/case statements — missing else clause in always @(*) block creates a latch. This is usually unintentional and is a common RTL bug. A good DV engineer checks the synthesis report for unexpected latches and queries the RTL designer. Good synthesis tools warn about inferred latches — never ignore these warnings.
⚠ Watch Out
'Latch is bad' is too simple. Some designs intentionally use latches for power savings (C2MOS cells, clock gating cells). The real answer: latches require careful constraint management in STA and extra verification attention. FFs are the default choice for synchronous design.
Q5.2What is grey code? Why use it in async FIFO pointers and FSMs?HIGH▾
Answer
Grey code: a binary encoding where only ONE bit changes between any two consecutive values.

Regular binary: 011 (3) → 100 (4) — 3 bits change simultaneously.
Grey code: 010 (3) → 110 (4) — only 1 bit changes.

In async FIFO: read and write pointers cross clock domains. If pointers use binary encoding: a transition like 3→4 (011→100) changes 3 bits simultaneously. The destination domain samples mid-transition and sees a garbage intermediate value (e.g., 101=5, 110=6, or 001=1) — wrong pointer value → FIFO corruption → data loss.
With grey code: only 1 bit changes per count — destination domain sees either old value or new value. Never a corrupted intermediate.

In FSMs: prevents glitches on state decode output when transitioning between states — decoder logic produces cleaner transitions.
💡 Insight
This is one of the most fundamental CDC concepts. The key insight: a 2-flop synchroniser resolves metastability for a SINGLE bit — it cannot resolve MULTI-bit signals because each bit synchronises independently and may resolve at different cycles, creating a transient garbage value. Grey code makes multi-bit signals safe to synchronise because only ONE bit changes at a time — so the synchroniser either captures the old value or the new value, never garbage.
Q5.3What is GLS? What does it detect that RTL simulation misses?HIGH▾
Answer
GLS (Gate Level Simulation): simulate the post-synthesis netlist with actual gate delays annotated from SDF (Standard Delay Format) file produced by synthesis/STA tools.

Detects (that RTL cannot):
1. Timing violations — setup/hold failures that cause functional errors under real delays.
2. X-propagation — unknown states from uninitialized flip-flops, multi-driver conflicts, or metastability spreading.
3. Reset issues — async reset timing, incomplete reset coverage, clock-tree delays affecting reset synchronisation.
4. Clock gating bugs — enable signals with glitches, incorrect gating polarity, timing violations in gated clock paths.
5. Don't-care optimisation — synthesis optimised based on don't-care conditions that your functional TB didn't exercise but real silicon will encounter.
💡 Insight
GLS is the last line of defence before tape-out. Many bugs that pass functional simulation are caught in GLS. Particularly: reset sequences (async reset arrives relative to different clock phases after synthesis), clock domain crossings (synchroniser timing with real delays), and retention/isolation cell behaviour (power management). Knowing the categories of bugs GLS catches (not just 'it tests timing') is what experienced interviewers want.
📌 Pro Tip
Types of GLS runs: Zero-delay GLS (confirms functional correctness of netlist — no timing). SDF-annotated GLS (confirms timing correctness with real delays). Both are needed for complete sign-off. Zero-delay first to confirm correct netlist, then SDF to confirm timing.
Q5.4What is metastability? How do you prevent it? What is MTBF?HIGH▾
Answer
Metastability: when a FF's data or clock input changes within the setup or hold window, the FF enters a metastable state — output neither 0 nor 1, oscillating. Eventually resolves, but takes unpredictable time. If downstream logic samples during this window, it sees garbage.

Prevention:
1. Never let asynchronous signals directly drive synchronous logic without synchronisation.
2. 2-flop synchroniser for single-bit signals: first FF may go metastable but has a full clock period to resolve before second FF samples.
3. Grey code pointers for multi-bit signals crossing clock domains (async FIFO).
4. Handshake protocol for multi-bit control signals (req/ack across domains).

MTBF: Mean Time Between metastability Failures. MTBF = exp(C2 × T_resolve) / (C1 × f_clk × f_data). With adequate timing slack (full clock period to resolve), MTBF becomes centuries — acceptable for production silicon.
💡 Insight
The MTBF formula is sometimes asked at senior interviews at AMD and Qualcomm. The key insight: faster clock rates reduce T_resolve (less time for the synchroniser FF to resolve before the next FF samples). This is why high-frequency designs need careful synchroniser analysis and sometimes need 3-flop synchronisers.
Q5.5Setup violation vs hold violation: causes and fixes.HIGH▾
Answer
Setup violation: data changes TOO LATE relative to the clock edge — violates setup time (data must be stable N ns BEFORE the clock edge).
Cause: too much combinational logic delay on the data path — the path is too slow.
Fix: reduce combinational logic depth (pipeline the path, restructure logic, retiming), increase clock period, use faster cells.

Hold violation: data changes TOO EARLY after the clock edge — violates hold time (data must remain stable N ns AFTER the clock edge).
Cause: the data path is TOO FAST — data from launching FF propagates and changes before the capturing FF's hold window ends.
Fix: add buffers on the short data path (increase delay), ECO buffers inserted by router.

Key insight: setup violations fixed by slowing/optimising logic. Hold violations fixed by adding delay. Hold violations are harder to fix in silicon (require ECO buffers) vs setup (can fix in timing by restructuring).
⚠ Watch Out
Hold violations are more dangerous than setup violations in several ways: (1) they cannot be fixed by slowing the clock — they're independent of clock period. (2) They can be introduced by variation (process, voltage, temperature) even if clean at nominal. (3) They appear in GLS as X-propagation from the capturing FF. A design with hold violations can work in simulation but fail in silicon.
Q5.6Stuck-at fault testing: how do you verify a bit is stuck at 0 or 1?MED▾
Answer
Stuck-at-0 (SA0) test for data bit 5:
1. Write 0xFFFFFFFF to address — all bits should be 1.
2. Read back — if bit 5 reads 0 → SA0 confirmed.
3. Write 0x00000020 (only bit 5 = 1) — read back — if bit 5 is 0 → SA0 confirmed.

Stuck-at-1 (SA1) test for data bit 5:
1. Write 0x00000000 — all bits should be 0.
2. Read back — if bit 5 reads 1 → SA1 confirmed.

Walking ones / zeros pattern: write 0x00000001, read back, shift left, repeat — covers each bit independently. Detects SA0 (walking ones: if bit stuck at 0, the one can't reach it) and SA1 (walking zeros: if bit stuck at 1, zero can't overwrite it).
💡 Insight
This comes from WD (Maneesh Gupta) face-to-face interview. The DFT engineering view: ATPG (Automatic Test Pattern Generation) generates patterns specifically designed to sensitise each fault and observe the effect at primary outputs. The DV view: toggle coverage verifies each bit transitions 0→1 and 1→0. Zero toggle on a bit is a signal that the stuck-at test may have been missed.
Q5.7Combinational circuits: implement OR gate using 2:1 MUX. Build full adder.MED▾
Answer
OR gate using 2:1 MUX:
MUX(sel=A, I0=1, I1=B) = A ? B : 1 — no, that's not right.
Correct: MUX(sel=A, I0=B, I1=1) → when A=0, out=B; when A=1, out=1. This is A OR B. ✓
Alternative: MUX(sel=B, I0=A, I1=1) → symmetric, also correct.

Full adder truth table: inputs A, B, Cin → outputs Sum, Cout.
Sum = A XOR B XOR Cin.
Cout = (A AND B) OR (B AND Cin) OR (A AND Cin).
Gate count: 2 XOR + 2 AND + 1 OR = 5 gates.

Verify full adder: 8 combinations (2³). Walking ones approach: apply 001, 010, 100 — each verifies one input path. Then combinations: 011, 101, 110, 111, 000.
📌 Pro Tip
MUX as universal building block: AND(A,B) = MUX(sel=A, I0=0, I1=B). NAND = MUX(sel=A, I0=1, I1=~B). NOR = MUX(sel=A, I0=~B, I1=0). XOR = MUX(sel=A, I0=B, I1=~B). Knowing these mappings is useful for FPGA implementation discussions where LUTs (lookup tables) implement arbitrary combinational functions.
