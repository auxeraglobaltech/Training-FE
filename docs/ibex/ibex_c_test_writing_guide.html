1 Big Picture

A C test is an ordinary C program compiled for RV32IMC and loaded into the testbench memory. The core runs it, and the only way the program can talk to the outside world is through loads and stores on its data bus. Every feature in this guide uses that one channel: a store to a chosen address means something to the testbench.

2 Memory Map & C Pointers

Ibex has no MMU: a pointer value in C is the physical address on the bus. If you know the memory map, you can reach any location by casting a number to a pointer.

Where should a test put its data? Use the scratch area 0x15000–0x15FFF for anything you address by number. The linker never places code, globals or stack there, and link.ld fails the build if globals grow far enough to collide with it. Writing to random RAM addresses can corrupt your own globals or stack, which gives confusing failures.

From a C pointer to a bus transaction

The line *p = 0x12345678; compiles to a single store instruction. The core's load-store unit puts it on the data bus, and tb_top.sv writes the four bytes into mem_b[]. Here is the real compiler output from runs/<run>/mem_rw_basic.dis:

  volatile uint32_t *p = (volatile uint32_t *)0x00015000;
  *p = 0x12345678u;
     4a8:  12345437   lui   s0,0x12345        # s0 = 0x12345000
     4ac:  67840413   addi  s0,s0,1656        # s0 = 0x12345678   (data)
     4b6:  64d5       lui   s1,0x15           # s1 = 0x00015000   (address)
     4c2:  c080       sw    s0,0(s1)          # STORE word -> bus write
  uint32_t rd = *p;
     4c4:  4094       lw    a3,0(s1)          # LOAD word  -> bus read
Always use volatile for these pointers. Without it the compiler may keep the value in a register, merge two stores into one, or delete a read whose result it thinks it already knows. Then the test never touches the bus and checks nothing. volatile means: perform every access exactly as written.

Pointer type decides the access size (byte lanes)

The same address can be accessed as a byte, a halfword or a word. The pointer type picks the instruction (sb / sh / sw), and that sets the data_be byte enables, which control which bytes of the word are written.

Example test: sw/tests/mem_rw_basic.c

StepWhatWhy it matters
1One word at literal 0x00015000Simplest possible write → read → compare.
2Patterns 0, FFFFFFFF, A5A5A5A5, 5A5A5A5A, DEADBEEFAll-0 / all-1 / alternating bits catch stuck or shorted data bits.
3Walking-1 across bits 0..31Each data bit toggles on its own.
4Byte / halfword stores, word read-backByte enables, lane order and little-endian layout (Figure 4).
5Fill 64 words with their own address, then verify allFinds address aliasing: a later write wrongly landing on an earlier location.
6Read an initialised globalGlobals are memory too; proves crt0 copied .data (§6).

The core of the test is a compare helper that counts mismatches and keeps going, so one run reports every bad location:

static uint32_t errors;

static void check(const char *what, uint32_t addr, uint32_t exp, uint32_t got) {
  if (got != exp) {
    errors++;
    printf("  MISMATCH %s addr=%x exp=%x got=%x\n", what, addr, exp, got);
  }
}

  volatile uint32_t *p = (volatile uint32_t *)0x00015000;
  *p = 0x12345678u;
  uint32_t rd = *p;
  check("word", (uint32_t)p, 0x12345678u, rd);
  ...
  if (errors) test_fail(errors);   /* fail code = number of mismatches */
  test_pass();

The same access written three ways (all three are identical on the bus):

*(volatile uint32_t *)0x00015000 = v;          /* raw cast, fine for one-offs   */
REG32(SCRATCH_BASE) = v;                         /* memmap.h macro: readable      */
volatile uint32_t *p = (volatile uint32_t *)SCRATCH_BASE;  p[4] = v;   /* p[4] is 0x15010 */
Pointer arithmetic counts elements, not bytes. With uint32_t *p = 0x15000, p + 1 is 0x15004. With a uint8_t * it would be 0x15001. This is why step 5 writes blk[i] = (uint32_t)&blk[i]: printing &blk[i] shows the real byte address.

3 C Prints

There is no UART model and no libc. A "print" is just one store per character to CONSOLE_TX (0x30000). The ibex_console component watches the bus for those stores, collects the characters into a line, and on '\n' prints the line through uvm_info. That puts C output in the same log, with the same timestamps, as the SV messages.

API — sw/common/print.h

CallExample outputNotes
print_str("text\n")textCheapest call: one store per character.
print_hex(0x15000)0x00015000Always 8 digits: addresses and registers line up.
print_dec(-42)-42Signed. print_udec() for unsigned.
print_char('A')AThe single primitive everything else is built on.
printf(fmt, ...)addr=0x00015000 n=3Supports %d %u %x %s %c %%. No widths or flags. %x = print_hex.
 
#include "../common/print.h"

print_str("step 1 done\n");
printf("addr=%x data=%x errors=%d\n", (uint32_t)p, *p, errors);
Rules. (1) End every message with \n. The console only prints complete lines, so text without a newline stays buffered and may never appear. (2) Prints cost simulation time. Each character is a store plus formatting code, about 90 ns (9 clocks) of sim time per character with print_str in this TB, more with printf. Inside long loops, print a summary instead of every iteration. (3) printf here is our function, not libc's. The build uses -ffreestanding, so GCC treats it as a normal function.

The SV side is short enough to read in full (tb/env/ibex_console.sv):

forever begin
  @(vif.mon_cb);
  if (vif.mon_cb.data_req && vif.mon_cb.data_we &&
      {vif.mon_cb.data_addr[31:2], 2'b00} == CONSOLE_TX) begin
    c = vif.mon_cb.data_wdata[7:0];
    if (c == "\n") begin
      `uvm_info("C_PRINT", line, UVM_NONE)
      line = "";
    end else if (c != 8'h0D) begin      // drop CR (SV has no "\r" escape)
      line = {line, string'(c)};
    end
  end
end

4 C ↔ SV Handshake

Many tests need the C program and the SV testbench to take turns. For example: C sets up a peripheral, SV drives some stimulus, then C checks the result. sv_sync(cmd, arg) provides this. C pauses at that line, SV runs its code for cmd, and C resumes on the next line with SV's return value.

Mailbox registers (TB I/O page)

RegisterAddressC doesMeaning
C2SV_ARG0x30014storeArgument for the next command. Must be written before CMD.
C2SV_CMD0x30010storeCommand id (non-zero). This store wakes SV. SV clears ACK at once.
SV2C_ACK0x30018load0 while SV is busy; equals the command id when SV has finished.
SV2C_DATA0x3001CloadResult returned by SV. Valid once ACK == cmd.

C side — sw/common/c2sv.h

static inline uint32_t sv_sync(uint32_t cmd, uint32_t arg) {
  REG32(C2SV_ARG) = arg;
  REG32(C2SV_CMD) = cmd;
  while (REG32(SV2C_ACK) != cmd) { }    /* SV is running its part */
  return REG32(SV2C_DATA);
}

/* compiles to (c_sv_handshake.dis):
     2fe: lui  a5,0x30          # a5 = 0x30000 (TB I/O page)
     302: sw   a1,20(a5)        # C2SV_ARG  @ 0x30014
     304: sw   a0,16(a5)        # C2SV_CMD  @ 0x30010   <- SV wakes here
     308: lw   a4,0(a5)         # SV2C_ACK  @ 0x30018   (a5 += 24 first)
     30a: bne  a4,a0,308        # spin until ACK == cmd
     312: lw   a0,28(a5)        # SV2C_DATA @ 0x3001C   -> return value */

SV side — the base test serves every command

ibex_base_test runs this loop in the background for every test. You never edit it. You only decide what each command does, by overriding handle_c_cmd():

// tb/tests/ibex_base_test.sv
task serve_c_cmds();
  logic [31:0] cmd, arg, result;
  forever begin
    env.c2sv.get_cmd(cmd, arg);        // blocks until C stores C2SV_CMD
    result = '0;
    handle_c_cmd(cmd, arg, result);    // the test's SV code for this step
    env.c2sv.reply(cmd, result);       // releases C
  end
endtask
// tb/tests/ibex_c_sv_sync_test.sv
virtual task handle_c_cmd(logic [31:0] cmd, logic [31:0] arg,
                          output logic [31:0] result);
  case (cmd)
    CMD_SV_WAIT: begin
      `uvm_info("SV", $sformatf("part 1: C is paused, SV runs for %0d clocks", arg), UVM_NONE)
      repeat (arg) @(posedge vif.clk);
      result = arg;
    end
    CMD_SV_COMPUTE: result = arg * 2 + 1;
    CMD_IRQ_ON:     env.agent.drv.poke_irq(IRQ_LINE_EXTERNAL, 1);
    CMD_IRQ_OFF:    env.agent.drv.poke_irq(IRQ_LINE_EXTERNAL, 0);
    default:        super.handle_c_cmd(cmd, arg, result);   // warn + ack
  endcase
endtask

Example test: sw/tests/c_sv_handshake.c

#define CMD_SV_WAIT     1u   /* SV waits `arg` clocks, returns arg        */
#define CMD_SV_COMPUTE  2u   /* SV returns arg * 2 + 1                    */
#define CMD_IRQ_ON      3u   /* SV asserts irq_external_i                 */
#define CMD_IRQ_OFF     4u   /* SV deasserts irq_external_i               */

  print_str("C : part 1 running, handing over to SV\n");
  r = sv_sync(CMD_SV_WAIT, 50);                       /* pure hand-off       */
  printf("C : back from SV (it ran %d clocks), continuing\n", r);

  r = sv_sync(CMD_SV_COMPUTE, 20);                    /* data both ways      */
  if (r != 41) test_fail(1);

  sv_sync(CMD_IRQ_ON, 0);                             /* SV drives the DUT   */
  if (!(read_csr(mip) & MIE_MEIE)) test_fail(3);      /* C sees the effect   */
  sv_sync(CMD_IRQ_OFF, 0);
  ...
  test_pass();

Adding your own step takes four edits: (1) pick a new non-zero id and #define it in the C test; (2) add the matching localparam in your SV test class; (3) add a case branch in handle_c_cmd(); (4) call sv_sync(ID, arg) from C where SV should take over. Run with TEST_NAME=<your SV test>. Under plain ibex_base_test an unknown command is acknowledged with a UVM_WARNING, so C never hangs.
Things to know.
• C always starts the exchange. SV cannot interrupt C through this mailbox. If SV must get C's attention on its own, use an interrupt (poke_irq) and a trap handler.
• Command 0 is reserved: ACK = 0 means "busy".
• SV clears ACK the moment it sees the CMD store, so reusing the same id for two consecutive steps is safe.
• While C spins in sv_sync() it keeps reading SV2C_ACK. That is normal bus traffic in the waveform, not a hang.

5 How a C Test Ends

Every test ends with exactly one store to tohost (0x10000). The value stored is the verdict. ibex_monitor catches the store, ibex_scoreboard decodes it, and tb_top calls $finish 100 ns later, so the final log lines get written. If tohost is never written, the base-test watchdog ends the run as a TIMEOUT.

C test doestohostLog line (tb/env/ibex_scoreboard.sv)
test_pass() · return 00x0000_0001[SB] TEST PASSED (tohost=1)
test_fail(7) · return 70xFA11_0007[SB] TEST FAILED - C test reported fail code 7 (0x0007)
illegal instruction0x0000_0002[SB] TEST FAILED - tohost=0x00000002: unexpected trap (exception cause=2) or legacy fail code
for (;;) { }—[SB] TEST FAILED - TIMEOUT: C test never wrote tohost

All four rows were checked with throwaway tests during this bring-up.

// sw/common/test_end.h
#define TOHOST_PASS       0x00000001u
#define TOHOST_FAIL_TAG   0xFA110000u   /* upper 16 bits mark a C-reported fail */

static inline void __attribute__((noreturn)) test_pass(void) {
  tohost = TOHOST_PASS;
  for (;;) { }
}

static inline void __attribute__((noreturn)) test_fail(uint32_t code) {
  tohost = TOHOST_FAIL_TAG | (code & 0xFFFFu);
  for (;;) { }
}

Returning from main() works too: crt0.S applies the same encoding to the return value. Use whichever reads better. test_fail() can be called from anywhere, including deep inside a helper function.

  # sw/crt0.S, after "call main"
  la   t0, tohost
  li   t1, 1
  beqz a0, write_tohost      # return 0      -> 1           (PASS)
  slli a0, a0, 16
  srli a0, a0, 16
  li   t1, 0xFA110000
  or   t1, t1, a0            # return code   -> 0xFA11_code (FAIL)
write_tohost:
  sw   t1, 0(t0)
Why the 0xFA11 tag? The default trap handler also writes tohost, with the raw mcause. Interrupt mcause values have bit 31 set and causes ≤ 31, and exception codes are small numbers, so none of them can look like 0xFA11_xxxx. The tag keeps "my check failed" separate from "the core trapped". Older tests that still write small raw codes (tohost = 2) are reported as "unexpected trap … or legacy fail code".
Pick a distinct fail code per check (1, 2, 3 …) or report a count, as mem_rw_basic does. Then the one-line verdict tells you which check failed without opening waves. Print the details first (printf), then call test_fail().

6 Before main() — What crt0.S Does

You can write tests without reading crt0.S. But knowing what runs before main() explains why globals, stack and traps behave the way they do.

C declarationSectionWhere it lives / who sets it
const uint32_t t[] = {…};.rodataROM. Read-only, never copied.
uint32_t g = 0xC0FFEE11;.dataRAM (from 0x10008). Value copied from its ROM image by crt0.
static uint32_t errors;.bssRAM, after .data. Zeroed by crt0.
uint32_t local; (in a function)stackRAM, below 0x30000. Not initialised: always assign before use.
*(uint32_t*)0x15000—Scratch area. Nothing puts anything here; your test owns it.

7 Write & Run Your Own Test

Template

/*
 * my_test - one line saying what this test proves.
 */
#include <stdint.h>
#include "../common/memmap.h"     /* SCRATCH_BASE, REG32()        */
#include "../common/print.h"      /* print_str, printf            */
#include "../common/test_end.h"   /* test_pass, test_fail         */
/* #include "../common/c2sv.h"       sv_sync - if SV takes part    */

int main(void) {
  print_str("my_test: start\n");

  volatile uint32_t *buf = (volatile uint32_t *)SCRATCH_BASE;
  buf[0] = 0xA5A5A5A5u;
  if (buf[0] != 0xA5A5A5A5u) {
    printf("my_test: readback %x\n", buf[0]);
    test_fail(1);
  }

  print_str("my_test: PASS\n");
  test_pass();
}

Build & run (from sim/)

source ~/.cadence_env.bash                       # xrun on PATH

make sim TEST=mem_rw_basic                       # C test + default ibex_base_test
make sim TEST=c_sv_handshake TEST_NAME=ibex_c_sv_sync_test   # C test + its SV test
make sim TEST=my_test WAVES=1 SEED=1             # waves into the run directory
make sim TEST=my_test SIM_ARGS=+TIMEOUT_NS=5000000   # longer watchdog (5 ms)
make sw  TEST=my_test                            # build only: .elf .vmem .dis .pdis

Each run creates runs/run_<date>_<time>_seed<N>/ with xrun.log, the .elf/.vmem/.dis/.pdis of the test and, with WAVES=1, waves.shm. Grep the log for C_PRINT, \[SV\] and \[SB\] to read the story of the run.

Checklist

volatileEvery pointer to memory or TB registers is volatile.
scratchAbsolute-address data stays inside 0x15000–0x15FFF.
\nEvery print ends with a newline.
one endEvery path ends in test_pass() / test_fail(n) / return, with a distinct n per check.
ids matchIf you use sv_sync: C #defines and SV localparams agree, and you ran with the right TEST_NAME.
.disWhen in doubt, read <test>.dis: it shows each C line next to the instructions it became.

8 Fixes Made Along the Way

Building this infrastructure exposed several latent problems. They are recorded here because each one is a classic bring-up trap.

ProblemRoot causeFix
Initialised globals read as 0 (int g = 5; → 0) .data was linked to run from RAM but its initial values are stored in ROM (the .vmem holds load addresses), and crt0 never copied them across. It went unnoticed because the only globals until then started at 0. Copy loop in crt0.S using _data_lma/_data_start/_data_end from link.ld. Checked by mem_rw_basic step 6.
Copy loop would end every test tohost/irq_ctrl lived in .data. Copying .data stores 0 to 0x10000, and the TB treats any tohost store as the verdict. Moved them to a .tohost (NOLOAD) section pinned at 0x10000 (with a linker ASSERT). They rely on the TB's zero-filled memory.
hello_world printed nothing uart_simple.h wrote to 0x20000, but no SV component watched that address. The bytes went silently into RAM. ibex_console + print.h on the TB I/O page. uart_simple.h removed.
Every 'r' missing from prints ("Hello fom Ibex!") SystemVerilog string literals have no \r escape, so "\r" is just the letter r. The console's "skip CR" check was dropping every 'r'. Compare against 8'h0D. Lesson: check escape sequences when moving C habits into SV.
A C test could not report its own failure Any tohost ≠ 1 was decoded as a trap mcause, so "data mismatch, code 2" was logged as "illegal instruction". A hang produced no error at all. 0xFA11 fail tag, scoreboard decode, TIMEOUT check in check_phase.

Regression after these changes: all 14 C tests (12 existing + mem_rw_basic + c_sv_handshake) pass on Xcelium 25.03. The four failure modes in §5 were each confirmed with a deliberately failing test.
