Module 0 · Orientation

Writing C tests for a RISC-V core

In this course you write small C programs that run on the Ibex RISC-V core inside a simulation. Each program checks one feature of the core and reports a verdict. The UVM testbench around the core watches the program, helps it when asked, and decides whether the test passed or failed.

By the end of this module you can

  • Set up the Cadence environment and run any test with one make command.
  • Find the three kinds of lines that matter in a log: [C_PRINT], [SV], [SB].
  • Name the 18 existing tests and say which SV test class each one needs.
Think of it like this. The Ibex core is a new employee on their first day. Your C test is the task sheet you hand them ("store this number, read it back, tell me if it matches"). The UVM testbench is the supervisor standing behind them: it hands them the memory they need, listens when they talk, pokes them with interrupts when asked, and writes the final grade.

Verification is not about proving the core works. Your job is to try hard to break it, then record that you couldn't. Every test in this course follows the same pattern: do something, check the result, report a verdict. A test that does not check anything can never fail. That makes it worthless, however green it looks.

Prerequisites

You should be comfortable with basic C (pointers, structs, loops) and have seen a UVM testbench before (test, env, agent, driver, monitor). You do not need to know RISC-V assembly. When you need it, we read the compiler's own listing (the .dis file) together.

Where the results go

Each run creates its own folder, runs/run_<date>_<time>_seed<N>/. It holds xrun.log, the test's .elf, .vmem, .dis (C source mixed with assembly) and .pdis (assembly only). With WAVES=1 it also holds waves.shm. This one-liner shows only the lines you care about from the newest run:

Knowledge check

You add a new C test sw/tests/my_test.c that only uses pointers and prints. Which command runs it?

TEST is the C file name without .c. TEST_NAME picks the SV test class, and its default ibex_base_test is fine for a test that never calls sv_sync(). make sw only builds and never simulates.

A run ends and the log has no [SB] line at all. What should you suspect first?

The scoreboard always prints exactly one verdict: PASS, a FAIL with a reason, or TIMEOUT. No [SB] line means the UVM test never ran. Look at the top of xrun.log for *E errors, or for Error 127 in the make output.

Good & bad practices

✓ Re-run failures with the same seed

When a run fails, re-run it with SEED=<the seed in the folder name> and WAVES=1.

Why: the failing run folder already records its seed. Reproducing the exact run first saves hours of "it passes for me".

✗ Judging by the make exit code

Assuming a run passed because make finished without an error.

Why it hurts: a UVM_ERROR does not always change the exit code. The only verdict is the [SB] line, so always grep for it.

✓ Run the whole regression before you commit

Run ./test.sh after touching anything shared: crt0.S, link.ld, sw/common/*, tb/*.

Why: shared code breaks other people's tests first, and you will not notice from your own test alone.

✗ Deleting the runs/ folder mid-debug

Running make clean while you still need the failing run's log and waves.

Why it hurts: make clean removes runs/ completely, and with it your only copy of the failure.

Module 1 · The testbench

Testbench architecture

Before writing tests, you need a map of what surrounds the core. This testbench is unusual: it has no sequences generating stimulus. The stimulus is the C program itself. The UVM components mostly listen to the core's data bus and react to particular addresses.

By the end of this module you can

  • Draw the testbench: tb_top, the memory model, the DUT, ibex_if and each UVM component.
  • Explain what a passive bus tap is and why the testbench uses taps instead of a sequencer.
  • Say which component reacts to a store at 0x10000, 0x10004, 0x30000 and 0x30010.
  • Read the data-bus timing of one store and one load.
Think of it like this. The core's data bus is a corridor everyone has to walk down. The memory is a room at the end of the corridor. The UVM components are security cameras on the corridor walls: each one films the corridor and only reacts when someone carries a parcel addressed to "its" door. Cameras never stop anyone. That's what passive means.

Passive taps: how every component listens

Every listening component has the same five-line heart. On each clock it samples the data bus through the mon_cb clocking block. If it sees a store to its address, it acts. Here is the monitor, the simplest one:

tb/env/ibex_monitor.svthe tohost tap
task run_phase(uvm_phase phase);
  forever begin
    @(vif.mon_cb);                                  // once per clock
    if (vif.mon_cb.data_req && vif.mon_cb.data_we &&  // a store ...
        vif.mon_cb.data_addr == 32'h00010000) begin  // ... to tohost
      ap.write(vif.mon_cb.data_wdata);              // hand value to scoreboard
    end
  end
endtask

The console (0x30000), the c2sv mailbox (0x30010/14) and the driver's irq watcher (0x10004) are the same loop with a different address and a different action.

Why a clocking block? mon_cb samples with default input #1step: the values the bus held just before the clock edge. Without it, a tap waking on @(posedge clk) could race with the DUT changing the bus in the same time step. Then it would sometimes see the old value and sometimes the new one, depending on the simulator.
tb/top/ibex_if.sv
clocking mon_cb @(posedge clk);
  default input #1step;
  input data_req, data_gnt, data_we, data_be, data_addr, data_wdata;
endclocking

Why no sequencer?

In a typical UVM testbench, a sequence makes transactions and a driver turns them into pin wiggles. Here the core creates all the bus traffic by running the program. A sequencer would have nothing to send. The "driver" here only drives reset and the interrupt pins. The interesting control flow lives in C, and SV helps only when C asks (Module 7).

The memory model in tb_top

Memory is one big byte array, mem_b, that serves both buses. Grants are immediate (zero wait states) and read data comes back exactly one clock later. That's the simplest timing Ibex accepts.

tb/top/tb_top.svdata memory, simplified
assign u_if.data_gnt = u_if.data_req;                 // grant at once

always @(posedge clk) begin
  data_rvalid_r <= u_if.data_req;                     // response 1 clk later
  if (u_if.data_req && u_if.data_we && !is_tb_io(u_if.data_addr)) begin
    if (u_if.data_be[0]) mem_b[{u_if.data_addr[31:2],2'b00}+0] = u_if.data_wdata[ 7: 0];
    if (u_if.data_be[1]) mem_b[{u_if.data_addr[31:2],2'b00}+1] = u_if.data_wdata[15: 8];
    if (u_if.data_be[2]) mem_b[{u_if.data_addr[31:2],2'b00}+2] = u_if.data_wdata[23:16];
    if (u_if.data_be[3]) mem_b[{u_if.data_addr[31:2],2'b00}+3] = u_if.data_wdata[31:24];
  end
  // loads from the TB I/O page come from SV registers, not from mem_b
  data_rdata_r <= is_tb_io(u_if.data_addr) ? read_tb_io(u_if.data_addr)
                                           : read_word(u_if.data_addr);
end

Notice !is_tb_io(...). Stores to the 0x30000 page never reach memory. The page is a set of mailboxes, not RAM, which is why C must use volatile pointers to talk to it (Module 3).

One store and one load on the data bus

Where the test ends: three cooperating pieces

  1. monitor sees the store to 0x10000 and passes the value to the scoreboard, which prints the verdict.
  2. tb_top sees the same store and calls $finish 100 ns later, so the last prints make it into the log.
  3. If no store ever comes, the base test watchdog drops its objection after timeout_ns. The scoreboard's check_phase then reports TIMEOUT.

Module 4 covers this in detail.

Check the address table above, and remember what is_tb_io() excludes from the memory write path. A load is never seen by a tap: every tap checks data_we.

  • (a) No tap reacts: 0x15000 is ordinary RAM. mem_b[0x15000..0x15003] = 07 00 00 00.
  • (b) The console adds 'A' to its line buffer. mem_b is not written, because it's the TB I/O page.
  • (c) The driver decodes bit 31 = 1 (assert) and line 1 = timer, then drives irq_timer=1. mem_b[0x10004] is also written, since 0x10004 is normal RAM that the driver merely watches.
  • (d) No tap reacts (it's a load). tb_top's read mux returns sv2c_ack.

Knowledge check

Why does the testbench have no UVM sequence generating bus traffic?

The DUT is a bus master. Stimulus for a CPU is the program it runs, so the testbench's job is to be the memory (tb_top) and to watch (taps).

A C test stores 0x55 to 0x30000, then loads 0x30000. What does it read back?

read_tb_io() returns sv2c_ack / sv2c_data for 0x30018/1C and 0 for every other word in the page. Stores to the page are never written to mem_b.

What does default input #1step in mon_cb protect you from?

Sampling at #1step means "the value just before this edge". It is deterministic whatever order the simulator schedules the DUT's and TB's processes in.

Good & bad practices

✓ Keep taps passive

A monitor-style component only reads the bus and reports through ports or prints. The component that drives a pin (the driver) is a separate one.

Why: a passive tap can be reused in any environment, even one where something else drives the bus, such as an SoC-level testbench.

✗ Sampling on raw @(posedge clk)

Writing a new tap as @(posedge vif.clk) if (vif.data_req ...) without the clocking block.

Why it hurts: it works on one simulator version and breaks on the next. These races are some of the hardest bugs to find.

✓ One address, one owner

Every TB I/O address is decoded in exactly one SV component, and documented in sw/common/memmap.h.

Why: when two components react to the same store, you get double prints or double IRQ toggles that look like DUT bugs.

✗ Hard-coding an address in a second place

Adding a new mailbox address in SV without adding it to memmap.h (or the other way round).

Why it hurts: C and SV quietly disagree. C stores into nowhere, SV waits forever, and the only symptom is a TIMEOUT.

C testbench architecture

A C test is not a normal program. There is no operating system, no libc, no printf from a library and no exit(). This module shows the small software environment that replaces all of that: how a .c file becomes bytes in mem_b, and what runs before main().

By the end of this module you can

  • Read sw/link.ld and say where code, constants, globals, the stack and the scratch area live.
  • List what sw/crt0.S does from reset to main().
  • Pick the right sw/common/ header for each job.
Think of it like this. On a PC, the operating system is a hotel. It hands your program a furnished room (stack, heap, libraries) and cleans up when you check out. On this core there is no hotel, just an empty plot. crt0.S is the builder who puts up the walls (stack pointer), moves the furniture in (.data copy) and sweeps the floor (.bss clear) before your main() moves in.

What a .vmem looks like

objcopy -O verilog writes an address line (@...) followed by bytes. $readmemh loads each byte into mem_b at that address. Here is the real start of hello_world.vmem:

@00000080
6F 00 40 18                         <- 0x80: j _start   (reset vector)
@00000100
6F 00 00 18 6F 00 C0 17 6F 00 80 17   <- 0x100: trap_vectors, 32 x "j trap_common"
...

0x6F is the RISC-V jal opcode, and j is jal x0. Every vector slot jumps to the same trap_common, so each jump's offset is 4 smaller than the one before it.

The memory map, as the linker builds it

VMA and LMA: why globals need copying An initialised global like static uint32_t g = 0xC0FFEE11; must be writable, so it lives in RAM (its run address, VMA). But the .vmem is only loaded once, at time 0, so the starting value 0xC0FFEE11 has to be stored somewhere permanent: ROM (its load address, LMA). crt0.S copies it from ROM to RAM before main(). Without that copy, g would read as 0.

Activity 2 · Where does it live?

For each object in this test, say which section it ends up in, whether it is in ROM or RAM, and who gives it its starting value:

static const uint32_t table[4] = {1, 2, 3, 4};   /* (a) */

int main(void) {
  uint32_t local = 5;                             /* (d) */
  volatile uint32_t *p = (volatile uint32_t *)0x15000; /* (e) what p points to */
  ...

const data never changes, so does it need RAM? Globals without an initialiser are zero by the C rules: who does the zeroing here? Locals live in registers or on the stack.

  • (a) .rodata, ROM. Its value comes straight from the .vmem.
  • (b) .bss, RAM. crt0.S zeroes it.
  • (c) .data, RAM (VMA). The value is stored in ROM (LMA) and copied by crt0.S.
  • (d) A register or the stack (RAM, below 0x30000). The value is set by the instructions of main each time it runs.
  • (e) Not a C object at all: the linker never places anything at 0x15000 (the scratch area). Its content is whatever was last stored there, which is 0 at time 0 because tb_top zero-fills mem_b.

Check your answers: in the .dis, the address of each symbol tells you where it landed (0x0xxxx = ROM, 0x1xxxx = RAM).

Knowledge check

Why is the .tohost section marked NOLOAD in link.ld?

If tohost were in .data or .bss, crt0's copy or zero loop would store to 0x10000 before main(). Every test would then end at boot with tohost = 0, which counts as a failure.

What is the .dis file most useful for?

When an ISR prints mepc=0x5f8, you search the .dis for 5f8: to see which C statement was interrupted. You'll do exactly this in Module 10.

A test's main() does return 3;. What ends up in tohost?

crt0.S applies the same encoding as test_fail(): 0 becomes 1 (PASS), and anything else becomes 0xFA110000 | (code & 0xFFFF).

Good & bad practices

✓ Read the .dis when in doubt

When you're not sure the compiler did what you meant, open runs/.../<test>.dis and look at the instructions under your C line.

Why: with -Os the compiler reorders and removes code. The listing is the only ground truth for what the core actually ran.

✗ Using libc functions

Calling memcpy, malloc, strlen or sprintf in a test.

Why it hurts: there is no C library (-nostdlib). The link fails, or worse, GCC turns a simple loop into a memcpy call that doesn't exist. Write the loop yourself.

✓ Keep link.ld and memmap.h in step

Any address change goes into link.ld, memmap.h and the SV that decodes it, in one commit.

Why: the ASSERTs in link.ld catch some mistakes at build time, but nothing checks C against SV automatically.

✗ Big arrays on the stack

Declaring a huge local such as uint32_t buf[30000]; inside a function.

Why it hurts: nothing checks the stack size. About 117 KB of stack grows down from 0x30000 straight through the scratch area and the globals, and corrupts them without any error. Use the scratch area or a static array instead.

Module 3 · C test basics

C pointers for memory access

Everything a C test does to the outside world is a load or a store through a pointer: checking memory, printing, ending the test, talking to SV. In this module you follow one pointer store all the way from the C line to the bytes in mem_b.

By the end of this module you can

  • Write to and read from an absolute address such as 0x15000 in C.
  • Explain exactly what volatile does, and show what goes wrong without it.
  • Predict data_be and the resulting word for 8-, 16- and 32-bit stores (little-endian).
  • Find your pointer accesses in the .dis listing.
Think of it like this. Memory is a long street of numbered houses, and each house holds one byte. A pointer is a house number written on an envelope. *p = 7 means "deliver 7 to that house". The pointer's type says how many neighbouring houses the delivery fills: uint8_t* fills one, uint16_t* two, uint32_t* four.

An absolute address in C

An address is just a number, and casting it to a pointer type lets you read and write it:

sw/tests/mem_rw_basic.cstep 1
volatile uint32_t *p = (volatile uint32_t *)0x00015000;

*p = 0x12345678u;     /* store word -> data_we=1, be=4'b1111 */
uint32_t rd = *p;     /* load word  -> data_we=0             */
if (rd != 0x12345678u) test_fail(1);

Writing that cast everywhere is noisy, so memmap.h wraps it in a macro:

sw/common/memmap.h
#define SCRATCH_BASE   0x00015000u      /* free RAM for tests, 4 KB */
#define REG32(addr)    (*(volatile uint32_t *)(addr))

REG32(SCRATCH_BASE + 0x20) = 0xA5A5A5A5u;          /* store */
uint32_t v = REG32(SCRATCH_BASE + 0x20);           /* load  */
Use the scratch area: 0x15000–0x15FFF The linker never places code, globals or the stack there, and an ASSERT in link.ld fails the build if globals ever grow into it. Writing anywhere else in RAM with an absolute pointer can corrupt your own globals or stack, and the resulting failure looks nothing like its cause.

The journey of one store

Here is the same thing as it appears in the listing. The C line is printed above the instructions the compiler generated for it. With -Os the compiler interleaves other work, so the lines don't always appear in source order:

runs/run_*/mem_rw_basic.dis
  *p = 0x12345678u;                 /* store word -> data_we=1, be=4'b1111 */
 4c2:   c080                    sw      s0,0(s1)
  uint32_t rd = *p;                 /* load word  -> data_we=0            */
 4c4:   4094                    lw      a3,0(s1)

c080 is a 16-bit compressed instruction, the C in rv32imc. It does exactly the same as a 32-bit sw.

Why volatile is not optional

The compiler assumes memory only changes when your code changes it. Under that assumption, a store followed by a load of the same address is pointless: it already knows the value. So with -Os it may delete the bus accesses entirely, and your memory test then tests nothing.

without volatile
uint32_t *p = (uint32_t *)0x15000;

The rule volatile tells the compiler: "every read and write of this location is an action with side effects: do each one, exactly as written, in order". Use it for every pointer to the scratch area, the TB I/O page, tohost, and any variable shared between main() and an interrupt handler (Module 10). All the helpers in sw/common already use it.

Good & bad practices

✓ Use named addresses

Write REG32(SCRATCH_BASE + 0x40) and keep every address in memmap.h.

Why: when the memory map moves, you change one line. A raw 0x15040 scattered through 30 tests becomes 30 silent bugs.

✗ Absolute pointers into "free-looking" RAM

Picking 0x12000 because "nothing is there".

Why it hurts: .data, .bss and the stack move whenever any test or header changes. Today's empty spot is tomorrow's global variable, and the test then corrupts itself.

✓ Verify in the .dis and the waves once

For every new kind of access, check once that the instruction you expected (sb/sh/sw/lw) is really there and really on the bus.

Why: it takes two minutes and removes a whole class of "the test checks nothing" bugs.

✗ Casting away volatile

Passing a volatile uint32_t* to a helper that takes a plain uint32_t*.

Why it hurts: inside the helper the compiler is free to optimise the accesses away again. Keep volatile on every parameter in the chain.

Module 4 · C test basics

How a C test ends

On a PC, a program ends by returning to the operating system. Here there is nothing to return to: the core would just keep fetching instructions forever. So every test ends by doing one specific thing: a single store to tohost at address 0x10000. The value of that store is the verdict.

By the end of this module you can

  • End a test with test_pass(), test_fail(code) or return, and know they are equivalent.
  • Decode any tohost value into PASS, a C fail code, or an unexpected trap.
  • Explain the four ways a run can end, and which component decides each.
  • Recognise each outcome from its [SB] line in the log.
Think of it like this. tohost is the exam answer sheet. The core may scribble on scrap paper (RAM) as much as it likes, but the moment it writes on the answer sheet, the invigilator (scoreboard) grabs it and marks it. Writing nothing at all until the clock runs out (watchdog) is also a fail.

Why the 0xFA11 tag? Without it, a test that calls test_fail(2) and a core that takes an illegal-instruction trap (mcause = 2) would both write 2, and you could not tell "my check failed" from "the core crashed". The tag ("FAIL" in hex-speak) in the upper 16 bits makes every C-reported fail unmistakable. Codes are limited to 1–0xFFFF.

The four endings

The C side

sw/common/test_end.h
#define TOHOST_PASS       0x00000001u
#define TOHOST_FAIL_TAG   0xFA110000u   /* upper 16 bits mark a C-reported fail */

static inline void __attribute__((noreturn)) test_pass(void) {
  tohost = TOHOST_PASS;
  for (;;) { }                  /* park here until tb_top calls $finish */
}

/* code: 1..0xFFFF, pick a distinct value per check so the log tells you
 * which check failed. */
static inline void __attribute__((noreturn)) test_fail(uint32_t code) {
  tohost = TOHOST_FAIL_TAG | (code & 0xFFFFu);
  for (;;) { }
}

The for (;;) matters. After the store, the core keeps running for the 100 ns before $finish. Parking it in a loop guarantees it doesn't wander into code that prints or stores something misleading. noreturn tells the compiler this function never comes back, so it doesn't need to generate code after the call.

Returning from main() gives the same result, because crt0.S applies the same encoding to the return value:

  sw   t1, 0(t0)

  j _halt

Activity 4 · Decode the verdict

A regression gives you these tohost values (or none). For each one, say what happened and what you would look at first:

(a) 0x00000001   (b) 0xFA110012   (c) 0x00000002   (d) 0x80000007   (e) no tohost store, test ran for 1 ms

Check the upper 16 bits first: are they 0xFA11? If not, and the value is not 1, it is an mcause. Bit 31 of an mcause means interrupt. Codes: 2 = illegal instruction, 7 = timer (interrupt) or store fault (exception), 11 = ecall / external.

  • (a) PASS.
  • (b) The C test called test_fail(0x12). Search the test source for test_fail(0x12) or test_fail(18), and read the [C_PRINT] lines just before.
  • (c) Illegal-instruction exception with no handler: the core executed something it could not decode. Find the PC: in waves look at mepc, or add a handler that prints mepc, then look it up in the .dis. Common causes: jumping into data, a corrupted return address, a stack overflow.
  • (d) A timer interrupt arrived and the test had no handler for it, or did not handle that cause. Someone enabled mie.MTIE + mstatus.MIE and the pin was high.
  • (e) TIMEOUT: the test hung. Usually it is waiting for a flag that never gets set (an ISR that never ran, an sv_sync with no SV handler) or stuck in a loop. Look at the last [C_PRINT], then dump waves and check the PC.

Knowledge check

A test writes tohost = 1 in the middle of main(), then carries on with more checks that would fail. What is the verdict?

tohost is write-once by design. That is why test_pass() must be the very last thing a test does, after every check.

Why does a TIMEOUT get reported in check_phase instead of in write()?

A tohost store ends the sim via $finish before check_phase runs. So check_phase is only reached when the watchdog expired, and tohost_seen is then 0.

Your test defines no trap_c_handler and executes an illegal instruction. What happens?

The weak symbol in crt0.S is linked whenever no test provides a strong one. It guarantees a crash ends the test immediately, with the cause, instead of becoming a mystery hang.

Good & bad practices

✓ A distinct fail code per check

test_fail(1), test_fail(2), ... one number per if, and print the values before failing.

Why: "fail code 4" in a nightly regression points to one line of C without re-running anything.

✗ Writing tohost directly

tohost = 2; for(;;){} scattered through the test (the old style).

Why it hurts: raw 2 is indistinguishable from mcause 2 (illegal instruction). Use test_fail() so the 0xFA11 tag is always added.

✓ test_pass() as the last line

Every check first, then the pass print, then test_pass().

Why: tohost is write-once, so anything after the pass is never checked.

✗ Raising the timeout to "fix" a TIMEOUT

Bumping +TIMEOUT_NS 10x because a test sometimes times out.

Why it hurts: a test that needs a hundred times its normal run time usually has a real hang. You've hidden the symptom and made every failing run 10x slower.

Module 5 · C test basics

Pass or fail: write-read-compare tests

Now you can access memory (Module 3) and end a test (Module 4). Put the two together and you have the most common self-checking test there is: write a known value, read it back, compare, report. The skill is choosing values and orders that would actually expose a bug.

By the end of this module you can

  • Write a reusable check() helper that logs every mismatch with address, expected and actual values.
  • Choose patterns that target specific faults: stuck bits, shorted bits, byte-lane errors, address aliasing.
  • Decide between fail-fast and collect-all-errors, and pick meaningful fail codes.
  • Prove your test can fail, and debug a real mismatch from the log.
Think of it like this. Testing memory with only 0x00000000 is like testing a piano by pressing no keys. Every key "works". Good patterns press every key, then pairs of neighbouring keys in opposite ways, then check that pressing one key doesn't sound another.

Complete the template above so that it:

Knowledge check

Why is 0xA5A5A5A5 followed by 0x5A5A5A5A a better pair than 0x0F0F0F0F / 0xF0F0F0F0 for finding shorted neighbouring data bits?

A short between bits n and n+1 only shows when they're written to different values. With 0F/F0, neighbours inside a nibble always carry the same value. (Strictly, 0xAAAAAAAA / 0x55555555 alternate every bit. A5/5A comes close and also exercises the nibble edges.)

A block test writes and immediately reads back each word, one at a time. Which bug can it never detect?

Each word is read before anything else can overwrite it, so aliasing is invisible. Fill everything first, then verify.

Your memory test reports MISMATCHes where exp ^ got = 0x00000400 at every address. What is the most likely cause?

0x400 = 1 << 10: one data bit, the same everywhere. Walking-1 would name it directly as the step bit = 10.

Good & bad practices

✓ Print address, expected and actual

Every mismatch line has all three, in hex.

Why: "test failed" sends you back to rerun with waves. "addr=0x15104 exp=0x15104 got=0x15004" tells you the bug (address bit 8) straight from the log.

✗ Expected values computed the same way as the data

Writing x = f(i), then comparing the read value against a second read rather than against f(i).

Why it hurts: comparing memory with memory checks nothing. If both reads return the same wrong value, the test passes.

✓ Break every new test once

Flip one expected value, see the FAIL, revert.

Why: it's the only proof that your check is wired up. Silent always-pass tests are one of the most common escapes in real projects.

✗ Only ever using one pattern

Testing memory with 0xDEADBEEF alone, because it "looks random".

Why it hurts: a fixed pattern drives each bit only one way. Half the stuck-at faults (any bit stuck at the value it already holds) cannot fail.

What a print costs

Each character is a function call, a store and a loop iteration: roughly 15–20 clock cycles per character here. You can measure it from real timestamps in csr_mscratch:

@  9925000: [C_PRINT]   mscratch wrote 0x00000000 read 0x00000000
@ 17385000: [C_PRINT]   mscratch wrote 0xffffffff read 0xffffffff

7.46 µs between two 44-character lines (counting the leading spaces and the \n) is 746 cycles, about 17 cycles per character, including the CSR access and the hex formatting. A short status line costs about 0.5–1 µs.

Prints change timing Adding or removing a print moves every later event in time. That is harmless for a memory test. In an interrupt test, though, a print decides where the interrupt lands: you can see it in the next section. Never put a print inside a loop whose timing you are measuring (mcycle deltas, interrupt latency).

A real gotcha: the spliced line

The first version of irq_csv_single.c asked SV for an interrupt 50 clocks in the future, then printed a line. The print takes far longer than 50 clocks, so the interrupt arrived mid-print and the ISR printed its own line. The console has one line buffer, and here is what came out:

[C_PRINT] C :ISR: mcause=0x8000000b (external), mepc=0x0000030e
[C_PRINT] ISR: mstatus=0x00001880  MIE=0 MPIE=1
[C_PRINT]  SV will raise irq_external, computing meanwhile

Main had printed "C :" when the interrupt hit. The ISR's text was appended to the same buffer, and its \n flushed both. Main's remaining characters then came out as a line of their own. The fix in the test: print before asking for the interrupt, and give it a longer delay (200 clocks).

sw/tests/irq_csv_single.cafter the fix
/* Print first: a print still running when the ISR fires would get the
 * ISR's text spliced into the middle of its line in the log. */
print_str("C : asking SV for irq_external in 200 clocks, computing meanwhile\n");
sv_irq_raise(IRQ_LINE_EXTERNAL, 200);

Practical rules

  1. End every print with \n. Text without it stays in the console's buffer and appears later, glued to the next line, or never if the test ends first.
  2. Print before the important thing, not just after it. If a test hangs, the last [C_PRINT] tells you how far it got.
  3. Prefix with who is talking. "C : ...", "ISR: ..." and "[3] ..." make interleaved logs readable, and the [SV] tag already marks SV lines.
  4. Print values in hex for addresses, data and CSRs, so they match the waves and the .dis.
  5. Keep ISR prints short, and never print in a loop that waits for an interrupt (Module 10).
Activity 6 · Predict the log

What exactly appears in the log for this code, and how many stores to 0x30000 does it make?

printf("v=%x n=%d%%", 255, -3);
print_str(" done\n");
print_str("tail");

%x always prints 0x plus 8 digits. %% prints one %. A log line only appears at \n.

[C_PRINT] v=0x000000ff n=-3% done

One line. The first printf has no \n, so it joins the next print. "tail" never appears unless a later print sends a \n. Stores: "v=0x000000ff n=-3%" is 18, " done\n" is 6, "tail" is 4, so 28 in total, even though only 24 characters made it into the log.

Knowledge check

A test prints print_str("step 3 done"); just before hanging. The log's last line is "step 2 done". Why?

The console prints at \n only. Without one, your most useful debug line (the last one) is lost exactly when you need it.

Why don't the characters you print end up in mem_b?

is_tb_io() blocks the write to mem_b. The store exists only on the bus, where the console tap sees it.

You add printf("i=%d\n", i) inside the loop of csr_counters.c. What happens?

Prints are real instructions on the real core. They count in mcycle and minstret, and change every timing-based result.

Good & bad practices

✓ A start and an end line in every test

"my_test: start" first and "my_test: PASS" before test_pass().

Why: in a regression log of 500 runs you can tell at a glance whether a test ran at all, and how far it got.

✗ Debug prints left in timing loops

Leaving a printf inside a spin loop "just for debug".

Why it hurts: it changes when interrupts land and how long loops take. The bug you were chasing may vanish, or a new one appear, only because of the print.

✓ Short, prefixed ISR prints

One line per ISR entry, starting with "ISR:".

Why: you can still read the order of events, and the ISR stays short enough that it doesn't distort what it is measuring.

✗ Using libc format specifiers

printf("%08x %lu", ...)

Why it hurts: the mini printf prints them literally and consumes no argument, so every later argument is printed against the wrong specifier.

Module 7 · C test basics

C ↔ SV communication

Some things a C program can't do on its own: wait an exact number of clocks, drive a pin on the DUT, peek at an internal signal, compute an expected value with SV's tools, or start a UVM sequence on another interface. sv_sync() lets C pause, hand control to SV, and continue with a result when SV is done.

By the end of this module you can

  • Explain the four mailbox registers and the exact order of one sv_sync() round trip.
  • Read c_sv_handshake.c and its SV partner ibex_c_sv_sync_test.sv, and predict the log.
  • Add your own command on both sides.
  • Name the rules that keep the handshake from hanging.
Think of it like this. C is a chef following a recipe; SV is the kitchen assistant. At step 4 the recipe says "ask the assistant to fetch 20 eggs, and wait". The chef writes "20" on a slip (ARG), rings the bell (CMD), and stands still watching the counter (ACK). The assistant does the job, however long it takes, puts the result on the counter (DATA) and raises the ticket with the same number (ACK = CMD). The chef sees the ticket, takes the result, and moves on to step 5. The chef is always in charge of the order.

One round trip, step by step

The C side: eight instructions

sw/common/c2sv.h
static inline uint32_t sv_sync(uint32_t cmd,
                               uint32_t arg) {
  REG32(C2SV_ARG) = arg;
  REG32(C2SV_CMD) = cmd;
  while (REG32(SV2C_ACK) != cmd) { }
  return REG32(SV2C_DATA);
}

Knowledge check

Why does the mailbox clear sv2c_ack the moment it sees a CMD store?

c_sv_handshake doesn't repeat ids, but irq_csv_multi calls sv_irq_raise (cmd 0x10) five times. Without the clear, the second call would return instantly.

You run c_sv_handshake but forget TEST_NAME=ibex_c_sv_sync_test. What happens?

The base test's default handle_c_cmd always acknowledges. It never hangs, but it does nothing, so the first real check catches it. Look for the C2SV warning in the log.

During CMD_SV_WAIT with arg = 50, what is the core doing?

The core never stops. "C is paused" means it is busy-waiting. That matters: an enabled interrupt can still be taken during the wait (Module 10).

Good & bad practices

✓ Let SV log every command it handles

Start each case branch with a `uvm_info("SV", ...) naming the step.

Why: interleaved [C_PRINT] and [SV] lines are the story of the test. Without SV lines, a hang in a handshake is invisible.

✗ Putting the flow in SV

SV deciding on its own timer when to raise pins or change things, while C guesses when it happened.

Why it hurts: the two sides drift apart as soon as C's code changes length (a new print, a different compiler flag). Keep C as the master and let SV act only when asked.

✓ Shared command header for shared commands

Commands used by many tests go in a header (like irq_csv.h) with one SV test class that implements them.

Why: one contract, one implementation. Each new test reuses it instead of re-inventing id 7.

✗ Checking results only in SV

Sending a value to SV and having SV uvm_error on a mismatch, while C carries on and passes.

Why it hurts: the verdict is split in two. Return the result to C and let C call test_fail(), or make sure the SV error really fails the run.

Module 8 · RISC-V privileged

CSR testcases

Control and Status Registers (CSRs) are the core's own configuration and status registers: interrupt enables, the trap vector address, the cause of the last trap, cycle counters. They don't live in memory. They have their own 4096-entry address space, and only special instructions can reach them. This module shows how to access CSRs from C and the four kinds of CSR test.

By the end of this module you can

  • Use read_csr, write_csr, set_csr_bits and clear_csr_bits, and name the instruction each one becomes.
  • Explain why CSR accesses never appear on the data bus.
  • Write four kinds of CSR test: plain read/write, atomic read-modify-write, WARL, and free-running counter.
  • Decode mstatus, mie and mtvec bit fields on Ibex.
Think of it like this. Memory is the warehouse out back, reached by truck (the data bus). CSRs are the switches and gauges on the dashboard, right in front of the driver. Flipping a switch doesn't send a truck anywhere, which is why a bus tap can never see a CSR access. Some switches are spring-loaded (WARL: they snap to a legal position), and some gauges move on their own (counters).

/* `reg` must be a bare CSR name token (mstatus, mie, mtvec, ...), not a
 * string or macro expansion, since it is pasted into the asm template. */
#define read_csr(reg) ({ \
  uint32_t __v; \
  asm volatile ("csrr %0, " #reg : "=r"(__v)); \
  __v; \
})

#define set_csr_bits(reg, mask) ({ \
  uint32_t __v; \
  asm volatile ("csrrs %0, " #reg ", %1" : "=r"(__v) : "r"((uint32_t)(mask))); \
  __v; \
})

C has no syntax for CSRs, so the macros use inline assembly. #reg turns the token mstatus into the string "mstatus" inside the instruction. asm volatile is the CSR equivalent of volatile pointers: it stops the compiler from removing or reordering the access.

Why "atomic" matters write_csr(mstatus, read_csr(mstatus) | MSTATUS_MIE) takes two instructions. An interrupt arriving between them could change mstatus, and your write would then overwrite that change. set_csr_bits(mstatus, MSTATUS_MIE) is one instruction, csrrs, so nothing can get in between. Use set/clear for single-bit changes.

Four kinds of CSR test

1. Plain read/write: csr_mscratch

mscratch has no side effects, so write/read-back tests the CSR instructions themselves and nothing else.

3. WARL: csr_mtvec_warl

WARL = Write Any, Read Legal. You may write any value, but the register only keeps the bits that are legal for this implementation. A WARL test writes an illegal value and checks that the read-back matches the implementation's rule, not the value written.

Knowledge check

You add a bus tap looking for mscratch writes. It never fires. Why?

0x340 is mscratch's CSR number, not a memory address. To check a CSR from SV you would probe the core's internal signals, or have C send the value over sv_sync.

Why is set_csr_bits(mstatus, MSTATUS_MIE) safer than write_csr(mstatus, read_csr(mstatus) | MSTATUS_MIE)?

The read-modify-write in C takes several instructions. A trap in between that modified mstatus would be undone by your stale write.

A colleague's WARL test writes 0x00012345 to mtvec and expects to read 0x00012345. On Ibex it fails. Who is wrong?

Good & bad practices

✓ Check "nothing else moved"

After changing one field, compare the other bits against their old value, as csr_mstatus_rmw does with & ~MSTATUS_MIE.

Why: a CSR bug often flips a neighbouring field. A test that checks only the bit it wrote misses it.

✗ Exact cycle counts as pass criteria

Why it hurts: any compiler change, extra print or pipeline option breaks the test without any real bug. Use bounds that prove the behaviour, not the exact number.

✓ Expected values from the spec and the RTL docs

Derive WARL and reset values from the Ibex documentation and the RTL, and cite the source in a comment.

Why: copying what the simulation printed into the expected value just records today's behaviour, bugs included.

✗ Leaving mtvec / mie modified

Changing a global CSR in a test and never restoring it.

Why it hurts: the next trap or interrupt goes somewhere unexpected, and the failure appears far from its cause.

Module 9 · RISC-V privileged

Traps, context save & restore

A trap is the core dropping what it is doing to run a handler, then (usually) coming back as if nothing happened. "As if nothing happened" is the hard part. Every register the interrupted code was using must be saved and restored exactly. This module shows what the hardware does, what our software (trap_common in crt0.S) does, and why each step is there.

By the end of this module you can

  • Distinguish exceptions from interrupts, and say what mepc points to for each.
  • List the five things Ibex does in hardware on trap entry, and the three that mret does.
  • Draw the 80-byte trap stack frame and explain why those registers are saved.
  • Write a trap_c_handler() that resumes correctly after an exception.
Think of it like this. You are writing a report when the phone rings. Before answering, you put a bookmark in the page (mepc), note why you stopped (mcause) and switch off notifications (MIE = 0). That is the hardware's part. Then you clear your desk into a box (save registers to the stack), take the call (C handler), put everything back exactly where it was (restore), remove the bookmark, and continue mid-sentence (mret).

What the hardware does

What software does: trap_common

The hardware saved only the PC and a few status bits. Every general-purpose register still holds the interrupted code's values, and the C handler is about to use them. trap_common saves them first:

  sw   t0, 64(sp)           #     to the stack, NOT left in the CSRs

  csrw mstatus, t0

  lw   ra,  0(sp)

  mret                      # PC = mepc, MIE = MPIE

The C handler contract

sw/common/trap.h
/* Each test defines this for the causes it cares about; a weak default
 * in crt0.S (forwards mcause to tohost, halts) covers tests that don't.
 *
 * Returns the PC execution should resume at via mret - usually just
 * `mepc` unchanged. */
uint32_t trap_c_handler(uint32_t mcause, uint32_t mepc, uint32_t mtval);
Change the resume address only through the return value write_csr(mepc, x) inside the handler does nothing useful: trap_common rewrites mepc from its stack slot right before mret. That is deliberate, because it is what makes nesting safe. The return value is stored into that slot, so returning the address is the only supported way to change where execution resumes.

Activity 9 · Read the frame

(a) An interrupt arrives while sp = 0x0002FFC0. At what addresses does trap_common store mepc and a3?
(b) A test's handler for ecall (mcause 11) returns mepc unchanged. What happens?
(c) The handler does write_csr(mepc, mepc + 4) and returns mepc. Where does execution resume?

(a) First sp -= 80, then the offsets from Figure 9.2. (b) For an exception, mepc points at the trapping instruction. (c) Look at what trap_common does with the return value and the mepc CSR after the call.

  • (a) New sp = 0x2FFC0 − 0x50 = 0x2FF70. mepc at +64 = 0x2FFB0; a3 at +44 = 0x2FF9C.
  • (b) mret jumps back to the ecall, which traps again, forever. The test hangs and TIMEOUTs (or floods the log if the handler prints). Exceptions must return mepc + 4 (or +2).
  • (c) At the original mepc. The CSR write is overwritten: trap_common stores the return value into the frame and writes the mepc CSR from the frame before mret. That's exactly why trap.h warns against it.

Knowledge check

Why does trap_common not save s0–s11?

The RISC-V ABI splits the work. The caller (here, trap_common acting for the interrupted code) saves caller-saved registers, and every C function restores the callee-saved ones it touches. Saving them again would only cost time.

Inside trap_c_handler, what is mstatus.MIE?

irq_csv_single checks exactly this. Its ISR reads mstatus=0x1880: MIE = 0, MPIE = 1, MPP = 3. Nesting happens only if the handler sets MIE itself.

Why does every slot in trap_vectors have to be exactly 4 bytes?

That's why the table is wrapped in .option norvc. With compression on, the assembler could turn j trap_common into a 2-byte c.j.

Good & bad practices

✓ Handle the causes you expect; fail on the rest

Check mcause exactly and call test_fail() with a print for anything unexpected.

Why: a handler that "returns mepc for everything" turns a real bug (say, a load fault) into a silent loop or a false pass.

✗ Changing mepc with write_csr

write_csr(mepc, mepc + 4); return mepc;

Why it hurts: it is overwritten before mret (the nesting-safe design), so the trap re-executes the faulting instruction forever.

✓ Print mcause, mepc and mtval in every handler

And look mepc up in the .dis.

Why: these three values plus the listing answer "what trapped, where, and why" without opening the waves.

✗ Writing your own save/restore per test

Adding inline assembly in a test to save a few registers "just for this ISR".

Why it hurts: trap_common already does it correctly for every test. A second, partial copy is where context-corruption bugs come from.

#define CMD_IRQ_RAISE       0x10u   /* arg = line | delay << 16  */
#define CMD_IRQ_CLEAR       0x11u   /* arg = line                */
#define CMD_IRQ_RAISE_MASK  0x12u   /* arg = bit n set -> line n */

#define IRQ_CSV_MIN_DELAY   20u     /* clocks */

static inline void sv_irq_raise(uint32_t line, uint32_t delay_clks) {
  if (delay_clks < IRQ_CSV_MIN_DELAY) delay_clks = IRQ_CSV_MIN_DELAY;
  sv_sync(CMD_IRQ_RAISE, (line & 0x1Fu) | (delay_clks << 16));
}

static inline void sv_irq_clear(uint32_t line) {
  sv_sync(CMD_IRQ_CLEAR, line & 0x1Fu);
}

/* Immediate, so only call it with interrupts globally disabled. */
static inline void sv_irq_raise_mask(uint32_t line_mask) {
  sv_sync(CMD_IRQ_RAISE_MASK, line_mask);
}

  printf("ISR: mcause=%x (%s), mepc=%x\n", mcause, mcause_name(mcause), mepc);
  printf("ISR: mstatus=%x  MIE=%d MPIE=%d\n", isr_mstatus,
         (isr_mstatus & MSTATUS_MIE) != 0, (isr_mstatus & MSTATUS_MPIE) != 0);

   * loop may have had live values in any of them; only trap_common's
   * save/restore in crt0.S protects them. */
  asm volatile ("li t0,-1; li t1,-1; li t2,-1; li t3,-1; li t4,-1; li t5,-1;"

                    "a3", "a4", "a5", "a6", "a7");

   * the same interrupt is taken again immediately. */

  set_csr_bits(mstatus, MSTATUS_MIE);

    a = b;
    b = t;

Knowledge check

An ISR forgets to call sv_irq_clear(). What happens after its mret?

Ibex's interrupt lines are level-sensitive. "Handled" only means the source stopped asking. Symptoms: endless ISR prints, then TIMEOUT.

Why must irq_count in irq_csv_single be volatile?

The compiler doesn't know an ISR exists. You can see the volatile load in the listing: lw a5,12(s3) at 0x5f4 runs on every iteration.

In irq_csv_priority, why does sv_irq_raise_mask() have no delay, while sv_irq_raise() does?

The delay exists to stop an ISR's sv_sync from overlapping main's. With interrupts globally off, there's no ISR to overlap, and the test needs all five pending before the gate opens.

In irq_csv_nested, the fast0 ISR prints mepc=0x50a. Where is that?

The .dis shows 0x50a is lw a4,12(a3) loading fast_done inside trap_c_handler (the timer ISR was inlined into it). That is exactly where nesting should happen.

Good & bad practices

✓ Check the cause exactly, and fail on surprises

Compare the full mcause (with bit 31) against the expected value, and test_fail() with a print otherwise.

Why: a spurious or wrong interrupt is a real bug. A handler that tolerates anything hides it.

✗ Waiting on a flag that isn't volatile

static int seen; while (!seen) {}

Why it hurts: the loop may compile to an endless branch that never re-reads memory. The ISR runs, sets the flag, and main never notices. You get a TIMEOUT that looks like "no interrupt".

✓ Make the interrupt land in real work

Have main compute something in registers while waiting, then verify it, as irq_csv_single does.

Why: an interrupt that only ever hits an empty spin loop never tests context save. Live registers at the moment of the trap are what expose save/restore bugs.

✗ Raising before acking, or sv_sync in overlapping places

An SV handler that drives the pin before returning, while ISRs also call sv_sync.

Why it hurts: it hangs only when the interrupt lands inside main's spin loop. That depends on timing, so it passes today and fails after an unrelated print is added.

The new-test checklist

  1. One line of intent. Write the header comment first: what feature, what check, how to run it.
  2. Copy a template (below) into sw/tests/<name>.c. Include only the headers you use.
  3. Write checks before stimulus details. Every if gets its own test_fail(N) or goes through check().
  4. Print at the start, at each step, and before PASS. End every print with \n.
  5. Need SV? Reuse an existing command set first (irq_csv.h). Otherwise add commands to a test class and register it in ibex_pkg.sv.
  6. Build only: make sw TEST=<name>. Fix warnings, and glance at the .dis for your key accesses.
  7. Run with a fixed seed: make sim TEST=<name> [TEST_NAME=...] SEED=1.
  8. Break it once on purpose. Confirm the FAIL message, then revert.
  9. Add the mapping to sim/test.sh if it needs a special TEST_NAME, then run ./test.sh: everything still passes.
  10. Commit the test, any SV change, and the test.sh line together.

Capstone · irq_mem_combo

Write sw/tests/irq_mem_combo.c, run with TEST_NAME=ibex_irq_csv_test, that does all of this:

  1. Fills 32 words at SCRATCH_BASE + 0x400 with address-as-data (Modules 3, 5).
  2. Enables fast1 and asks SV to raise it in 100 clocks (Modules 7, 8, 10).
  3. While waiting, verifies the 32 words in a loop, counting mismatches (Module 5).
  4. The ISR prints mcause and mepc, writes 0xDEAD0000 | count to SCRATCH_BASE + 0x500, clears the pin and returns (Modules 6, 9).
  5. Main keeps verifying until the ISR has run, then checks: no mismatches, ISR ran exactly once, and the word at 0x15500 is 0xDEAD0001.
  6. Prints a summary and ends with test_pass() or a distinct test_fail() per check (Module 4).

Then answer: where did mepc land (look it up in the .dis)? What happens if you remove volatile from the ISR flag?

Structure main as: fill → enable → sv_irq_raise(IRQ_LINE_FAST(1), 100) → do { verify all 32 } while (!isr_done);. Keep the verify loop's counters in locals so they're live in registers when the interrupt lands. That also exercises context save.

/*
 * irq_mem_combo - memory checks running while SV raises fast1; the ISR
 * leaves a marker in memory that main verifies afterwards.
 * Run: make sim TEST=irq_mem_combo TEST_NAME=ibex_irq_csv_test
 */
#include <stdint.h>
#include "../common/memmap.h"
#include "../common/csr.h"
#include "../common/irq_csv.h"
#include "../common/print.h"
#include "../common/trap.h"
#include "../common/test_end.h"

#define NWORDS 32
static volatile uint32_t isr_count;

uint32_t trap_c_handler(uint32_t mcause, uint32_t mepc, uint32_t mtval) {
  printf("ISR: mcause=%x (%s) mepc=%x\n", mcause, mcause_name(mcause), mepc);
  if (mcause != (MCAUSE_INT | MCAUSE_FAST(1))) {
    printf("ISR: unexpected, mtval=%x\n", mtval);
    test_fail(0xE0);
  }
  isr_count++;
  REG32(SCRATCH_BASE + 0x500) = 0xDEAD0000u | isr_count;
  sv_irq_clear(IRQ_LINE_FAST(1));
  return mepc;
}

int main(void) {
  print_str("irq_mem_combo: start\n");
  volatile uint32_t *blk = (volatile uint32_t *)(SCRATCH_BASE + 0x400);
  for (uint32_t i = 0; i < NWORDS; i++) blk[i] = (uint32_t)&blk[i];

  write_csr(mie, MIE_MFIE(1));
  set_csr_bits(mstatus, MSTATUS_MIE);
  print_str("C : fill done, asking SV for fast1, verifying meanwhile\n");
  sv_irq_raise(IRQ_LINE_FAST(1), 100);

  uint32_t errors = 0, passes = 0;
  do {
    for (uint32_t i = 0; i < NWORDS; i++)
      if (blk[i] != (uint32_t)&blk[i]) errors++;
    passes++;
  } while (isr_count == 0);
  clear_csr_bits(mstatus, MSTATUS_MIE);

  uint32_t marker = REG32(SCRATCH_BASE + 0x500);
  printf("C : %d verify passes, %d errors, marker=%x\n", passes, errors, marker);
  if (errors)                   test_fail(1);
  if (isr_count != 1)           test_fail(2);
  if (marker != 0xDEAD0001u)    test_fail(3);

  print_str("irq_mem_combo: PASS\n");
  test_pass();
}

mepc lands somewhere inside the verify loop: search the .dis for the address it printed. Without volatile on isr_count, the compiler may hoist the read out of the do/while, so the loop never ends and the test TIMEOUTs even though the ISR ran and printed.

Final check

Your new test TIMEOUTs. The last line is [C_PRINT] C : waiting for fast1, and the log shows [SV] irq fast1 -> 1 but no ISR print. What do you check first?

Pin high, no trap: one of the other two AND inputs is 0 (Figure 10.1). Read mie_q and mstatus_q in waves, or print read_csr(mie) before waiting. A typical cause is write_csr(mie, ...) with the wrong macro, such as MIE_MFIE(0) instead of MIE_MFIE(1).

Which change to a C test is least likely to change any other test's result?

Every test links the shared headers, crt0.S and link.ld, so changes there need a full ./test.sh. A new test file only affects itself.

Good & bad practices

✓ Debug from the log first, waves second

Read the last prints, the [SB] reason and the .dis before opening SimVision.

Why: a well-printed test usually tells you the answer in under a minute. Waves are for confirming, not for searching.

✗ "It passed once" as done

Committing after one green run.

Why it hurts: you haven't proven the test can fail, or that it didn't break others. Break it once, then run ./test.sh.

✓ Small, single-purpose tests

One feature per test, with a name that says what it is (irq_csv_priority, not test7).

Why: when a nightly regression shows one red line, the test name alone should point you at the feature.

✗ Copy-pasting checks without the fail codes

Cloning a test and leaving every test_fail(1) as is.

Why it hurts: "fail code 1" now means five different things. Renumber every check.
