MODULE 1

What is an SoC?

Learning objectives

  • Describe what a System-on-Chip is and why the industry moved to it.
  • Identify the major building blocks of a typical SoC.
  • Understand the role each block plays and how they relate to each other.
  • See where a verification engineer's work fits into the picture.
Analogy — a city. An SoC is like a small city built onto a single piece of silicon. The CPUs are the workers, the memories are warehouses, the peripherals are the shops and ports that connect to the outside world, and the interconnect is the road network that lets everyone move goods around. A city with brilliant workers but no roads does nothing. The same is true of a chip.

From boards to chips

Twenty-five years ago, a "system" meant a printed circuit board with separate chips: a processor here, a memory chip there, a USB controller in the corner, all wired together with copper traces. It worked, but it was big, slow, power-hungry, and expensive.

A System-on-Chip (SoC) takes all of those separate chips and integrates them onto a single piece of silicon. Your phone's main chip contains CPUs, a GPU, memory controllers, camera pipelines, modems, security blocks, and dozens of smaller controllers — all on one die a few millimetres across.

The payoff is enormous: shorter wires mean faster communication and lower power; integration means lower cost and smaller size. The cost is complexity. A modern SoC can contain tens of billions of transistors, and verifying that they all work together is one of the hardest problems in engineering — which is why your job exists.

Initiator vs target. A block that starts a transaction (issues a read or write request) is an initiator — older docs say "master." A block that responds to requests is a target — older docs say "slave." Arm's current terminology is Manager and Subordinate. You'll see all three vocabularies in real projects; they mean the same pair of roles. This course uses manager/subordinate, noting master/slave where the signal names still use them.

Where verification fits

Every one of these blocks is designed by an RTL team and verified by a DV team. But integrating them is a separate, enormous verification problem: does the CPU's view of memory match what the memory controller actually stores? Does a DMA transfer corrupt data when the GPU is hammering the same bus? These are system-level questions, and they all flow through the interconnect — which is why understanding the interconnect (and its protocols, AXI and CHI) is the spine of this whole course series.

The life of a single transaction

To make the abstract concrete, follow one ordinary event — a CPU reading a 64-bit value from DRAM — across the whole chip. Almost every SoC concept appears somewhere in this journey:

  1. The CPU core executes a load instruction. The address misses in its L1 and L2 caches, so the request leaves the core as a bus transaction.
  2. The request enters the interconnect, carrying an address, a size, an ID, and attributes (is it cacheable? secure?).
  3. The interconnect's decoder inspects the address and routes the request toward the DRAM region (Module 3).
  4. If the path crosses a clock-domain or width boundary, the interconnect converts it (Module 2 & 5).
  5. The memory controller receives the request and translates it into DRAM commands (activate, read), obeying the timing rules of the DRAM standard.
  6. DRAM returns the data; the memory controller hands it back to the interconnect, which routes it to the requesting core using the transaction's ID.
  7. The core fills its cache line and completes the load. The instruction retires.

A verification engineer must ask, at every arrow in that chain: what if the step is slow? what if two requests collide here? what if reset hits mid-flight? what if the address was one byte off? Each question is a test. The interconnect is where most of those questions live, which is why it dominates SoC verification.

How an SoC is built — and verified — end to end

An SoC is not written in one sitting; it flows through a pipeline of teams and stages. Knowing where you sit in it tells you what your tests are responsible for.

The economic logic that drives the whole discipline: the cost of a bug rises by roughly an order of magnitude at each stage it escapes. A bug caught in a block-level simulation costs an engineer an afternoon. The same bug found after tape-out can mean a respin — re-fabricating the chip — costing months and millions. This asymmetry is why companies spend more effort on verification than on design itself, and why "shift left" (catch it as early as possible) is the field's mantra.

Activity — classify the blocks

You are handed the block list for a new automotive SoC: a quad-core CPU cluster, an LPDDR5 controller, a CAN-FD controller, an image signal processor (ISP) for the camera, and a boot ROM. For each, decide whether it is primarily an initiator, a target, or both.

Ask one question per block: "Does this block start bus transactions, respond to them, or both?" A block that processes incoming camera data and writes results to memory is doing both — it responds to configuration writes and initiates data writes.
  • CPU cluster — initiator. It issues all the reads/writes to run software.
  • LPDDR5 controller — target. It responds to memory accesses.
  • CAN-FD controller — both. The CPU configures it (so it's a target for those writes), and it DMAs received frames into memory (so it's an initiator too).
  • ISP — both. Configured as a target; writes processed frames as an initiator.
  • Boot ROM — target. The CPU reads boot code from it; it never initiates.
The lesson: "initiator vs target" is a per-interface role, not a fixed property of a block. Many blocks have one of each.

Why did the industry move from multi-chip boards to Systems-on-Chip?

Shorter on-chip wires are faster and lower-power than board traces, and integration cuts cost and size. The trade-off is a steep rise in verification complexity — SoCs are harder to verify, not easier, and they need a more capable interconnect than ever.

MODULE 2

The Interconnect — the Heart of the SoC

Learning objectives

  • Explain why every SoC needs an interconnect rather than point-to-point wiring.
  • Describe the manager/subordinate model and arbitration.
  • Distinguish a crossbar from a shared bus from a network-on-chip (NoC).
  • Understand why interconnect verification is uniquely hard.
Analogy — the road network. If every building in a city had a private dedicated road to every other building, you'd pave the whole city. Instead, cities share roads and use traffic rules and intersections. The interconnect is the SoC's shared road network: shared wires, arbitration (traffic lights), and routing (signposts) so that N managers can reach M subordinates without N×M dedicated links.

Why not just wire blocks together?

Imagine 8 managers each needing to reach 12 subordinates. Point-to-point would need up to 96 separate bus connections, each with its own wires across the chip. That's impossible to route, impossible to time, and impossible to verify. The interconnect solves this by being a shared, managed fabric.

The interconnect has three core jobs:

  • Routing — look at a transaction's address and send it to the right subordinate.
  • Arbitration — when two managers want the same subordinate at once, decide who goes first.
  • Protocol conversion — bridge between a fast AXI manager and a slow APB peripheral, or between different data widths and clock domains.

Three interconnect topologies

TopologyHow it worksBest forProtocol
Shared busOne transaction at a time on shared wiresSmall, low-traffic subsystemsAHB, APB
CrossbarDedicated switched paths; many transfers in parallelA handful of high-bandwidth managersAXI
Network-on-ChipPackets routed hop-by-hop through routersMany-core, large SoCsCHI (and AXI carried over NoC)

Inside the interconnect

"The interconnect" sounds like one block, but it's really a collection of cooperating pieces. Knowing them by name makes interconnect bugs far easier to localise.

ComponentWhat it doesWhat can go wrong

Arbitration — deciding who goes first

When two managers want the same subordinate in the same cycle, the arbiter must choose. The scheme matters for both performance and fairness:

  • Fixed priority — manager 0 always beats manager 1. Simple, but the loser can starve (never get through) if the winner is always busy.
  • Round-robin — take turns. Fair, prevents starvation, slightly more logic.
  • QoS-weighted — honour the transaction's priority field (AXI's AxQOS), giving latency-critical traffic (like a display refresh) precedence over bulk traffic.

For a verification engineer, arbitration is a goldmine of corner cases: prove no manager starves under sustained contention, prove priority is actually honoured, and prove the arbiter never deadlocks when every manager and subordinate applies back-pressure at once.

Deadlock — the interconnect's nightmare. A deadlock is a cycle of dependencies where everyone waits forever: manager A holds a buffer slot and waits for B's resource; B holds a slot and waits for A's. Nothing moves. Deadlocks don't corrupt data — they hang the chip — so they slip past data-checking and must be hunted with dedicated stress (fill every buffer, back-pressure every channel) and simulation timeouts.

Why interconnect verification is hard

The interconnect is where everything interacts. A bug in a UART affects the UART. A bug in the interconnect can corrupt any transaction from any manager to any subordinate. The verification challenge is combinatorial: every manager × every subordinate × every transaction type × every concurrency scenario × every ordering case. You cannot test all of it directly, which is why constrained-random stimulus and protocol assertions (covered later) are essential.

A useful way to size the problem: a modest fabric with 8 managers, 12 subordinates, 3 transaction types and even a handful of concurrency states already has hundreds of thousands of meaningful combinations — and that's before bursts, IDs, errors, and reset interactions multiply it further. This is precisely why the field leans on coverage-driven constrained-random verification: you let a constrained generator explore the space automatically and measure (via functional coverage) which combinations you've actually hit, rather than trying to hand-write a directed test for each.

Activity — pick a topology

A new SoC has: 2 CPU clusters, 1 GPU, 1 NPU, 4 memory controllers, and ~30 slow peripherals (timers, GPIO, UARTs). Sketch what topology you would use for (a) the compute-to-memory paths and (b) the peripherals, and say why.

The compute-to-memory paths are few in number but extremely high bandwidth — they need parallelism. The 30 peripherals are numerous but each is tiny and slow. Does it make sense to give each peripheral a full high-bandwidth port?

(a) Compute-to-memory: a high-bandwidth crossbar or NoC carrying AXI/CHI. These paths carry the bulk of the chip's traffic and must run in parallel, so they justify the area cost.

(b) Peripherals: put all 30 behind a single APB bridge hanging off the main fabric. The peripherals are slow and infrequently accessed, so they share one low-cost path. Spending crossbar area on a GPIO block would be wasteful.

This "fast fabric + slow bridge" split is the single most common SoC interconnect pattern you'll see.

A crossbar's main advantage over a shared bus is:

A crossbar provides concurrent paths, so M0→S0 and M1→S1 can transfer at the same time. The cost is more wires and silicon area — the opposite of "fewer wires." It still decodes addresses to route, and it is not inherently lower power.

MODULE 3

Memory Map & Address Decoding

Learning objectives

  • Define a memory map and explain why it is the contract of an SoC.
  • Trace how an address turns into a routing decision.
  • Understand decode errors and why they matter for verification.
  • Read a simple memory map table and spot overlaps and holes.
Analogy — postal addresses. Every subordinate in the SoC lives at a range of addresses, just like every house has a street address. When a manager issues a transaction, it writes the destination address on the "envelope." The interconnect is the postal sorting office: it reads the address and routes the envelope to the right house. If the address belongs to no house, the letter comes back stamped "no such address" — that's a decode error.

The memory map

A memory map assigns every subordinate a unique, non-overlapping range in a single global address space. It is the master contract of the SoC: software, RTL, and verification all rely on it being exactly right. A one-bit error in a memory map can make an entire chip unbootable.

RegionBase addressSizeTarget
Boot ROM0x0000_000064 KBROM
On-chip SRAM0x0001_0000256 KBSRAM
Peripherals (APB)0x4000_000016 MBAPB bridge
DRAM0x8000_00002 GBMemory controller

How an address becomes a route

When a transaction arrives, the interconnect's decoder compares the address against each region. The comparison is usually just looking at the upper address bits. For the map above, address bit patterns select the target:

// Illustrative address decode — combinational logic in the interconnect
always_comb begin
  sel = NONE;                              // default: no target selected
  if (addr[31:16] == 16'h0000) sel = ROM;      // 0x0000_0000 .. 0x0000_FFFF
  else if (addr[31:16] inside {[16'h0001:16'h0004]}) sel = SRAM;
  else if (addr[31:24] == 8'h40) sel = APB;
  else if (addr[31]    == 1'b1)   sel = DRAM;     // 0x8000_0000 and up
  else sel = DECODE_ERROR;                // address belongs to no region
end

What this builds in hardware: a small block of comparators and priority logic. Its output selects which subordinate port the transaction is forwarded to. If nothing matches, it raises a decode error, and the interconnect returns an error response to the manager rather than hanging.

Two classic memory-map bugs: an overlap (two regions claim the same address — the decoder's behaviour becomes ambiguous) and a hole (an address that should be valid falls outside every region — accesses get decode errors). Both are prime targets for verification.

Decode errors and the verification angle

A correct interconnect must never hang on an unmapped access. It must return a clean error response (in AXI, a DECERR) so the manager can recover. A common system bug: an access to a hole causes the bus to lock up because no subordinate responds and the interconnect forgot to generate the error itself. Your tests must deliberately poke unmapped addresses to prove the chip survives.

Address interleaving (striping)

A high-performance SoC rarely sends all DRAM traffic to one memory controller — that controller would become a bottleneck. Instead the address space is interleaved (striped) across several controllers: consecutive cache-line-sized chunks of the address space are handed to different controllers in rotation. A linear sweep through memory then spreads evenly across all of them, multiplying bandwidth.

// 4-way interleave on bits [8:7] (256-byte granularity, 4 channels)
always_comb mc_select = addr[8:7];   // 0,1,2,3 → MC0..MC3
// addr 0x..000 → MC0, 0x..080 → MC1, 0x..100 → MC2, 0x..180 → MC3, 0x..200 → MC0 ...

Verification angle: interleaving means a single logical region now maps to several physical targets depending on address bits. Your reference model must reproduce the exact interleave function, and your coverage must confirm every channel is exercised — a decode bug that sends two stripes to the same controller silently halves bandwidth and may corrupt data under contention.

More than one view of memory

The map is not always the same for everyone. Modern SoCs expose different views of the address space depending on the requester's privilege:

  • Secure vs Non-secure (TrustZone). A secure region (keys, secure boot code) must be invisible to non-secure accesses. The AxPROT attribute carries the security level, and the decode + a protection unit together decide whether the access is even allowed to reach the target.
  • Virtual vs physical. Software sees virtual addresses; an MMU/SMMU translates them to physical addresses before they hit the memory map. The interconnect decodes physical addresses.
  • Per-master maps. Some fabrics give different managers slightly different views (e.g. a DSP that can't see the secure region at all).
Security is a "must-never-happen" property. A non-secure access reaching a secure region is not a performance bug — it's a security breach. These properties are verified with assertions (prove the illegal access is always blocked), not merely with coverage (which only shows a case was hit). This mindset carries straight into the AXI course's treatment of AxPROT and NSAID.

Alignment and access size

The map also constrains how a region may be accessed. A 32-bit control register typically must be accessed as an aligned 4-byte word; a byte write to it may be illegal and return an error. Memory regions are usually flexible (any size, any alignment, via byte strobes), while peripheral registers are strict. Tests must probe each region with legal and illegal sizes/alignments and confirm the response matches the spec.

Activity — find the bug in this map

Review this fragment and identify the problem:

SRAM      : 0x0001_0000  size 256 KB   // ends at 0x0004_FFFF
TIMER     : 0x0004_0000  size 4 KB      // ???
DRAM      : 0x8000_0000  size 2 GB
Compute the end address of the SRAM region (base + size − 1) and compare it to the TIMER base address. Do the two ranges share any addresses?

Overlap. SRAM spans 0x0001_0000 to 0x0004_FFFF (256 KB). The TIMER is placed at 0x0004_0000 — which is inside the SRAM range. An access to 0x0004_0000 is ambiguous: depending on decoder priority it goes to SRAM or TIMER, and the behaviour may differ between RTL, software, and your reference model. This is exactly the kind of bug a memory-map consistency check (often auto-generated from a single source-of-truth spec) is designed to catch before tape-out.

A manager accesses an address that falls in a "hole" (no region). What should a correct interconnect do?

An unmapped access must produce a clean error response (DECERR in AXI), never a hang or a silent drop. Hanging the bus on a stray access is a severe system bug — and a deliberate verification target.

MODULE 4

The AMBA Family Landscape

Learning objectives

  • Place APB, AHB, AXI, ACE, and CHI on a single capability spectrum.
  • Choose the right protocol for a given block.
  • Understand why higher-performance protocols are more complex to verify.
  • See how this course series maps onto the family (AXI deep-dive, then CHI).
Analogy — modes of transport. APB is a bicycle: simple, cheap, slow, perfect for short local trips (configuring a timer). AXI is a multi-lane highway: many vehicles flowing in parallel at speed. CHI is a national logistics network with tracking, coordination between warehouses, and guaranteed consistency of inventory across the whole country. You pick the transport that matches the journey.

AMBA — Arm's interconnect standard

AMBA (Advanced Microcontroller Bus Architecture) is the family of interconnect protocols defined by Arm and used across most of the industry. The members differ mainly in performance and the problems they solve.

ProtocolFull nameKey ideaTypical use
APBAdvanced Peripheral BusDead-simple, low-power, single transfer at a timeRegister config, slow peripherals
AHBAdvanced High-performance BusPipelined single shared channelOlder designs, simple memory access
AXIAdvanced eXtensible Interface5 independent channels, bursts, out-of-order via IDsHigh-bandwidth memory and accelerators
ACEAXI Coherency ExtensionsAXI + hardware cache coherency (snoops)Multi-core CPU clusters
CHICoherent Hub InterfacePacket/flit-based, scalable coherent fabricLarge many-core SoCs, server-class

The performance-vs-complexity trade

Each step up the family buys performance but costs verification effort. APB has perhaps a dozen protocol rules. AXI has hundreds, because five channels operating independently with out-of-order completion creates an enormous space of legal behaviours. CHI is harder still, because coherency means the correctness of one cache's data depends on what every other cache is doing. The verification cost grows faster than the performance — which is exactly why protocol expertise is so valued.

The whole-system view: a single SoC uses several of these at once. CPU clusters talk CHI or ACE among themselves, the cluster presents AXI to the rest of the chip, high-bandwidth blocks use AXI, and a sea of slow peripherals sit behind an APB bridge. Bridges convert between them.

One SoC, many protocols — a walkthrough

Trace a real path to see how the family members coexist. Suppose software running on a CPU writes a configuration register inside a UART:

  1. The CPU cores keep their caches coherent over CHI (or ACE) inside the cluster.
  2. The cluster presents a single AXI manager port to the rest of the SoC.
  3. The write travels the main AXI fabric and is decoded toward the peripheral aperture.
  4. An AXI-to-APB bridge converts the burst-capable, out-of-order AXI transaction into a simple, single-transfer APB access the UART understands.
  5. The UART accepts the write on APB and returns a ready; the bridge translates that back into an AXI B response that propagates all the way to the core.

So one register write touches three protocols. The boundaries between them — the bridges — are where a surprising share of system bugs live, because each conversion can drop information.

What a bridge must get right (and what to verify)

Conversion concernWhat can go wrong
Burst → single transfersAn AXI burst must be split into several APB accesses; a bridge that mishandles the last beat drops data.
Out-of-order → in-orderAPB has no IDs and is strictly ordered; the bridge must serialise AXI's out-of-order traffic correctly.
Width mismatchA wide AXI write to a narrow APB register needs correct byte-lane selection via strobes.
Response mappingAn APB error (PSLVERR) must become the right AXI response (SLVERR), not get lost.
Attribute lossSecurity/cacheability attributes may have no APB equivalent — the bridge must enforce them, not silently drop them.

Verifying a bridge means driving the full richness of the upstream protocol (bursts, IDs, errors, odd sizes) and checking that the downstream behaviour and the returned responses are exactly correct — a perfect motivation for the deep AXI knowledge in the next course.

Activity — match protocol to block

For each block, name the most appropriate AMBA protocol: (1) a GPIO controller, (2) a high-bandwidth GPU reading textures from DRAM, (3) a cluster of 16 coherent CPU cores in a server SoC, (4) a dual-core cluster that must keep its two L1 caches consistent with each other.

Ask: does it need bandwidth? does it need cache coherency? does it need to scale to very many nodes? GPIO needs none of these. The 16-core server case is the scalability extreme.
  • (1) GPIO → APB. Slow, simple, configured occasionally.
  • (2) GPU ↔ DRAM → AXI. Needs high bandwidth and bursts, but no coherency with CPUs in the simplest case.
  • (3) 16 coherent cores, server → CHI. Scalability and coherency at large node counts is exactly CHI's purpose.
  • (4) Dual-core, keep two caches consistent → ACE. Coherency at small scale; ACE extends AXI with snoops without going full CHI.

Why does verification effort grow as you move from APB → AXI → CHI?

The explosion comes from concurrency (AXI's independent channels and out-of-order completion) and coherency (CHI's cross-cache correctness). More legal states and interactions mean exponentially more scenarios to verify — not raw wire count or clock speed.

MODULE 5

Clocks, Reset, and Power Domains

Learning objectives

  • Understand why an SoC has many clock domains, not one.
  • Explain clock domain crossing (CDC) and why it is dangerous.
  • Describe reset domains and the ordering problem.
  • Understand power domains and why blocks get switched off.
Analogy — time zones. A global company has offices in different time zones. When the New York office hands a document to the Tokyo office, you can't just assume it arrives "now" — you need a careful handoff that accounts for the time difference, or messages get garbled. Clock domains are the SoC's time zones, and CDC is the careful handoff.

Why many clocks?

Different blocks want different speeds. A CPU wants 3 GHz; a UART wants a few MHz; DRAM has its own clock derived from the memory standard. Running everything at one clock would waste power (slow blocks clocked too fast) and be impossible to time (fast blocks dragged down). So an SoC has dozens of clock domains, each its own region of synchronous logic.

Clock domain crossing (CDC)

When a signal travels from one clock domain to another, it can be sampled right as it changes, landing the receiving flop in a half-way "metastable" state — neither 0 nor 1. If that uncertain value propagates, the chip behaves randomly. The fix is a synchronizer (typically two back-to-back flops) that gives metastability time to settle.

Interconnect connection: the interconnect frequently bridges clock domains — a fast AXI manager talking to a slower subordinate. AXI fabrics include clock-crossing components, and verifying that transactions survive the crossing intact is part of interconnect verification.

Reset domains

An SoC doesn't reset all at once. Different blocks have different reset signals released in a careful sequence — for example, the clocks and power must be stable before logic comes out of reset, and a CPU must not start fetching until the memory it boots from is ready. Getting reset ordering wrong is a classic cause of chips that "sometimes don't boot."

Power domains

To save energy, an SoC switches off blocks that aren't in use — the GPU sleeps when you're not gaming. These regions are power domains. Crossing from an always-on domain into a powered-off one needs isolation cells (to stop floating values corrupting the live domain) and state-retention flops (to remember settings while asleep). This is the realm of UPF/CPF power-intent verification.

Reset sequencing in detail

"Release reset" is really a choreography. A typical power-on sequence:

  1. Power rails stabilise; the power-management controller confirms voltages are good.
  2. Clocks start and PLLs lock (reach a stable frequency) — logic must stay in reset until then.
  3. Reset is released to the always-on domain and the boot infrastructure first.
  4. The boot ROM and the memory it needs come out of reset before the CPU that will fetch from them.
  5. The CPU is released last and begins fetching boot code.

Get the order wrong and the chip "sometimes" fails to boot. Two reset styles matter: asynchronous assertion (reset takes effect immediately, regardless of clock) with synchronous deassertion (release is aligned to a clock edge to avoid a metastable release). Verifying reset means asserting it at every phase — including in the middle of active transactions — and proving the design comes back to a clean, known state every time.

Reset-in-the-middle is a favourite bug hunt. Assert reset while a burst is mid-flight, while a FIFO is half full, while a CDC synchroniser is resolving. A robust design drains or cleanly drops in-flight work and re-initialises; a fragile one leaves a buffer pointer corrupted and fails on the next transaction.

Power states and the UPF intent

Each power domain moves through defined states. The hardware that makes this safe — isolation cells, level shifters, retention flops, power switches — is described in a UPF (Unified Power Format) file, separate from the RTL, and verified as its own concern (power-aware simulation).

StatePowerLogic / contentsSpecial cells needed
ONFullRunning normally—
RetentionLow (just enough)Clock off, but flop state preservedRetention flops
OFFNoneState lost; outputs would floatIsolation cells clamp outputs
  • Isolation cells clamp the outputs of an off domain to a safe value so a live neighbour doesn't read a floating X.
  • Level shifters bridge domains running at different voltages.
  • Retention flops hold critical state on a tiny always-on supply so a block can resume instantly instead of cold-booting.

Verification angle: power-aware simulation injects the real power sequencing and checks that isolation is enabled before power-down and disabled after power-up, that retained state survives a sleep/wake cycle, and that no X escapes an off domain. This connects directly to AXI5's wake-up signaling (AWAKEUP) covered later — the protocol-level handshake that lets the bus wake a sleeping block without losing transactions.

Activity — diagnose the intermittent boot

A chip boots correctly 95% of the time but occasionally hangs at power-on. Power and clocks look fine on the scope. List two SoC-level mechanisms from this module that could cause an intermittent (not every time) failure, and why intermittency is the clue.

"Intermittent" almost always means a timing race — something that depends on the exact alignment of two independent events. Which two mechanisms in this module are fundamentally about the relative timing of independent things?

1. A CDC bug. Metastability is probabilistic — it only causes a failure when a capture edge happens to land in the tiny metastability window. That naturally produces a "fails 5% of the time" signature.

2. A reset-sequencing race. If two reset deassertions race and the order isn't guaranteed, the boot succeeds whenever they happen to land in the lucky order and fails otherwise.

The lesson: intermittent failures point to timing/ordering races, which is why CDC and reset verification use dedicated static tools rather than relying on simulation to "happen to" hit the bad case.

What is the purpose of a two-flop synchronizer on a CDC path?

The first flop may go metastable; the second flop samples it one cycle later, by which time the value has almost certainly resolved to a clean 0 or 1. It does not speed up, level-shift, or reset anything — it buys settling time.

MODULE 6

Verifying an SoC

Learning objectives

  • Distinguish block-level, subsystem-level, and full-chip verification.
  • Understand where protocol VIP (verification IP) fits in.
  • Adopt the verification mindset for an interconnect-centric system.
  • See the bridge into the AXI and CHI courses that follow.
Analogy — testing a car. You test the engine on a bench (block level). You test the engine + transmission + wheels as a drivetrain (subsystem level). Then you drive the whole car on a test track (full-chip). Each level catches different bugs — a part can be perfect on the bench and still fail when integrated.

The three levels of verification

LevelWhat's the DUTCatches
BlockA single IP (e.g. the DMA, or the interconnect itself)Functional bugs inside one block; protocol compliance on its ports
SubsystemA few blocks wired together (e.g. CPU + interconnect + memory)Integration bugs — wrong connections, mismatched parameters, ordering between blocks
Full-chipThe entire SoC running firmwareSystem scenarios, boot, software/hardware mismatch, performance under real traffic

Verification IP (VIP)

You rarely verify an AXI block against a hand-written model. Instead you use VIP: a pre-built, protocol-compliant agent that can act as an AXI manager (driving stimulus), an AXI subordinate (responding), a monitor (checking every transaction against the spec), and a coverage collector. Commercial VIP (from Synopsys, Cadence, Siemens) embeds hundreds of protocol assertions so you don't have to re-derive the rulebook. Understanding the protocol — what the next two courses teach — is what lets you configure and trust that VIP.

The mindset (carry this into the AXI and CHI courses): your job is not to prove the design works — it's to try your hardest to break it and document that you couldn't. For an interconnect, "breaking it" means concurrent traffic, out-of-order completions, unmapped addresses, back-pressure on every channel, and reset in the middle of a burst. The protocol rules tell you exactly which corners exist.

The verification engines — and when to use each

"Verification" isn't one tool. Different engines trade speed for visibility and capacity, and a real project uses all of them:

EngineWhat it isStrengthLimit
SimulationRTL run in a software simulator with a UVM testbench.Full visibility, easy debug, constrained-random + coverage.Slow — can't boot a full OS in reasonable time.
FormalMathematically proves properties hold for all inputs.Exhaustive — no test case can be "missed."Doesn't scale to whole SoCs; best on well-bounded blocks (arbiters, FIFOs, protocol rules).
EmulationRTL mapped onto special-purpose hardware.Millions of times faster than sim; can boot software.Expensive; less visibility than simulation.
FPGA prototypeRTL on an FPGA board.Near-real-time; great for software bring-up.Long build times; hard to debug internal signals.

A common division of labour: formal proves the interconnect's arbiter never deadlocks and protocol rules always hold; simulation runs constrained-random traffic with scoreboards and coverage; emulation/FPGA boots real firmware to catch system-level and software-visible bugs. Each catches a class the others miss.

The test pyramid and coverage closure

Most verification effort lives at the bottom of a pyramid: a large number of fast, focused block-level tests; fewer subsystem tests; a small number of slow, expensive full-chip/firmware tests at the top. Pushing effort down the pyramid is the practical form of "shift left."

How do you know when you're done? Not when tests pass — tests passing only means the bugs you happened to exercise weren't triggered. Completion is measured by coverage closure:

  • Code coverage — did simulation exercise every line, branch, and toggle of the RTL? A necessary floor, but it only tells you what ran.
  • Functional coverage — did you hit every scenario in the test plan (every burst type, every error, every interesting cross of conditions)? This tells you what was actually verified.
  • Assertion coverage — did your protocol assertions actually get exercised (not just never fire because the condition never occurred)?

A design "signs off" when functional coverage reaches its target with all tests passing and all assertions exercised. The deep AXI and CHI courses build exactly these coverage models for their protocols.

The trap of green. 100% code coverage with weak checks proves almost nothing — you ran the code but never confirmed it produced the right answer. Coverage measures exercise; scoreboards and assertions measure correctness. You need both, and the most dangerous project state is a wall of green dashboards hiding a scoreboard that isn't really checking anything.

Activity — choose the right level

You've found a bug: under heavy traffic, a DMA write to DRAM occasionally returns the wrong data when the GPU is also writing nearby. At which verification level would you ideally have caught this, and what stimulus would have exposed it?

The bug only appears when two initiators contend for the same target. Can a single-block testbench, with only one DUT and VIP on its ports, create contention between two real initiators? What's the smallest scope that contains both the DMA path and the GPU path through the interconnect?

Subsystem level — the smallest scope that contains both initiators, the interconnect, and the shared DRAM target. A pure block-level interconnect testbench could also catch it if its VIP managers are configured to generate concurrent, overlapping-address traffic with full back-pressure and out-of-order completion.

The exposing stimulus: two managers issuing writes to nearby addresses concurrently, with randomized ready-delays on the write and response channels to shake out ordering/merging bugs. Relying on full-chip firmware to stumble onto this is far too late and far too slow — which is the whole argument for protocol-driven constrained-random testing at the lowest level that contains the bug.

What does a protocol VIP monitor primarily do?

A monitor passively watches the bus and checks compliance — every handshake, every ordering rule, every response code — and reports violations. It's the embodiment of "assertions are your safety net." It doesn't drive clocks or skip checks.

Good & Bad Practices

✓ Good practice

Catch each bug at the lowest verification level that can contain it — block, then subsystem, then full-chip.

Why: a bug found at block level costs minutes; the same bug found in full-chip firmware costs days of triage across many interacting blocks.

✗ Common mistake

Relying on full-chip firmware tests to stumble onto interconnect corner cases.

Why it hurts: firmware exercises only typical traffic and runs slowly; out-of-order, back-pressure, and unmapped-address corners almost never arise by chance.

✓ Good practice

Use protocol VIP with bundled assertions and a coverage model rather than hand-rolling checks for a standard protocol.

Why: commercial VIP encodes hundreds of protocol rules already verified across the industry — re-deriving them by hand is slow and error-prone.

✗ Common mistake

Treating "all my directed tests pass" as "the SoC is verified."

Why it hurts: directed tests only check what you thought of. Coverage-driven constrained-random is what exercises the scenarios you didn't anticipate — which is where silicon bugs hide.
