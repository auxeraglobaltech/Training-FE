01

Why assertions catch bugs RTL simulation misses

Module 1 · ~2.5 min · Hook
Outcome: Understand the exact gap that SVA fills — and why protocol checkers built without assertions tend to fail silently on corner-case violations.

Imagine a 5-stage pipeline. At cycle 100 of your sim, a response arrives on a bus with no matching request. The transaction silently corrupts a register. Your testbench $display never fires — nothing looks wrong. Three weeks later, tape-out readiness review. A static timing tool flags an impossible state. That violation was seeded at cycle 100.

This is the gap SVA closes. Assertions are always-on monitors embedded in or bound to your DUT. They sample the design at every clock edge and immediately flag protocol deviations — while you still have a waveform to debug.

Two types of assertions
Immediate
Point-in-time check
Lives inside a procedural block. Evaluates a Boolean expression right now. Equivalent to if (!expr) $error() but wired into the simulator assertion framework.
Concurrent
Multi-cycle protocol check
Evaluated only at clock edges using sampled values. Can span dozens of cycles. This is where SVA's real power lives — protocol sequences, handshakes, timing windows.
immediate vs concurrent
// Immediate — inside always block, checks right now
always @(posedge clk)
  assert (a && b) else $error("a and b must both be high");

// Concurrent — clock-driven, sampled values, multi-cycle capable
// The keyword 'property' marks it as concurrent
c_assert: assert property(@(posedge clk) not(a && b));
Key takeaway: Use immediate assertions for sanity checks inside testbench tasks. Use concurrent assertions for any multi-cycle protocol behaviour in the DUT — handshakes, acknowledge latency, bus arbitration, FSM transitions.
02

SVA building blocks — sequence, property, assert

Module 2 · ~10 min · Core concept + examples
Outcome: Construct a complete concurrent assertion from scratch using the three-layer SVA architecture. Apply timing delays, implication operators, and sequence reuse.
The three-layer architecture
Boolean → Sequence
Events over time
A sequence is a named Boolean timeline. The ##N operator says "N clock cycles later." Sequences can be parameterised and reused.
Sequence → Property
Logical rule
A property wraps sequences using implication (|-> / |=>), not, disable iff. The clock lives here for clean reuse.
Property → Assert
Activation
assert property(p) activates the check in simulation. Without this line, the property is defined but completely silent.
full 3-layer example
// Goal: req must be followed by ack within 2 cycles

sequence seq_req_ack;
  req ##[1:2] ack;    // ack arrives 1 OR 2 cycles after req
endsequence

property p_req_ack;
  @(posedge clk) req |-> ##[1:2] ack;
endproperty

chk_req_ack: assert property(p_req_ack)
  else $error("ACK not received within 2 cycles of REQ");
The ## timing operator
SyntaxMeaning
a ##2 bb must be high exactly 2 cycles after a
a ##[1:4] bb must be high somewhere in cycles 1–4 after a
a ##[0:4] bb high same cycle as a, or within 4 cycles (overlapping window)
a ##[1:$] bb will eventually be high — unbounded eventuality operator
Implication operators

Implication makes assertions conditional: only evaluate the consequent if the antecedent matched. Without implication, the checker fires at every clock edge — thousands of false failures on idle cycles.

OperatorNameConsequent startsExample
|-> Overlapped Same clock cycle as antecedent a |-> b — a high ⟹ b high same cycle
|=> Non-overlapped Next clock cycle after antecedent a |=> b — a high ⟹ b high next cycle
implication examples
// Overlapped: grant arrives in same cycle as request
property p_same_cycle;
  @(posedge clk) req |-> grant;
endproperty

// Non-overlapped: read_data valid one cycle after read_en
property p_read_latency;
  @(posedge clk) read_en |=> data_valid;
endproperty

// Fixed delay on consequent: b high 2 cycles after a
property p_fixed;
  @(posedge clk) a |-> ##2 b;
endproperty

// Sequence antecedent: addr_phase complete before data_phase
sequence s_addr;
  (addr_valid && addr_ready) ##1 !addr_valid;
endsequence
property p_axi_addr;
  @(posedge clk) s_addr |-> ##[1:4] data_valid;
endproperty
Best practice: Define clocks in the property, not in the sequence. Clock-free sequences can be reused across different clock domains — the property binds them to a clock at assertion time.
Key takeaway: Every concurrent SVA follows Boolean → sequence → property → assert property. Implication is the gating mechanism that keeps assertions silent when the trigger condition is absent.
03

Repetition operators, built-in methods & signal sampling

Module 3 · ~9 min · Core concept + examples
Outcome: Express burst patterns with repetition, detect signal transitions with $rose/$fell/$stable, look back in time with $past, and use system functions for one-hot and unknown checks.
Repetition operators — three flavours
[*n]
Consecutive
Signal high for exactly n back-to-back cycles. b[*3] = b high cycles 1, 2, 3 consecutively.
[->n]
Go-to
Signal high n times, not necessarily consecutive. Last repetition must immediately precede the next element.
[=n]
Non-consecutive
Like go-to but last repetition does NOT need to immediately precede the next element. Sequence continues freely after.
repetition examples
// Consecutive: burst of exactly 3 data beats
property p_burst3;
  @(posedge clk) burst_start |-> ##1 data_valid[*3];
endproperty

// Go-to: ack fires exactly 3 times, then done goes high
property p_ack3;
  @(posedge clk) start |-> ##1 ack[->3] ##1 done;
endproperty

// Consecutive range: between 2 and 4 valid beats
property p_burst_range;
  @(posedge clk) burst_start |-> ##1 data_valid[*2:4];
endproperty
Built-in sampling methods
$rose(sig)
True if LSB changed to 1. Detects rising edge inside a sequence without sensitivity list complexity.
$fell(sig)
True if LSB changed to 0. Detects falling edge — useful for frame-end or de-assertion checks.
$stable(sig)
True if signal value did not change. Check data stability during a hold period.
$past(sig, N)
Returns value of sig N clock cycles ago. Check cause-before-effect: was req high 2 cycles before ack?
$rose, $fell, $stable, $past examples
// $rose: no irq for 2 cycles after rising edge of enable
property p_irq_guard;
  @(posedge clk) $rose(enable) |-> ##[1:2] !irq;
endproperty

// $past: if ack is high now, req must have been high 2 cycles ago
property p_ack_preceded;
  @(posedge clk) ack |-> ($past(req,2) == 1);
endproperty

// $past with clock gating: only check if 'c' was active
property p_gated;
  @(posedge clk) ack |-> ($past(req,2,c) == 1);
endproperty

// $stable: data must not change while valid is asserted
property p_data_stable;
  @(posedge clk) (valid && !ready) |-> $stable(data);
endproperty
System functions — structural monitors
$onehot, $isunknown, $countones
// One-hot FSM: exactly one state bit high at all times
a_onehot:  assert property(@(posedge clk) $onehot(state));

// Zero one-hot: zero or one bit high (includes idle = 0)
a_onehot0: assert property(@(posedge clk) $onehot0(arb_grant));

// No X/Z on critical data bus
a_no_x:    assert property(@(posedge clk) !$isunknown(data_bus));

// At least 2 bits set — redundancy / voting check
a_redund:  assert property(@(posedge clk) $countones(vote_bus) >= 2);
Key takeaway: Use [*n] for burst enforcement, [->n] for counted non-consecutive events, $rose/$fell for edge-triggered rules, $past for cause-before-effect, and $onehot/$isunknown as always-on structural monitors.

Advanced constructs + hands-on exercise

Module 4 · ~8 min · Apply + bridge
Outcome: Write a complete assertion suite for a simplified AHB-lite bus using disable iff, .ended, and a variable delay workaround. Walk away with a reusable template.
disable iff — resettable assertions

Real designs have resets. Without disable iff, your assertion suite generates a flood of spurious failures during the reset sequence — noise that buries real bugs.

disable iff
// Checker silenced whenever reset is asserted — clean reset handling
property p_no_spurious;
  @(posedge clk)
  disable iff (reset)
  req |-> ##1 ack[->3] ##1 done;
endproperty
chk: assert property(p_no_spurious);
.ended — synchronising sequence endpoints

When two sequences must align at their endpoints rather than their start points, attach .ended to the sequence name. The property checks that both sequences finish with a specified inter-sequence delay.

.ended construct
sequence s_cmd;
  (cmd_valid && cmd_ready) ##1 !cmd_valid;
endsequence

sequence s_resp;
  resp_valid ##[1:3] resp_ready;
endsequence

// Response must END exactly 2 cycles after command sequence ends
property p_cmd_resp_align;
  @(posedge clk) s_cmd.ended |-> ##2 s_resp.ended;
endproperty
Variable delay — the workaround pattern
Common pitfall: a ##cfg_delay b causes a compile-time error — SVA delay values must be elaboration-time constants. Use the sequence pattern below for configurable delays driven by DUT parameters or testbench variables.
variable delay workaround
// Reusable variable-delay sequence — works like a countdown loop
sequence delay_seq(v_delay);
  int delay;
  (1, delay=v_delay) ##0
  first_match((1, delay=delay-1) [*0:$] ##0 delay <= 0);
endsequence

int cfg_latency;  // set by testbench, e.g. cfg_latency = 4

property p_configurable_latency;
  @(posedge clk)
  disable iff (reset)
  req |-> delay_seq(cfg_latency) |-> ack;
endproperty
chk_lat: assert property(p_configurable_latency);
Hands-on exercise — AHB-lite assertion suite
✏️

Write 4 assertions for an AHB-lite simplified bus

⏱ ~6 min
Signals: clk, hresetn (active-low), htrans[1:0], hready, hrdata[31:0], hresp
  1. When htrans == 2'b10 (NONSEQ transfer), hready must go high within 1 to 4 cycles. Use overlapped implication and a timing window.
  2. If hresp == 1 (ERROR response), hready must be low on the same cycle. Use overlapped implication.
  3. After reset de-assertion ($rose(hresetn)), hrdata must not contain X or Z for the next 2 cycles. Use $isunknown.
  4. Wrap assertion 1 in a disable iff so it is silent while !hresetn.
Reference answer
AHB-lite assertion suite
// 1 + 4: NONSEQ → hready within 1-4 cycles, reset-safe
property p_hready_window;
  @(posedge clk)
  disable iff (!hresetn)
  (htrans == 2'b10) |-> ##[1:4] hready;
endproperty
chk1: assert property(p_hready_window);

// 2: ERROR response → hready low same cycle (overlapped)
property p_err_no_ready;
  @(posedge clk)
  disable iff (!hresetn)
  hresp |-> !hready;
endproperty
chk2: assert property(p_err_no_ready);

// 3: Post-reset hrdata must not contain X/Z for 2 cycles
property p_no_x_post_reset;
  @(posedge clk)
  $rose(hresetn) |-> ##1 (!$isunknown(hrdata))[*2];
endproperty
chk3: assert property(p_no_x_post_reset);

05

APB Protocol Assertions

Module 5 · ~10 min · Protocol-specific examples
Outcome: Write a complete SVA checker for the AMBA APB3/APB4 protocol — covering setup phase, access phase, wait states, error response, and signal stability rules.
APB signal overview
Master → Slave
Request signals
PSEL selects the slave. PENABLE qualifies the access phase. PWRITE indicates direction. PADDR carries address. PWDATA carries write data.
Slave → Master
Response signals
PREADY extends the access phase (wait states). PRDATA carries read data. PSLVERR signals a transfer error (APB4).
Two-phase handshake
Setup → Access
Phase 1 (Setup): PSEL=1, PENABLE=0. Phase 2 (Access): PSEL=1, PENABLE=1. Transfer completes when PREADY=1 in access phase.
Core APB assertions — setup and access phase sequencing
APB phase sequencing
// ── Rule 1: PENABLE must follow PSEL by exactly 1 cycle (setup phase = 1 cycle)
property p_apb_setup_phase;
  @(posedge PCLK)
  disable iff (!PRESETn)
  ($rose(PSEL)) |-> ##1 PENABLE;
endproperty
apb_setup: assert property(p_apb_setup_phase)
  else $error("APB: PENABLE must assert exactly 1 cycle after PSEL");

// ── Rule 2: PENABLE must not assert without PSEL being high
property p_apb_penable_requires_psel;
  @(posedge PCLK)
  disable iff (!PRESETn)
  PENABLE |-> PSEL;
endproperty
apb_penable_psel: assert property(p_apb_penable_requires_psel)
  else $error("APB: PENABLE high without PSEL — protocol violation");

// ── Rule 3: Transfer completes when PREADY=1 in access phase
//           PSEL and PENABLE must deassert the cycle after PREADY
property p_apb_transfer_end;
  @(posedge PCLK)
  disable iff (!PRESETn)
  (PSEL && PENABLE && PREADY) |-> ##1 !PENABLE;
endproperty
apb_xfer_end: assert property(p_apb_transfer_end)
  else $error("APB: PENABLE must deassert the cycle after PREADY");
APB signal stability assertions
During the access phase (while PSEL=1, PENABLE=1, PREADY=0), all master-driven signals must remain stable — address, write data, and write-enable must not glitch mid-transfer.
APB signal stability during wait states
// ── Rule 4: PADDR stable during entire access phase (wait states)
property p_apb_addr_stable;
  @(posedge PCLK)
  disable iff (!PRESETn)
  (PSEL && PENABLE && !PREADY) |-> $stable(PADDR);
endproperty
apb_addr_stable: assert property(p_apb_addr_stable)
  else $error("APB: PADDR must not change during access phase wait states");

// ── Rule 5: PWDATA stable during write access phase
property p_apb_wdata_stable;
  @(posedge PCLK)
  disable iff (!PRESETn)
  (PSEL && PENABLE && PWRITE && !PREADY) |-> $stable(PWDATA);
endproperty
apb_wdata_stable: assert property(p_apb_wdata_stable)
  else $error("APB: PWDATA must not change during write access phase");

// ── Rule 6: PWRITE stable for entire transfer duration
property p_apb_pwrite_stable;
  @(posedge PCLK)
  disable iff (!PRESETn)
  (PSEL && !PREADY) |-> $stable(PWRITE);
endproperty
apb_pwrite_stable: assert property(p_apb_pwrite_stable);
APB4 error response and read data validity
APB4 PSLVERR and PRDATA
// ── Rule 7: PSLVERR only valid when PREADY is high (APB4)
property p_apb_slverr_requires_pready;
  @(posedge PCLK)
  disable iff (!PRESETn)
  PSLVERR |-> (PSEL && PENABLE && PREADY);
endproperty
apb_slverr: assert property(p_apb_slverr_requires_pready)
  else $error("APB4: PSLVERR must only assert when PREADY is high");

// ── Rule 8: PRDATA must be valid (no X/Z) on read transfer completion
property p_apb_rdata_valid;
  @(posedge PCLK)
  disable iff (!PRESETn)
  (PSEL && PENABLE && !PWRITE && PREADY && !PSLVERR)
  |-> !$isunknown(PRDATA);
endproperty
apb_rdata_valid: assert property(p_apb_rdata_valid)
  else $error("APB: PRDATA contains X/Z on read completion");

// ── Rule 9: No X/Z on PADDR or PSEL during active transfer
assert property(@(posedge PCLK) disable iff(!PRESETn)
  PSEL |-> !$isunknown(PADDR));

// ── Rule 10: Max wait-state limit — PREADY must assert within N cycles
//            Catches a slave that hangs and never responds
property p_apb_max_wait;
  @(posedge PCLK)
  disable iff (!PRESETn)
  (PSEL && PENABLE && !PREADY) |-> ##[1:16] PREADY;
endproperty
apb_max_wait: assert property(p_apb_max_wait)
  else $error("APB: slave held PREADY low for more than 16 cycles");
Reset behaviour
APB reset state checks
// ── Rule 11: PSEL and PENABLE must both be low during reset
property p_apb_reset_state;
  @(posedge PCLK)
  !PRESETn |-> (!PSEL && !PENABLE);
endproperty
apb_reset: assert property(p_apb_reset_state)
  else $error("APB: PSEL/PENABLE must be deasserted during reset");

// ── Rule 12: First transfer setup only starts after reset deasserts
property p_apb_post_reset_idle;
  @(posedge PCLK)
  $rose(PRESETn) |-> ##1 !PENABLE;
endproperty
apb_post_reset: assert property(p_apb_post_reset_idle);
Key takeaway: APB assertions break into four groups — phase sequencing (PSEL→PENABLE ordering), signal stability during wait states, APB4 error/data validity, and reset state correctness. Always pair disable iff (!PRESETn) on all checks except the reset state assertion itself.
06

AXI4 Protocol Assertions

Module 6 · ~12 min · Protocol-specific examples
Outcome: Write SVA checkers for AXI4 Write Address, Write Data, Write Response, Read Address, and Read Data channels — covering valid/ready handshake stability, ordering rules, ID matching, and burst constraints.
AXI4 channel overview
Write path
AW · W · B channels
Write Address (AW): AWVALID/AWREADY, AWID, AWLEN, AWBURST. Write Data (W): WVALID/WREADY, WDATA, WSTRB, WLAST. Write Response (B): BVALID/BREADY, BID, BRESP.
Read path
AR · R channels
Read Address (AR): ARVALID/ARREADY, ARID, ARLEN, ARBURST. Read Data (R): RVALID/RREADY, RDATA, RID, RLAST, RRESP.
Handshake rule
valid/ready protocol
Transfer occurs when both VALID and READY are high on the same rising clock edge. Once VALID asserts, it must stay high and the payload must stay stable until handshake completes.
Fundamental AXI handshake rule — valid stability
This is the most important AXI rule: once a source asserts VALID, it must not deassert VALID until the handshake completes (READY goes high). This applies to all five channels identically.
AXI valid stability — applies to all 5 channels
// ── VALID must stay high once asserted until READY handshake
// ── Template: replicate for AWVALID, WVALID, BVALID, ARVALID, RVALID

property p_axi_awvalid_stable;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (AWVALID && !AWREADY) |-> ##1 AWVALID;
endproperty
axi_awvalid_stable: assert property(p_axi_awvalid_stable)
  else $error("AXI: AWVALID deasserted before AWREADY — protocol violation");

// ── Write data WDATA/WSTRB must stay stable while WVALID && !WREADY
property p_axi_wdata_stable;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (WVALID && !WREADY) |-> ($stable(WDATA) && $stable(WSTRB));
endproperty
axi_wdata_stable: assert property(p_axi_wdata_stable)
  else $error("AXI: WDATA/WSTRB changed while WVALID waiting for WREADY");

// ── AWADDR must not change while AWVALID and waiting for AWREADY
property p_axi_awaddr_stable;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (AWVALID && !AWREADY) |-> $stable(AWADDR);
endproperty
axi_awaddr_stable: assert property(p_axi_awaddr_stable);
Write channel — WLAST and burst count
AXI write data channel — WLAST rules
// ── WLAST must assert on the last beat of a write burst
// ── After WLAST handshake, WVALID must deassert (no extra beats)
property p_axi_wlast_deassert;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (WVALID && WREADY && WLAST) |-> ##1 !WVALID;
endproperty
axi_wlast: assert property(p_axi_wlast_deassert)
  else $error("AXI: WVALID must deassert cycle after WLAST handshake");

// ── WSTRB must not be all-zero during a valid write beat
// ── All zeros means no bytes written — likely a master bug
property p_axi_wstrb_nonzero;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (WVALID && WREADY) |-> (WSTRB != 0);
endproperty
axi_wstrb: assert property(p_axi_wstrb_nonzero)
  else $warning("AXI: WSTRB all-zero on write beat — no bytes enabled");

// ── Write response channel: BRESP must not be X/Z
property p_axi_bresp_valid;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (BVALID && BREADY) |-> !$isunknown(BRESP);
endproperty
axi_bresp: assert property(p_axi_bresp_valid);
Read channel assertions
AXI read address and read data channels
// ── ARVALID stability: once asserted, hold until ARREADY
property p_axi_arvalid_stable;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (ARVALID && !ARREADY) |-> ##1 ARVALID;
endproperty
axi_arvalid: assert property(p_axi_arvalid_stable);

// ── RDATA must not be X/Z on a valid read data beat
property p_axi_rdata_valid;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (RVALID && RREADY && RRESP == 2'b00) |-> !$isunknown(RDATA);
endproperty
axi_rdata: assert property(p_axi_rdata_valid)
  else $error("AXI: RDATA contains X/Z on OKAY read beat");

// ── RLAST must assert on the last read data beat
// ── After RLAST, RVALID must deassert (slave must not send extra beats)
property p_axi_rlast_deassert;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (RVALID && RREADY && RLAST) |-> ##1 !RVALID;
endproperty
axi_rlast: assert property(p_axi_rlast_deassert)
  else $error("AXI: RVALID must deassert cycle after RLAST handshake");

// ── RRESP must be valid (no X/Z) when RVALID is asserted
property p_axi_rresp_valid;
  @(posedge ACLK)
  disable iff (!ARESETn)
  RVALID |-> !$isunknown(RRESP);
endproperty
axi_rresp: assert property(p_axi_rresp_valid);
Reset state — all VALID signals must be deasserted
AXI reset state assertions
// ── During reset: master-side VALID signals must all be low
property p_axi_master_reset;
  @(posedge ACLK)
  !ARESETn |-> (!AWVALID && !WVALID && !ARVALID);
endproperty
axi_reset_master: assert property(p_axi_master_reset)
  else $error("AXI: master VALID signals must be 0 during reset");

// ── During reset: slave-side VALID signals must all be low
property p_axi_slave_reset;
  @(posedge ACLK)
  !ARESETn |-> (!BVALID && !RVALID);
endproperty
axi_reset_slave: assert property(p_axi_slave_reset)
  else $error("AXI: slave VALID signals must be 0 during reset");
AXI4-Lite — simplified subset assertions
AXI4-Lite drops burst support. Burst length is always 1, so WLAST is always tied high. These additional assertions validate the lite constraints.
AXI4-Lite specific checks
// ── AXI4-Lite: AWLEN must always be 0 (single-beat only)
property p_axilite_awlen_zero;
  @(posedge ACLK)
  disable iff (!ARESETn)
  AWVALID |-> (AWLEN == 8'h00);
endproperty
axilite_awlen: assert property(p_axilite_awlen_zero)
  else $error("AXI4-Lite: AWLEN must be 0 — bursts not supported");

// ── AXI4-Lite: WLAST must always be high with WVALID
property p_axilite_wlast_always;
  @(posedge ACLK)
  disable iff (!ARESETn)
  WVALID |-> WLAST;
endproperty
axilite_wlast: assert property(p_axilite_wlast_always);

// ── AXI4-Lite: BRESP must be OKAY(00) or SLVERR(10) — no EXOKAY or DECERR
property p_axilite_bresp;
  @(posedge ACLK)
  disable iff (!ARESETn)
  (BVALID && BREADY) |-> (BRESP == 2'b00 || BRESP == 2'b10);
endproperty
axilite_bresp: assert property(p_axilite_bresp)
  else $error("AXI4-Lite: BRESP illegal — only OKAY or SLVERR allowed");
Key takeaway: AXI assertions divide by channel. The universal rule — VALID must not deassert before READY — is the most critical and applies identically to all five channels. Layer on top: payload stability checks, LAST signal rules, X/Z guards, and reset state requirements. Use the AXI4-Lite extras when AWLEN/ARLEN must be zero.

Binding SVA to your DUT from the Testbench

Module 7 · ~8 min · Testbench integration
Outcome: Attach assertion modules non-intrusively to any DUT using the bind construct — without modifying RTL source. Understand the four bind forms, hierarchical access, interface-based binding, and UVM integration patterns.
Why use bind instead of embedding assertions in RTL?
Problem with RTL embedding
Modifies production code
Assertions inside the RTL module get synthesised unless carefully guarded. Any mistake contaminates the golden design and requires RTL sign-off re-approval.
Bind advantage
Zero RTL changes
The bind construct instantiates a checker module inside the target scope at elaboration time — the DUT source is never touched. Synthesis tools ignore bound modules by default.
Scope access
Full signal visibility
The bound module sees all signals of the target scope — including internal nets, registers, and sub-module outputs — exactly as if the checker were written inside the RTL module itself.
Form 1 — bind to a module type (all instances)
Binding to a module type applies the checker to every instance of that module in the design hierarchy. Use this for protocol checkers that must cover all slave instances of a common interface.
bind to module type
// Step 1: Define the checker module — ports match DUT signal names
module apb_checker (
  input logic PCLK, PRESETn,
  input logic PSEL, PENABLE, PWRITE, PREADY, PSLVERR,
  input logic [31:0] PADDR, PWDATA, PRDATA
);
  // All your SVA properties live here
  property p_setup_phase;
    @(posedge PCLK) disable iff(!PRESETn)
    $rose(PSEL) |-> ##1 PENABLE;
  endproperty
  chk_setup: assert property(p_setup_phase);
  // ... more assertions ...
endmodule

// Step 2: bind to every instance of 'apb_slave' in the design
// Port connections use .checker_port(dut_signal) syntax
bind apb_slave apb_checker u_apb_chk (
  .PCLK    (PCLK),

  .PRDATA  (PRDATA)

Form 3 — bind using an interface
When your DUT connects via a SystemVerilog interface, the checker can accept the interface directly — cleaner than listing every individual signal port by port. The checker accesses all signals through the virtual interface handle.
bind with interface port
// Interface definition (shared between DUT and checker)
interface axi4_if (
  input logic ACLK,
  input logic ARESETn
);
  logic        AWVALID, AWREADY;
  logic [31:0] AWADDR;
  logic [7:0]  AWLEN;
  logic        WVALID, WREADY, WLAST;
  logic [63:0] WDATA;
  logic [7:0]  WSTRB;
  logic        BVALID, BREADY;
  logic [1:0]  BRESP;
  // ... AR and R channel signals ...
endinterface

// Checker module takes the interface directly
module axi4_checker (axi4_if axi);
  property p_awvalid_stable;
    @(posedge axi.ACLK) disable iff(!axi.ARESETn)
    (axi.AWVALID && !axi.AWREADY) |-> ##1 axi.AWVALID;
  endproperty
  chk: assert property(p_awvalid_stable);
endmodule

// Bind — pass the interface handle directly
bind axi4_master axi4_checker u_axi_chk (.axi(m_axi_port));
Form 4 — bind inside a UVM testbench
In a UVM environment, the bind statement lives in the top-level testbench module — not inside a class. The virtual interface is then passed into the UVM hierarchy through the config DB so the checker can also report through the UVM reporting mechanism if desired.
bind in UVM top-level testbench
// tb_top.sv — static elaboration context, UVM test runs inside
module tb_top;
  import uvm_pkg::*;

  // DUT instantiation
  axi4_master dut (
    .ACLK    (clk),
    .ARESETn (resetn),
    .m_axi   (axi_bus)
  );

  // ── bind the checker non-intrusively ──────────────────────
  bind axi4_master axi4_checker u_axi_chk (
    .ACLK    (ACLK),
    .ARESETn (ARESETn),
    .AWVALID (AWVALID),
    .AWREADY (AWREADY),
    .AWADDR  (AWADDR),
    .AWLEN   (AWLEN),
    .WVALID  (WVALID),
    .WREADY  (WREADY),
    .WDATA   (WDATA),
    .WSTRB   (WSTRB),
    .WLAST   (WLAST),
    .BVALID  (BVALID),
    .BREADY  (BREADY),
    .BRESP   (BRESP)
  );

  // Pass virtual interface into UVM config DB for monitor/scoreboard
  initial begin
    uvm_config_db #(virtual axi4_if)::set(
      null, "uvm_test_top.*", "axi_vif", axi_bus);
    run_test();
  end
endmodule
Accessing internal DUT signals through bind
One of the most powerful features of bind is that the checker has full access to internal DUT signals — FIFOs, FSM state registers, pipeline stage signals — without those ever appearing on the DUT's port list. The bound module lives in the target scope.
accessing internal signals via bind
// DUT module has internal signal 'state_reg' — not on port list
module axi_slave_checker (
  input logic        ACLK, ARESETn,
  input logic [2:0]  state_reg,    // internal FSM state — visible via bind
  input logic        AWVALID, AWREADY,
  input logic [31:0] AWADDR
);
  // Check that FSM never enters illegal state 3'b111
  property p_no_illegal_state;
    @(posedge ACLK) disable iff(!ARESETn)
    state_reg != 3'b111;
  endproperty
  chk_state: assert property(p_no_illegal_state)
    else $error("FSM entered illegal state 7");
endmodule

// In bind: 'state_reg' maps to DUT's internal net directly
bind axi_slave axi_slave_checker u_slv_chk (
  .ACLK      (ACLK),
  .ARESETn   (ARESETn),
  .state_reg (state_reg),   // internal DUT net — no RTL change needed
  .AWVALID   (AWVALID),
  .AWREADY   (AWREADY),
  .AWADDR    (AWADDR)
);
Where does the bind statement go?
Recommended
Separate bind file
Create apb_bind.sv or axi_bind.sv. Add it to the filelist only for simulation, not synthesis. This keeps the RTL filelist completely clean.
Alternative
tb_top module
Place inside the top-level testbench module at the same level as DUT instantiation. Works well for UVM environments. Must be in module context — not inside a class or task.
Never here
Inside UVM classes
bind is a static elaboration construct. It cannot appear inside class, function, task, or initial blocks. It must be at module scope.
Simulation filelist setup
filelist.f — sim only, not in synth filelist
// RTL files (shared with synthesis)
+incdir+./rtl
./rtl/apb_slave.sv
./rtl/axi_master.sv

// Verification only — excluded from synthesis filelist
./tb/tb_top.sv
./tb/sva/apb_checker.sv     // checker module definition
./tb/sva/axi4_checker.sv    // checker module definition
./tb/sva/apb_bind.sv        // bind statement for APB
./tb/sva/axi4_bind.sv       // bind statement for AXI4

// Simulator compile command (VCS example)
// vcs -sverilog -f filelist.f -assert enable_diag ...
Key takeaway: Use bind to keep assertion code 100% separate from RTL. Four forms: module-type (all instances), specific instance (hierarchy path), interface-port, and UVM top-level. The bound module lives in the target scope and sees all internal signals. Always put bind statements in dedicated _bind.sv files excluded from the synthesis filelist.
