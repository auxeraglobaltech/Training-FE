1 · Introduction & Scope

Vortex is an open-source RISC-V GPGPU: a SIMT (single-instruction, multiple-thread) processor that executes standard RV32IMF code extended with a small set of warp/thread-control instructions. Upstream it is verified with a Verilator/C++ harness (sim/rtlsim). This project instead brings a single Vortex core up under Cadence Xcelium and drives it from a native SystemVerilog UVM environment — no C++ harness, no DPI in the RTL build.

The driving surface is upstream's own sim/rtlsim/rtlsim_shim.sv: a thin wrapper around the Vortex top that exposes flat, per-bank memory ports, a DCR (device-configuration-register) write port, and a start/busy control pair — exactly the contract the C++ harness's processor.cpp uses, replicated here in SV/UVM.

Vendored RTL under RTL/vortex/hw, sim/, etc. is kept pristine at the pinned commit (see SOURCE.md). All verification work lives under RTL/vortex/dv/; the few files needing Xcelium fixes are shadow copies in dv/shim/. Companion documents: Verification Plan and Test-Case Catalog.

2 · Architecture

Vortex is hierarchical: Vortex (top) → clusters → sockets → cores. Our configuration collapses this to one of each. A core contains the SIMT front-end (warp scheduler, fetch, decode), the issue stage (scoreboard, operand collect), execution units (ALU, LSU, FPU, SFU), and per-core L1 instruction/data caches. The single core's L1 misses flow through the (pass-through at this size) L2/L3 levels to the external memory ports that our testbench serves.

3 · SIMT Execution Model

Execution is organized as warps of threads in lock-step:

  • A thread is one SIMT lane: its own register file view, its own memory lane in the LSU.
  • A warp is a group of NUM_THREADS (= 4) threads sharing one PC. All active threads of a warp execute the same instruction each cycle.
  • The core holds NUM_WARPS (= 4) warps; the warp scheduler picks a ready warp each cycle, hiding memory latency by switching warps.
  • Divergence on a branch is handled with a thread mask + IPDOM stack: threads that take different paths are masked off and re-converged later. Software can also manipulate the mask directly with tmc.

At boot only warp 0, thread 0 is active. Software widens execution explicitly: tmc activates more threads of the current warp, wspawn launches additional warps at an entry PC. Our single-hart kernels (bare-metal C) run entirely on warp 0/thread 0; the divergence asm test exercises the full 4×4 fabric.

5 · Memory Hierarchy

  • L1 icache / dcache per core, write-through dcache with per-bank organization.
  • L2 (per cluster) and L3 (chip) — at 1 core these levels are pass-through (L2_ENABLED/L3_ENABLED = 0); requests are simply forwarded.
  • External memory ports: MEM_NUM_BANKS = 2 banks, each moving one 64-byte (512-bit) line per transaction with a per-byte byteen write mask and an opaque tag for out-of-order response matching (our responder replies in order).
  • Local memory (LMEM) exists upstream but is unused here (LMEM_SIZE = 0 in the kernel launch DCRs).

7 · Memory Interface & Addressing

Requests are line-addressed per bank. With INTERLEAVE = 1 (verified against processor.cpp:357), the byte address of a request on bank b is:

byte_addr = (mem_req_addr * MEM_NUM_BANKS + b) * DATA_SIZE     // = (addr*2 + b) * 64

8 · DCR Registers & Boot Sequence

Device Configuration Registers program the kernel launch. The boot sequence below mirrors upstream processor.cpp exactly and is implemented twice: in the directed smoke TB and as the UVM vx_boot_seq.

#DCR addrRegisterValue (this env)
1–20x010/0x011KMU_STARTUP_ADDR 0/10x8000_0000 / 0
3–40x012/0x013KMU_ARG 0/10 / 0 (no kernel arg struct)
5–70x014–0x016GRID_DIM x/y/z1 / 1 / 1
8–100x017–0x019BLOCK_DIM x/y/z1 / 1 / 1
11–130x01A–0x01CCLUSTER_DIM / …1 / 1 / 1
14—LMEM_SIZE0
15—BLOCK_SIZE1
16–17—WARP_STEP x (=NUM_THREADS) / y,z4 / 0

Full launch flow:

  1. Assert reset 8 cycles, release, wait RESET_DELAY = 8 more.
  2. Load the program hex into the TB memory model at 0x8000_0000.
  3. Issue the 17 DCR writes above.
  4. Pulse start for one cycle.
  5. Serve memory requests; wait until busy is low for 100 consecutive cycles.
  6. Per core: DCR read of BASE_CACHE_FLUSH (0x000) to flush dirty cache lines to memory.
  7. Read results back from the TB memory model (exit code, done flag, output region).

9 · Program Exit Contract

Every kernel (via dv/sw/common/crt0.S, or hand-assembled in nop.hex) ends with:

sw   a0, 0x8348      # exit code = main() return value; 0 = PASS
li   t1, 0x600DC0DE
sw   t1, 0x8350      # done flag: proves the kernel actually executed
wsync                # drain pending stores
tmc  x0              # retire the warp

Two words are deliberate — each defeats a distinct false-pass mode:

  • Exit code 0 = PASS at 0x8348 keeps the image compatible with the simx golden simulator, which returns the exit word's low byte as its process return code (a non-zero "magic pass value" scheme made simx exit rc=222 and broke co-sim).
  • Done magic at 0x8350: unwritten memory reads back 0 — identical to a passing exit code. The magic word distinguishes "kernel ran and passed" from "kernel never ran". The scoreboard additionally requires n_rd > 0 (the core fetched something).

Resolver bug worked around: the config generator emits 0 for macros whose definitions reference SV package localparams. L2_MEM_PORTS/L3_MEM_PORTS resolve to min(L2_NUM_REQS, 2) where L2_NUM_REQS = 1 at this size; the frozen shim config hand-sets both to 1 (a 0 makes elaboration fail with a non-positive array bound in [VX_MEM_PORTS]).
