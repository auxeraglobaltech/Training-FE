1 · Introduction & Scope

UberDDR3 is an open-source, formally-verified DDR3 memory controller with an integrated PHY. We use it as third-party RTL (vendored at a pinned commit) and build a UVM verification environment around its native pipelined Wishbone user interface in Cadence Xcelium. The DDR3 device is the bundled Micron x16 behavioral model; the 7-series PHY primitives are simulated with the repo's bundled behavioral models, so no Xilinx/Vivado libraries are required. This document specifies the parts a verification engineer must know; the environment is described in the companion Verification Plan and Test-Case Catalog.

Vendored RTL under RTL/uberddr3/rtl is kept pristine. All verification work and any compatibility shims live under RTL/uberddr3/dv/.

2 · Architecture

A user issues read/write requests over Wishbone; the controller schedules DDR3 commands (activate / read / write / precharge / refresh), runs the PHY, and returns data. One Wishbone transfer moves one full 128-bit word (a complete DDR3 burst: 8 beats × 16 bits).

4 · Wishbone Interface (pipelined B4)

The user interface is a pipelined Wishbone. A request is presented with i_wb_cyc + i_wb_stb; it is accepted on any cycle where i_wb_stb && !o_wb_stall. Completions return later as o_wb_ack (with o_wb_data for reads). The i_aux tag is presented with each request and echoed on o_aux, enabling response matching; for in-order single-outstanding traffic, request/ack pairing is simply FIFO order.

5 · Address Map

The 24-bit word address packs {row, bank, column}. The low bits are the column (within a row), the middle 3 bits select the bank, and the high bits select the row:

FieldWord-address bitsWidth
Column (word)[6:0]7 (COL_BITS − log₂8)
Bank[9:7]3 (8 banks)
Row[23:10]14

Each word address holds one 128-bit value. The verification scoreboard models memory as a sparse map keyed by this word address.

6 · Clocks & Reset

Four clocks (generated behaviorally in the testbench): i_controller_clk (100 MHz), i_ddr3_clk (400 MHz, ¼ of the controller period), i_ddr3_clk_90 (90°-shifted, used when ODELAY_SUPPORTED=0), and i_ref_clk (200 MHz for IDELAYCTRL). Reset i_rst_n is held low ~1 µs at start. The user must not drive Wishbone traffic until o_calib_complete is high.

7 · Calibration

After reset the controller runs a power-on sequence (shortened by MICRON_SIM), programs the DDR3 mode registers, and calibrates the PHY: write leveling (align DQS to CK at the device) and read calibration (align the read-capture). It then asserts o_calib_complete. In this build calibration completes at ≈ 8.93 µs of simulated time; the verification environment waits on o_calib_complete before issuing any request.

The Micron model emits timing-check warnings (e.g. "500 µs required before CKE") because MICRON_SIM deliberately shortens the real-silicon power-on. These are expected and benign.

8 · PHY & Simulation Model

The PHY uses Xilinx 7-series primitives (OSERDESE2, ISERDESE2, IDELAYE2, ODELAYE2, IDELAYCTRL, IOBUF…). For simulation, the repo ships behavioral models of these primitives in testbench/models/, selected by +define+SIM_MODEL +define+NO_TEST_MODEL. This is the key to a vendor-free flow: the full controller + PHY simulate in Xcelium with no Xilinx unisim / glbl libraries. The DDR3 device is the Micron 8 Gb x16 model (testbench/ddr3.sv).

9 · DV Integration Shims (Xcelium compatibility)

The vendored RTL is iverilog/Vivado-clean but needs two small, value-preserving shims to elaborate under Xcelium's stricter checks. Both live in dv/shim/; upstream files are untouched.

ShimWhy
dv/shim/ddr3_controller.svXcelium forbids system-function calls and forward-referenced parameters inside constant functions (IEEE 1364 §10.3.5). Five $rtoi($ceil(a/b)) expressions were replaced by the exact integer ceil-division (a+b−1)/b, and get_slot() was changed to compute its needed values from locally-available parameters instead of forward-referenced localparams. Values are identical.
dv/shim/aximwr2wbsp.v, dv/shim/ddr3_top_axi.vOnly used by the (optional) AXI build — see §10. Not part of the verified Wishbone flow.

10 · AXI Wrapper — Known Limitation

UberDDR3 also ships an AXI4 wrapper (ddr3_top_axi) over a Wishbone bridge. We initially targeted it but found that, under Xcelium, the bridge's FIFO-fill counter powers up to X (iverilog and Vivado effectively 2-state-initialise it), which poisons the write-accept logic and blocks AXI writes. Calibration and AXI reads work; AXI writes do not complete. Multiple targeted fixes (calibration-gated reset, force-init, an X-immune bridge shim) did not fully resolve it, and the deeper layer is a skid/handshake timing interaction in the third-party bridge.

Decision: the verification environment is built on the native Wishbone interface, which is the controller's real user interface and is fully working (all tests pass). The AXI wrapper is documented here as a known limitation; it works in iverilog/Vivado and could be revisited with one of those simulators or a deeper bridge rewrite.
